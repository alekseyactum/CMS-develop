# Global Price Section Workbench

This document fixes the first detailed requirement slice for the CMS screen opened from:

```text
Global sections -> Prices
```

The screen edits the locale-specific `global_price` source section. It is not the page-owned price
section editor used inside a concrete practice/service/problem page.

## Scope

`global_price` is an independent `global_owned` section.

It is the upper shared price source for generated service-tree pages. Base non-regional generated pages
may inherit, override allowed fields, or append allowed local price content from this source. Regional
pages inherit through the base page price layer, not directly from the global source when a matching base
page exists.

The global price editor manages only the shared source for the active CMS locale.

## Locale Model

Global sections remain locale-specific section records.

```text
global_price / uk -> its own section and version history
global_price / ru -> its own section and version history
global_price / en -> its own section and version history
```

The active CMS locale defines the main editor state and the menu indicators. If the CMS is in `uk`, the
sidebar and the `global_price` screen show the status of `global_price / uk`.

The editor may show other locale tabs as supporting context, but other locales do not change the main
status of the current screen.

Do not introduce a separate multilingual field-level storage model for this section. The same locale-per-
section model should remain consistent across all CMS sections.

## Readonly Header And Editable Content

The top header fields are system-owned, read-only content:

```ts
{
  title: string;
  accentText: string;
  description: string;
}
```

They are defined in backend code registry per locale. They are not edited by the normal global price UI and
are not stored in `cms_section_versions.content_json`.

The editable persisted content is only:

```ts
{
  items: PriceItem[];
}
```

The backend must return a complete working/public payload by combining the read-only header with editable
items:

```ts
{
  title: string;
  accentText: string;
  description: string;
  items: PriceItem[];
}
```

This keeps the public frontend simple: preview and published snapshots receive a complete resolved price
payload and do not need to know about backend registry defaults.

`notes` is not part of the first `global_price` contract.

## Price Item Contract

Each item in `items` has this shape:

```ts
{
  id: string;
  title: string;
  price: number;
  priceMode: 'fixed' | 'from' | 'up_to';
  description: string;
}
```

Rules:

- `id` is generated by the frontend when the editor adds an item;
- backend validates that `id` exists, is unique inside `items`, and matches `^[a-z0-9_-]+$`;
- item order is the array order in `items`; do not add `sortOrder` in the first slice;
- there is no `enabled`/`disabled` item flag in the first slice;
- deleting an item removes it from local frontend state; on draft save, the new section version contains
  the remaining `items`;
- previously published or drafted versions still preserve deleted items in history, so rollback or
  creating a draft from a historical version can restore them.

## Editor Opening Rules

Opening the editor must not create database rows except the stable section record when it does not yet
exist.

Working content is selected like this:

1. If `latest_draft` exists, edit `latest_draft`.
2. If no draft exists but `current_published` exists, show a frontend-editable copy of current published
   content. Do not create a draft until save.
3. If neither draft nor published exists, show an empty editable structure:

```ts
{
  items: []
}
```

The editor response should expose ready-to-render working state:

```ts
{
  workingVersionRole: 'latest_draft' | 'current_published_copy' | 'empty_new';
  readonlyContent: {
    title: string;
    accentText: string;
    description: string;
  };
  editableContent: {
    items: PriceItem[];
  };
  workingContent: {
    title: string;
    accentText: string;
    description: string;
    items: PriceItem[];
  };
}
```

## Save Draft Flow

The editor has one real backend save operation for the current locale.

The request accepts only editable content:

```json
{
  "content": {
    "items": []
  }
}
```

Readonly header fields must not be accepted as part of save payload.

The save operation creates or updates the `latest_draft` for the active locale.

There is no separate validate-content endpoint for this screen. The draft save endpoint returns the result
of the attempt and diagnostics.

If there are no critical errors:

```ts
{
  saved: true;
  draftVersionId: string;
  diagnostics: Diagnostics;
  editor: GlobalPriceEditorState;
}
```

If there are critical errors:

```ts
{
  saved: false;
  draftVersionId: null;
  diagnostics: Diagnostics;
  workingContent: SubmittedWorkingContent;
  editor: GlobalPriceEditorState;
}
```

In this case no draft is created or updated. The response must still return enough submitted/working
content for the frontend to keep the form data visible.

Warnings do not block saving. Critical errors block draft creation/update and publish.

Card-level buttons in the UI must not imply server persistence. A per-item button may apply changes only
to frontend state. The real backend operation is the global section save button:

```text
Create draft / Save draft
```

## Validation Rules

`global_price` requires a domain-specific validator beyond the generic object/list shape validator.

Severity:

- `error` blocks draft save and publish;
- `warning` is visible but non-blocking;
- do not introduce a separate technical severity named `alert`; UI may display warnings as alerts if it
  wants.

Rules:

```text
items:
- required
- must not be empty
- every item is validated
- id required, unique, /^[a-z0-9_-]+$/

title:
- required
- <= 4: error
- 5..45: ok
- 46..99: warning
- >= 100: error

price:
- required
- number
- > 0
- <= 100000
- > 100000: error

priceMode:
- required
- one of fixed | from | up_to

description:
- required
- < 50: warning
- 50..200: ok
- 201..399: warning
- >= 400: error
```

Diagnostics for price items must be field-addressable:

```json
{
  "severity": "error",
  "code": "PRICE_TITLE_TOO_SHORT",
  "fieldPath": "items[1].title",
  "itemId": "court",
  "field": "title",
  "message": "Title must be longer than 4 characters."
}
```

`fieldPath` is the generic path. `itemId` and `field` are convenience fields for card UI.

## Top Section Indicators

The top area of the screen describes the current section state, not the full version history.

For the active locale, expose:

```ts
{
  status: {
    kind: 'ok' | 'warning' | 'attention' | 'error';
    label: string;
    priority: number;
  };
  facts: {
    hasDraft: boolean;
    hasPublished: boolean;
    draftVersionNo: number | null;
    publishedVersionNo: number | null;
    errorCount: number;
    warningCount: number;
    lastEditedAt: string | null;
    lastEditedBy: string | null;
    lastPublishedAt: string | null;
    lastPublishedBy: string | null;
  };
}
```

Status priority:

```text
1. error
2. attention
3. warning
4. ok
```

Rules:

- `error`: latest working version has critical errors;
- `attention`: no published version exists, or there is an unpublished latest draft;
- `warning`: warnings exist without errors/attention;
- `ok`: a published version exists, there is no draft, and diagnostics are clean.

For status diagnostics:

- if `latest_draft` exists, use diagnostics for `latest_draft`;
- otherwise use diagnostics for `current_published`;
- if neither exists, show an attention/not-created state.

Other locale states may be shown near tabs, but they are supporting information only.

For this cross-locale tab/header UI, the frontend should not call the full editor endpoint three times.
The backend exposes a lightweight diagnostics endpoint for one global section:

```http
GET /api/admin/global-sections/{sectionKey}/locale-diagnostics
```

It returns all supported locales in one payload:

```ts
{
  sectionKey: 'global_price';
  title: string;
  locales: Array<{
    locale: 'uk' | 'ru' | 'en';
    section: SectionRecord | null;
    draftVersion: SectionVersion | null;
    publishedVersion: SectionVersion | null;
    status: {
      kind: 'ok' | 'warning' | 'attention' | 'error';
      label: string;
      priority: number;
    };
    facts: {
      hasDraft: boolean;
      hasPublished: boolean;
      draftVersionNo: number | null;
      publishedVersionNo: number | null;
      errorCount: number;
      warningCount: number;
      lastEditedAt: string | null;
      lastEditedBy: string | null;
      lastPublishedAt: string | null;
      lastPublishedBy: string | null;
    };
    diagnostics: Diagnostics | null;
  }>;
}
```

This endpoint is read-only and should not create missing section records for unopened locales. The full
`GET /api/admin/global-sections/{sectionKey}/editor?locale=...` endpoint remains the source for the active
locale form content.

For a “current site” comparison panel, use the public-content endpoint:

```http
GET /api/admin/global-sections/global_price/public-content?locale=uk
```

It returns the current published price payload only:

```ts
{
  sectionKey: 'global_price';
  locale: 'uk' | 'ru' | 'en';
  publishedVersion: SectionVersion | null;
  readonlyContent: GlobalPriceReadonlyContent | null;
  editableContent: GlobalPriceEditableContent;
  workingContent: GlobalPriceReadonlyContent & GlobalPriceEditableContent;
  diagnostics: Diagnostics | null;
}
```

Use `editor` for the form and `public-content` for comparison with the version that is currently active
on the public side.

## Version History

The right-side history panel shows indicators for each version row only. It must not duplicate the top
section state.

The database lifecycle state remains:

```ts
'draft' | 'published'
```

The API should add a computed `versionRole`:

```ts
'latest_draft' | 'draft_history' | 'current_published' | 'published_history'
```

A previously published version that is no longer current remains `lifecycleState = 'published'` in the
database and appears in the UI as `versionRole = 'published_history'`.

Version history rows should include:

```ts
{
  sectionVersionId: string;
  versionNo: number;
  lifecycleState: 'draft' | 'published';
  versionRole:
    | 'latest_draft'
    | 'draft_history'
    | 'current_published'
    | 'published_history';
  changeReason: 'manual_edit' | 'rollback' | 'copy_from_version';
  sourceSectionVersionId: string | null;
  createdAt: string;
  createdBy: string | null;
  publishedAt: string | null;
  publishedBy: string | null;
  diagnostics: {
    status: 'ok' | 'warning' | 'error';
    errorCount: number;
    warningCount: number;
  };
  actions: {
    canView: boolean;
    canOpenInEditor: boolean;
    canPublish: boolean;
    canCreateDraftFromVersion: boolean;
  };
}
```

Actions:

- `latest_draft`: view, open in editor, publish;
- `draft_history`: view, create new latest draft from this version;
- `current_published`: view only;
- `published_history`: view, create rollback draft from this version.

Viewing a version opens it in the main form as read-only history preview. If the current form has unsaved
changes, the frontend should warn before switching view.

Creating a draft from history always creates a new version and makes it the latest draft. It must not move
old pointers backwards or mutate historical versions.

## Publish And System Impact

Global price publication is an independent global-section flow, not a page publish flow.

Publication is triggered from the version history action for `latest_draft`. The main editor form only
creates or updates draft content.

Publishing `latest_draft`:

- validates the draft again;
- creates a new published section version;
- updates `cms_section_current_versions.current_published_version_id`;
- attempts affected page snapshot rebuild according to the global price policy;
- returns affected pages/bindings and rebuild results in the publish response.

Affected pages are only pages whose current public snapshot would actually change:

- inherit: affected;
- append: affected;
- override: not affected;
- disabled optional price binding: not affected;
- pages without price slot: not affected.

If some affected snapshot rebuilds are `failed` or `skipped`, the section publish can still be successful.
The publish response must expose those rebuild statuses. They are follow-up page/snapshot work, not proof
that the global price version failed to publish.

The backend must not read or mutate unrelated page-owned drafts during global price rebuild.

Public preview and published page snapshots must receive the full resolved price payload:

```ts
{
  title: string;
  accentText: string;
  description: string;
  items: PriceItem[];
}
```

## Implementation Impact

Backend work:

- refine `global_price` schema to editable `{ items }` plus read-only header content by locale;
- add global price domain validation with `error` and `warning` diagnostics;
- change global price save response to return `saved: true | false` instead of only throwing on business
  validation failure;
- add `workingVersionRole`, `readonlyContent`, `editableContent`, and `workingContent` to the editor
  payload;
- extend history rows with computed `versionRole`, diagnostics, and actions;
- add create-draft-from-version behavior for historical draft/published versions;
- keep publish response as the source of affected snapshot rebuild status.

Frontend work:

- render the top state block from backend-provided `status` and `facts`;
- use `workingContent` for visual preview/rendering and `editableContent` for form state;
- send only `{ content: { items } }` on draft save;
- treat card-level apply buttons as local UI state, not backend persistence;
- use history actions from the backend instead of inferring what each version can do;
- show publish rebuild failures from publish response.

Persistence impact:

- no new table is required for price items;
- no item-level enabled/disabled flag in the first slice;
- no field-level localization tables;
- no persisted resolved overlay versions;
- existing `cms_sections.locale`, `cms_section_versions.content_json`, and current version pointers remain
  the storage model.
