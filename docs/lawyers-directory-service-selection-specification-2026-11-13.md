# Отбор адвокатов по практике и услуге

Дата: 13.11.2026. Статус: согласованное ТЗ для CMS-бэка и site-front.

В каталоге адвокатов заменяем фильтр города зависимым выбором услуги. Состав подходящих
адвокатов определяет CMS по прямым оценкам компетенций, а случайный порядок показа формирует
site-front. Остальное поведение поиска и каталога сохраняем.

Это требования к реализации, а не сообщение о выполненной выкладке. Публикация этого ТЗ
не разрешает изменять данные ERP, запускать миграции или перепубликовывать страницы.

## Область изменений

Изменяется каталог `/lawyers`, `/ru/lawyers`, `/en/lawyers`: секции `lawyers_filter` и
`lawyers_listing`, их preview, сборка опубликованного снимка и применимое автообновление.

Не меняем подборки адвокатов на главной, «Про нас», страницах практик, услуг и проблем,
CTA-блоки, профиль адвоката и его список практик. Данные города, региона и офиса не удаляем;
убираем только фильтр города из интерфейса этого каталога. Географические правила других
страниц сохраняются.

Для каталога настоящее ТЗ заменяет прежнее правило принадлежности практике по любой
компетенции её поддерева. Остальные потребители продолжают работать по
[согласованным правилам точного уровня](lawyer-exact-qualification-selection-2026-10-24.md).

## Согласованное поведение каталога

В строке отбора остаются три элемента:

1. Поиск по имени или фамилии.
2. Практика.
3. Услуга выбранной практики вместо города.

Услуга недоступна до выбора практики; показываем подсказку «Спочатку оберіть практику»
с соответствующими переводами. После выбора практики исходное значение — «Усі послуги».
Можно выбрать практику без услуги. При смене или очистке практики выбранная услуга
сбрасывается; услугу чужой практики сохранять нельзя.

Поиск и выбранные условия действуют совместно через **И**. Сохраняем текущие правила
поиска: подстрока имени без учёта регистра, debounce 200 мс, немедленное применение очистки.
Селекторы применяются сразу, без новой кнопки «Застосувати». Режимы «Пошук / Відбір»
из административного списка публикаций сюда не переносим.

При изменении условий снова показываем первые 20 совпадений. «Показати ще» раскрывает
следующие 20 уже полученных карточек, без нового запроса к CMS, с сохранением текущего
перевода фокуса к первой раскрытой карточке. Не меняем содержимое и действия карточек.

## Допуск по компетенциям

Общие требования остаются действующими: адвокат доступен для публичного каталога,
локализованная страница опубликована и доступна по маршруту. При отборе по компетенциям
учитываются только активные и успешно разрешённые в CMS записи. Скрытые или недоступные
профили не добавляются ради заполнения выдачи. Применяется одна и та же проверка для
вариантов фильтра и карточек.

| Условия пользователя | Какая оценка допускает адвоката |
| --- | --- |
| Практика и услуга не выбраны | Действующий общий состав публичного каталога, без нового порога компетенций |
| Выбрана только практика | Прямая компетенция этой практики с оценкой **≥ 2**, без услуги и проблемы |
| Выбрана услуга | Прямая компетенция этой услуги внутри выбранной практики с оценкой **≥ 2**, без проблемы |

Для выбранной услуги оценку практики дополнительно не проверяем. Например, адвокат
с оценкой услуги 2 и оценкой практики 1 подходит для услуги, но не для выдачи только по практике.

Оценки дочерних проблем, родительских или соседних объектов не заменяют прямую оценку
и не повышают её. Отсутствующая оценка, `null` и значение меньше 2 не допускают адвоката.
Значение ровно 2 допускает; условие не должно превращаться в `> 2`.
Эти требования к компетенции и оценке применяются только при выборе практики или услуги.
В общем каталоге без фильтров адвокаты без компетенций остаются на прежних условиях.

При нескольких действительных записях одного точного уровня используем максимальную
прямую оценку и возвращаем одну карточку адвоката. Запись с неразрешёнными дочерними
внешними идентификаторами нельзя принять за прямую компетенцию родителя только потому,
что её внутренний ID услуги или проблемы оказался пустым.

## Списки практик и услуг

Практика появляется в списке, если среди доступных адвокатов есть хотя бы один:

- с прямой оценкой этой практики ≥ 2; **или**
- с прямой оценкой хотя бы одной её услуги ≥ 2.

Услуга появляется только внутри своей практики и только при наличии хотя бы одного
доступного адвоката с прямой оценкой этой услуги ≥ 2. Оценки проблем здесь не учитываются.
Действующие правила видимости справочников сохраняются. Наличие отдельной опубликованной
страницы услуги не является новым условием для её использования как значения фильтра:
выбор услуги фильтрует адвокатов, а не открывает страницу услуги.

Варианты не строятся по первым 20 карточкам, введённому имени или текущей выдаче только
по практике. Особенно важен случай, когда практика доступна за счёт услуги, но прямых
компетенций практики нет: выдача только по практике может быть пустой, однако список
её услуг должен оставаться доступным. После выбора услуги подходящие адвокаты появляются.
Не подменяем пустую выдачу более широким отбором.

Названия вариантов соответствуют текущей локальности. Практики и услуги сортируем
по отображаемому названию с учётом UA/RU/EN; для одинаковых названий используем стабильный ID.
Системные значения «Усі практики» и «Усі послуги» остаются первыми.

## Случайный порядок на site-front

CMS не перемешивает адвокатов. Она сохраняет детерминированный порядок по компетенциям
и существующим дополнительным критериям как порядок по умолчанию.

Site-front один раз при новом открытии каталога создаёт равномерную случайную перестановку
полного полученного набора карточек, например алгоритмом Fisher–Yates. Не использовать
`sort(() => Math.random() - 0.5)`.

- Перемешиваем до применения ограничения первых 20 карточек, а не каждую порцию отдельно.
- Поиск и фильтры оставляют подходящее подмножество в уже созданном случайном порядке.
- Ввод текста, очистка, выбор фильтров, «Показати ще», перерисовка компонента и повторное
  получение того же набора не создают новую перестановку.
- При переходе в профиль и возврате сохраняются условия, случайный порядок, раскрытое
  количество и положение прокрутки. Это отдельное требование новой реализации, а не
  утверждение о наличии такого восстановления в текущем фронте.
- Новое открытие каталога или полное обновление страницы создаёт новую перестановку.
  Случайное совпадение двух перестановок допустимо: нельзя требовать разных результатов
  на каждом открытии, особенно при одной или двух карточках.
- Состояние не смешивается между локальностями и разными маршрутами. Данные и порядок
  другой языковой версии не должны перезаписывать текущую.
- Не допускаем несовпадения SSR и hydration, визуального перескакивания карточек при
  последующих действиях и расхождения визуального порядка с порядком DOM и клавиатурного фокуса.

В основном сценарии с JavaScript высокая оценка не гарантирует первое место. Условия
допуска при этом не ослабляются. Без JavaScript сохраняем рабочий серверный каталог
в детерминированном порядке; случайный порядок — ответственность фронта, не новая задача CMS.

Перестановка обеспечивает равные шансы внутри полного переданного набора, но не обещает
одинаковое число показов за конечный период. Счётчики показов, персонализация и серверная
ротация в задачу не входят.

## Наша часть CMS-бэка

### Отбор и модель данных

1. Расширить существующую модель каталога прямыми компетенциями услуг и изменить
   принадлежность практике на прямую оценку согласно таблице выше.
2. Использовать существующие ERP-справочники и компетенции. Не создавать новый процесс
   импорта, не менять оценки ERP и не требовать новых ERP endpoints для этого отбора.
3. Разделить принадлежность практике по прямой оценке и доступность практики как родителя
   подходящих услуг. Список вариантов практики шире её прямой выдачи — это намеренное правило.
4. Не ограничивать состав top-N по компетенции перед клиентским перемешиванием. Проверить
   действующие технические пределы чтения, чтобы весь доступный каталог попадал в согласованный
   снимок. Если полный набор не помещается в существующий контракт, это требует отдельного
   решения до выкладки; нельзя объявлять случайность глобальной, перемешивая только top-N.

### Контракт preview и опубликованного снимка

Используем текущий публичный механизм чтения страницы и секции `lawyers_filter` /
`lawyers_listing`. Отдельный поисковый endpoint и запрос по каждому адвокату не нужны.

Целевое расширение действующего payload:

- `lawyers_filter.payload.services[]`: `id`, `practiceId`, локализованный `title`;
  `practices[]` сохраняет действующую форму и получает описанные выше правила доступности.
- `lawyers_listing.payload.items[].practiceIds` и `practiceScores[]` описывают только
  прямые действительные оценки практик ≥ 2, без агрегирования дочерних уровней.
- `items[].serviceIds[]` и `serviceScores[]` добавляют принадлежность услугам и прямые оценки;
  запись оценки содержит `serviceId`, `practiceId`, `score`.
- Массивы нового контракта присутствуют всегда, включая `[]`. Существующие поля карточки,
  города, офиса и прочие потребители не удаляются.
- Числа и связи в payload согласованы: frontend не должен повторно вычислять компетенции
  из других справочников или угадывать родителя по названию.
- Действующий `order` и метаданные ранжирования должны соответствовать новому составу
  и прямым оценкам. Они не обязывают новый site-front возвращать сортировку по компетенциям.

Точные TypeScript-типы, примеры и правила совместимости закрепить в техническом контракте
CMS-бэка до передачи Юрию. Присутствие полного нового контракта нужно отличать от старого
снимка без `services` и связей услуг: пустой новый список не равен отсутствию поддержки.
Старые агрегированные оценки практик нельзя выдавать за прямые оценки нового режима.

### Единообразие и проверки

Одинаковые правила нужны в секционном preview, preview страницы, обычной и exact-публикации,
а также при применимом scoped-обновлении опубликованного каталога. Обновление не должно
захватывать неопубликованные правки других секций.

Добавить unit/интеграционные проверки точного уровня, порога 2, отсутствующих оценок,
дубликатов, неактивных и неразрешённых компетенций, видимости и опубликованности профиля,
локализованных названий, полного набора карточек и согласованности вариантов с принадлежностью.
Проверить отсутствие лишних запросов на каждую карточку и регрессий у остальных подборок.

## Завдання Юрію для site-front

Обсяг — публічний каталог адвокатів у UA/RU/EN. CMS-front, профілі адвокатів, інші
підбірки та форми заявок у цій задачі не змінюємо.

1. Замінити селектор «Місто» на «Послуга». Залишити пошук за ім'ям і селектор практики.
   Послуги брати з нового payload CMS, а не з меню сайту чи окремих ERP-запитів.
2. До вибору практики показувати недоступний селектор послуг із поясненням. Після вибору
   показувати лише її послуги, починаючи з «Усі послуги». Зміна практики очищає послугу.
3. Без послуги відбирати за `practiceIds`; із послугою — за `serviceIds`, без додаткової
   вимоги входження до `practiceIds`. Пошук за ім'ям поєднується з відбором через **І**.
   Не враховувати компетенції проблем і не будувати власну ширшу формулу допуску.
4. Зберегти чинний пошук підстроки без урахування регістру, debounce 200 мс, негайне
   очищення, застосування селекторів без кнопки та розкриття по 20 карток без нового API.
   Не додавати запуск лише за Enter або режими з адміністративного списку публікацій.
5. Один раз рівномірно перемішувати повний набір до відбору й перших 20 карток. Надалі
   зберігати цей порядок під час пошуку, зміни умов, рендерів і «Показати ще».
   Повторне використання порядку CMS за оцінками після вибору практики чи послуги не потрібне.
6. Після повернення з профілю відновлювати умови, перестановку, кількість відкритих карток
   і прокрутку. Не змішувати контекст різних мов. Додати це явно, не покладатися лише на
   випадкове збереження локального стану компонента браузером.
7. Пропустити нові поля через типи, loaders і нормалізатори без втрат. Не вважати старий
   snapshot або помилку читання готовим новим контрактом. Під час перехідної сумісності
   не показувати нібито робочий вибір послуги на неповних даних; `services: []` є коректним
   порожнім списком, а не приводом повертатися до міста.
8. Показувати зрозумілий порожній результат, зберігаючи вибрані умови та доступні послуги.
   Забезпечити клавіатурний доступ, зрозумілу назву й стан селектора, повідомлення про
   кількість результатів та відповідність порядку фокуса фактичному порядку карток.
9. Додати регресійні тести. Перевірити широку й мобільну версії, усі три мови, hydration,
   повернення з профілю та відсутність додаткових запитів під час клієнтського відбору.

## Совместные критерии приёмки

Для одной практики и её услуги подготовить изолированные fixtures:

| Адвокат | Прямая оценка практики | Прямая оценка услуги | Оценка проблемы этой услуги | Только практика | Выбрана услуга |
| --- | --- | --- | --- | --- | --- |
| A | 2 | 1 | 5 | Да | Нет |
| B | 1 | 2 | Нет | Нет | Да |
| C | 4 | Нет | 5 | Да | Нет |
| D | Нет | Нет | 5 | Нет | Нет |
| E | Нет | 3, но компетенция неактивна | Нет | Нет | Нет |

Дополнительно проверить:

1. В отдельном fixture оставить только B: практика остаётся в вариантах. Выдача только
   по ней пуста, но услугу можно выбрать и получить B. Поиск по имени не удаляет варианты
   из селекторов.
2. Оценка ровно 2 допускает, ниже 2 и `null` — нет. Высокие оценки других уровней не помогают.
3. Дубликаты прямых компетенций не дублируют карточку. Скрытый/неопубликованный профиль,
   неразрешённая компетенция и несоответствие услуги практике не попадают в выдачу.
4. Услуга без подходящего адвоката отсутствует; чужая услуга не остаётся после смены практики.
5. Пустые и непустые значения поиска сочетаются с отбором, а сортировка вариантов соответствует
   локальности. Поведение базового поиска не изменилось.
6. Фиксированный источник случайности в тестах позволяет проверить перестановку без
   нестабильного требования «два открытия обязательно дают разный порядок».
7. Множество карточек до и после перемешивания совпадает, пропусков и дубликатов нет.
   Адвокат из конца исходного списка может оказаться среди первых 20.
8. Изменение условий, повторный рендер и раскрытие следующей порции не перемешивают список.
   Новая порция не повторяет уже показанные карточки. Возврат из профиля восстанавливает контекст.
9. Preview, новый опубликованный снимок и применимое автообновление дают один и тот же
   допустимый состав. Случайность принадлежит site-front и не изменяет CMS/ERP-данные.
10. Общий каталог без фильтров, остальные страницы, CTA-подборки и профиль сохраняют свои
    действующие правила. Без JavaScript каталог остаётся доступным.

## Порядок реализации и подключения

Сначала CMS-бэк готовит общий selector, расширение снимка, технический контракт и тесты.
Затем Юрий подключает согласованный контракт и клиентское перемешивание. До подключения
обеих сторон старые снимки не должны ошибочно считаться новыми данными.

Исторические версии и существующие опубликованные снимки не переписываем в обход
штатного процесса. Новый код сам по себе не меняет сохранённый снимок. Для применения
к уже опубликованному каталогу потребуется согласованное штатное обновление нужных
страниц UA/RU/EN; массовая перепубликация остальных страниц в эту задачу не входит.
