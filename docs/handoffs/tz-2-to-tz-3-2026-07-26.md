### Problem fixed

A page row could exist while one or more schema-required page-section bindings were absent. Previously
different surfaces could disagree: the page existed in the catalog, but matrix/editor/publish/coverage
could treat it as ready, missing, or irreparable.

### New common state

Page authoring/workbench exposes:

```ts
interface PageAuthoringInitializationState {
  status: "initialized" | "repair_required";
  expectedSectionSlots: number;
  boundSectionSlots: number;
  missingSectionSlots: string[];
}
```

Semantics:

- `initialized`: every applicable section slot is bound;
- `repair_required`: the page row exists but applicable section bindings are missing.

Regional applicability is respected. A national-only or otherwise non-applicable slot is not considered
missing for the regional row.

### Mutation rules

- Full matrix/list GET paths stay read-only.
- A read-only matrix detects `repair_required` but does not mutate the DB.
- Normal open/editor/bootstrap paths lazily create only missing bindings.
- Existing section content and bindings are not overwritten.
- Successful explicit bootstrap of an existing incomplete page returns:
  - `created: false`
  - `repaired: true`
- Repeating bootstrap after repair is idempotent and returns `repaired: false`.
- No background scan or automatic whole-DB repair runs after deploy.

### Workbench behavior

Incomplete rows expose critical:

```text
PAGE_AUTHORING_REPAIR_REQUIRED
```

The diagnostic includes missing slot keys. Preview/publish readiness is blocked until repair.

Bulk bootstrap plan statuses:

- `will_create`
- `will_repair`
- `already_exists`
- `blocked`

Bulk execution statuses:

- `created`
- `repaired`
- `already_exists`
- `blocked`
- `failed`

Summaries add `willRepair` and `repaired`.

### Reference coverage behavior

Coverage status is now:

- `missing`
- `repair_required`
- `initialized`
- `published`
- `blocked`
- `hidden`

Descendant coverage adds:

- `repairRequired`
- `initialized`
- `published`

An existing repair-required page counts as existing, but the descendant group is not complete.

Detailed contract:

- `docs/source-diagnostics-and-bulk-bootstrap-task.md`

## Completed Backend Change: Base Row Country Label

Frontend reported an unstable title workaround for practice/service/problem matrices.

Affected endpoint shape includes:

```text
GET /api/admin/page-workbench/page-types/problem_page?locale=uk&sourceId=...
```

The same issue applies to:

- `practice_page`
- `service_page`
- `problem_page`

Behavior before the fix:

- generated base variant has `kind: "base"`;
- base variant has `region: null`, `regionSlug: null`;
- base `regionTitle` is `null`;
- base `title`/`displayTitle` is the source object title;
- regional variants have a real localized `regionTitle`.

Current frontend fallback:

```js
row?.regionTitle || row?.title || row?.rowKey
```

Some UI levels then special-case `kind === "base"` and replace the value with `Ukraine`. The workaround is
unstable because not every endpoint/component applies the same replacement.

Implemented contract:

- backend returns a stable localized country/scope title for every base row:
  - `uk`: `Україна`
  - `ru`: `Украина`
  - `en`: `Ukraine`
- preserve `kind: "base"`, `region: null`, and `regionSlug: null`;
- preserve `sourceTitle` as the practice/service/problem title;
- use one backend-owned display contract consistently in matrix, navigation summary, generated source row,
  page row refresh, open response, and history-related row responses;
- frontend should render the returned field and remove `kind === "base"` text replacement.

The implementation makes `regionTitle` backend-owned and non-null for generated base rows of
`practice_page`, `service_page`, and `problem_page`. Consumer review confirmed that region identity is
determined through `kind`, `region`, `regionSlug`, and region IDs; `regionTitle` is display data and is
safe to populate for the country-wide scope. `practice_collection_page` and other generated page types
remain unchanged.

Backend validation coverage:

## Reviews Runtime-Only Contract Update (2026-07-27)

The reviews section contract for generated `practice_page`, `service_page`, and `problem_page` pages is
now intentionally runtime-only:

- remove `practice_reviews_block`, `service_reviews_block`, and `problem_reviews_block` from current page
  schemas;
- expose one standalone required runtime slot per page: `practice_reviews`, `service_reviews`, or
  `problem_reviews`;
- runtime payload contains `title`, `source`, and `items`;
- `title` is backend-owned and localized by page locale: `Відгуки`, `Отзывы`, or `Reviews`;
- there is no editable reviews `title` or `lead`, and CMS must show the section as read-only;
- historical snapshots are not rewritten and may still contain the old `*_reviews_block`.

During rollout, public consumers must support both snapshot shapes without rendering duplicate reviews:

```js
const title =
  reviewsRuntime?.payload?.title ??
  legacyReviewsBlock?.payload?.title ??
  localizedReviewsTitle(locale);
```

When the runtime payload has `title`, ignore the historical block. New publications use only the runtime
slot; an old currently published snapshot keeps working through the legacy fallback until it is
republished.
