# Проект ТЗ на переводы CMS из украинского оригинала

Дата: 3 ноября 2026 года. Статус: проект для согласования после сверки с кодом.

Цель — заменить независимое редактирование языковых версий управляемыми переводами. Украинский является исходным языком редакционного контента; RU и EN сохраняют существующие страницы, секции, историю, валидацию и публикацию. Главный приоритет — минимальные изменения действующего пользовательского процесса.

Документ описывает целевую доработку, а не уже работающий API. Создание этого проекта не разрешает включение облачных сервисов, миграции, перевод содержимого, публикацию страниц или выкладку.

## 1. Согласованные границы

- Исходный язык страниц, собственных секций и глобальных блоков — украинский. В API используется существующий код `uk`; обозначение UA в интерфейсе сохраняется.
- RU/EN — производные версии с соответствующей структурой. Самостоятельное создание другой структуры и независимое авторство на этих языках не добавляем.
- Перевод выполняет CMS через Google Cloud Translation. Поставщик один; экран выбора поставщиков и новая роль переводчика не нужны.
- RU/EN доступны для просмотра, навигации, валидации и обычной публикации. Текст исправляется отдельным действием «Исправить перевод» в существующем редакторе.
- Устаревание перевода — warning, не дополнительный запрет публикации. Отдельного подтверждения качества или актуальности, в том числе по фрагментам, нет.
- Валидация, открытие матрицы и чтение страницы не запускают перевод и не создают версии.
- Первичного или массового запуска нет. Старые данные постепенно актуализируются через предупреждения, явные команды и штатные изменения источника.
- URL, slug, canonical, редиректы и существующие правила маршрутизации этой задачей не реформируются. Предложение сделать общий украинский slug не принято.

## 2. Когда создаются переводы

| Событие | Действие CMS | Что происходит с опубликованным содержимым |
| --- | --- | --- |
| Сохранён украинский черновик секции | Перевод не запускается | Ничего |
| Успешно опубликовано изменённое украинское содержимое | Фоновый перевод изменившихся частей в RU и EN; новые обычные черновики затронутых секций | RU/EN остаются прежними до штатной публикации |
| Повторно опубликовано то же значимое содержимое | Нет повторного перевода и лишних версий | Ничего |
| В CMS изменился действительный исходный публичный текст справочника | Фоновый перевод изменившегося текста | После сохранения результата — обычное обновление зависимых страниц нужного языка |
| Повторный импорт справочника без изменения исходного текста | Нет перевода | Сохраняется действующее поведение no-op |
| Выполнена явная команда нового перевода | Полный новый перевод выбранного объёма в выбранный язык | Для секций — только черновики; для справочников — сохранение перевода и штатная очередь обновлений |

Для страницы источник — содержимое, действительно попавшее в опубликованную UA-версию, а не текущие формы, последние редакторские черновики или более новые неопубликованные зависимости. При раздельной публикации контента и SEO обрабатываются только фактически опубликованные изменения соответствующего scope.

Для глобальной секции событие — её собственная успешная публикация на украинском. Перевод глобальной секции создаётся один раз, а не отдельно для каждой использующей её страницы.

Публикация UA и сохранение источника не ждут Cloud Translation. Недоступность переводчика не откатывает опубликованное или сохранённое содержимое. Неудавшиеся задачи остаются в фоне с диагностикой и ограниченными повторами.

## 3. Версия целой секции и перевод изменённых частей

Единица сохранения результата — новая версия существующей секции. Отдельную систему версий полей, абзацев и переводов не создаём.

При автоматическом переводе сравниваем новый опубликованный источник с исходными данными, на которых основан последний сохранённый перевод. За основу целевого содержимого берём последнюю применимую сохранённую RU/EN-версию, включая незавершённый черновик; исторический или уже потреблённый указатель не должен подменять актуальную рабочую версию.

| Изменение источника | Новый перевод |
| --- | --- |
| Текст поля или блока не изменился | Сохранить существующий перевод, включая ручные исправления |
| Текст изменился | Перевести заново; прежняя ручная правка остаётся в предыдущей сохранённой версии |
| Блок добавлен | Перевести новый блок |
| Блоки переставлены | Сохранить переводы по идентификаторам, применить новый порядок |
| Блок удалён | Убрать из нового черновика; историю не изменять |
| Изменились общие нетекстовые данные | Применить их по существующим правилам поля без машинного перевода |

Гранулярность использует существующую структуру данных:

- В content builder уже есть `blockId`, а для соответствующих вложенных элементов — `itemId`, `rowId`, `columnId`. Перевод и перестановка сохраняют их.
- В списках профиля адвоката сохраняются существующие ID элементов и общие факты.
- Обычное текстовое поле переводится целиком.
- Старое или общее rich-text поле без надёжной идентичности элементов обрабатывается целиком как одно поле. Универсальную миграцию всех абзацев на новые ID в эту задачу не включаем. Следовательно, сохранение ручной правки неизменённого абзаца внутри изменившегося такого поля не обещается.
- При отсутствии доказанной исходной связи у старого перевода нельзя надёжно вычислить изменившиеся части. При следующем разрешённом запуске переводится соответствующий объект целиком; до запуска старое содержимое сохраняется с warning.

Повторная публикация UA не ждёт публикации предыдущего перевода. Создаётся следующий целевой черновик по этим же правилам. Предыдущие сохранённые версии остаются в истории; опубликованный RU/EN-снимок не заменяется.

Если из нескольких секций переведена только часть, успешные черновики сохраняются. Неудавшиеся секции повторяются отдельно. Внутри секции наполовину полученный результат не записывается как новая завершённая версия.

## 4. Ручные команды

| Команда | Объём | Результат |
| --- | --- | --- |
| Сделать новый перевод страницы | Собственные переводимые секции текущей RU- либо EN-страницы в доступном пользователю scope | Новые черновики с полным переводом опубликованного украинского источника |
| Сделать новый перевод секции | Одна собственная секция; для глобального содержимого — через глобальный редактор | Новый черновик этой секции |
| Сделать новый перевод записи справочника | Переводимые публичные поля одной записи в выбранном целевом языке | Новые значения существующих полей переводов, затем штатное обновление зависимых страниц |
| Исправить перевод | Разрешённые текстовые поля в существующем редакторе | Для секции — обычная новая сохранённая версия; для справочника — существующее сохранение перевода |

Ручной новый перевод намеренно обрабатывает выбранный объём полностью, даже если исходный текст не менялся. Ручные исправления в этот результат автоматически не переносятся. Для секций они остаются в истории; для справочников не обещается новая история версий, которой сейчас нет.

Команды выполняются для текущего выбранного языка, не для RU и EN одновременно. Для отзывов целевым может быть также украинский, если это перевод и исходный язык отзыва другой.

Новая явная команда создаёт новый черновик секции даже при совпадении результата с предыдущим текстом. Повтор того же принятого запроса после потери ответа или повтор попытки worker не создаёт дубликаты.

Команда страницы не редактирует глобальные источники и runtime-секции справочников, не подменяет их локальными копиями. Она не даёт контентному редактору права изменять SEO или наоборот. Backend возвращает разрешённый объём; фронт не обещает перевод недоступных пользователю секций.

Для глобальных секций сохраняются существующие команды публикации и распространения опубликованного глобального содержимого. Новый перевод глобальной секции сам его не публикует.

## 5. Происхождение и актуальность

Для каждой новой переводной версии требуется отдельная серверная информация об источнике: его тип, идентификаторы, язык, опубликованная версия или ревизия и хеш значимых исходных данных. Точные имена API-полей и таблиц определяются при реализации; это не существующий контракт.

Хеш учитывает текст, структуру и общие данные, которые действительно должны отразиться в соответствующем переводе. В него не включаются timestamps, актор, номер версии сам по себе и другая техническая информация, не меняющая результат. Правила извлечения и канонизации версионируются технически.

- Другой ID исходной версии при том же значимом содержимом сам по себе не означает устаревание.
- Украинский неопубликованный черновик не делает перевод устаревшим относительно сайта.
- Источник сравнения для секции страницы — соответствующая секция текущей опубликованной UA-страницы с тем же типом, сущностью и географическим контекстом.
- Новый RU/EN-черновик не делает старую опубликованную RU/EN-версию актуальной. Рабочая и опубликованная версии оцениваются отдельно.
- Ручная коррекция переводной секции наследует связь со своим источником; она не получает автоматически ссылку на более новый UA-источник.
- Публикация, создание опубликованной копии, копирование исторической версии и восстановление должны сохранять достоверное происхождение. Копия старого перевода не считается новым переводом текущего источника.
- Для справочника без версий используется хеш и сохранённое представление исходных переводимых данных, достаточное для следующего сравнения по полям. Новую редакционную систему версий справочников не создаём.

Существующий `sourceSectionVersionId` означает основу новой версии внутри той же секции. Использовать его вместо отдельной межъязыковой связи запрещено: это разные отношения.

## 6. Валидация и предупреждения

Все обычные проверки содержимого сохраняются. Успешный ответ переводчика не является доказательством корректной формы, юридической точности текста или готовности к публикации.

Содержательно незавершённый, но допустимый для хранения результат сохраняется как черновик с обычной диагностикой. Например, проблему длины SEO-текста показываем редактору, а не исправляем скрытым сокращением текста. Редактор вручную создаёт следующую версию той же секции. Существующие ограничения структуры и безопасного хранения не отменяются: повреждённый JSON или неправильные типы не записываются под видом незавершённого черновика.

Для переводов добавляются обычные причины уровня warning:

- источник изменился — перевод устарел;
- достоверной связи со старым источником нет — актуальность не определена.

Тексты и точные машинные коды определяются в контракте реализации. Ручное «подтвердить актуальность» отсутствует: новая достоверная связь появляется при выполнении перевода автоматически.

Предупреждение поднимается через существующий механизм диагностики секции, страницы, языка и бокового меню. Не создаётся по одному warning на каждое изменённое поле. Для одной секции и целевого языка сводка содержит одну причину неактуальности с деталями о рабочем и опубликованном состоянии, без двойного счёта той же причины. Отдельный актуальный черновик не должен скрывать предупреждение о всё ещё устаревшем опубликованном переводе.

Диагностика записи справочника и зависимых страниц использует существующие правила own/linked и дедупликации. Все остальные ошибки и предупреждения по-прежнему суммируются как конкретные проблемы, а не как количество проблемных секций.

Не смешивать три разных состояния:

1. актуальность перевода относительно источника;
2. существующий `coverage` — актуальность вычисленных диагностических итогов;
3. существующий `draft_stale` — состояние наследования и опубликованных зависимостей.

Перевод может иметь warning при полностью вычисленной диагностике `coverage=complete`. Переводное устаревание не записывается в `draft_stale` и не создаёт новый запрет публикации. Уже действующие ошибки валидации и ограничения публикации продолжают действовать.

## 7. Языковые страницы и существующая публикация

После первой публикации UA автоматически создаются недостающие RU/EN-страницы и необходимые собственные секции; переводы сохраняются черновиками. Уже существующие языковые страницы, секции и историю не пересоздаём.

Для ранее опубликованной UA-страницы без RU/EN-цели предлагается точечное уточнение реализации: создание недостающей цели выполняется также при последующей подходящей UA-публикации либо по той же явной команде «Сделать новый перевод страницы» из существующего контекста отсутствующего выбранного языка. Иначе путь «warning → исправление» недоступен: переводного редактора ещё нет. Новый экран и массовая обработка не требуются; простое переключение языка или валидация ничего не создают.

Используются существующие доменные правила идентичности, bootstrap и маршрутов. Нельзя сопоставлять страницы только по slug, названию или типу секции. Нельзя скопировать неопубликованную украинскую структуру под видом опубликованной. Неоднозначность соответствия или конфликт существующего маршрута возвращается как техническая проблема, а не исправляется переименованием URL.

Региональное наследование, границы собственных и общих источников сохраняются. Перевод не должен превращать унаследованную секцию в произвольную независимую локальную копию. До реализации составляется матрица поддерживаемых типов и контекстов. Неподдерживаемый существующим bootstrap или publication adapter контекст остаётся незавершённым объёмом доработки; сообщение «недоступно» не означает выполненное требование. Исключение типа страниц из согласованного охвата требует отдельного решения.

На сайт новые языковые страницы и переводы попадают только через обычную публикацию. Разделение content/SEO, права и первое SEO-подтверждение сохраняются. Подтверждение украинского SEO не переносится на перевод; автоматического SEO-подтверждения нет. Результат публикации и доставка в кеш остаются разными состояниями.

Скрытые и выключенные слоты сохраняют действующую семантику. Перевод не включает их самостоятельно и не публикует содержимое неопубликованных черновиков. Изменения структуры берутся из фактически опубликованного украинского источника.

## 8. Публичные данные ERP и владение переводами

CMS становится владельцем производных переводов публичных данных для сайта. ERP остаётся владельцем своих исходных данных. Обратную запись переводов в ERP не добавляем, внутренние ERP-процессы и интерфейсы других языков не реформируем.

Важное различие в текущем коде: исходное ERP-имя и публичное украинское имя в CMS — не всегда одно поле. У адвокатов и ряда других справочников публичный украинский текст уже редактируется в CMS. Адаптер выбирает действительный публичный источник, например `translations.uk.publicName`, а не автоматически подставляет `sourceName`.

Следовательно, перевод запускается при изменении эффективного исходного публичного текста в CMS: штатным редактором либо импортом, который действительно изменил этот текст. Изменение внутреннего ERP-поля не должно затирать отдельный CMS-owned публичный текст.

В область входят существующие публичные текстовые поля практик, услуг, проблем, регионов, офисов, адвокатов, отзывов и вакансий. Точный реестр полей строится по схемам и текущим DTO; произвольные строки из ERP и JSON целиком не отправляются в переводчик.

Связи, ID, даты, числовые факты, порядок, общие признаки, файлы и служебные поля не переводятся. Для структурированных образования и опыта сохраняются существующие ID, годы и порядок. Существующие URL-поля не передаются переводчику и обрабатываются по действующим правилам. Служебный `dealNumber` не становится публичным текстом.

Переводимые alt и подписи изображений обрабатываются у их существующего владельца; новый медиафайл или отдельная медиабиблиотека переводов не создаются. Общую карточку медиа нельзя изменить как побочный эффект команды перевода одной страницы.

### 8.1. Обновление зависимых страниц

- Изменение исходного публичного текста вызывает перевод; для обычных справочников UA-потребители обновляются существующим порядком. Для отзыва с достоверным оригиналом другого языка это потребители языка оригинала: например, RU при русском оригинале. Остальные языки обновляются после сохранения соответствующего перевода.
- Сохранение готового RU-перевода создаёт работу для действительно зависящих RU-страниц; аналогично для EN.
- Изменение общих нетекстовых данных может затрагивать все языки независимо от готовности текста. Эти два типа изменений не смешиваются.
- Используются текущие очереди, паузы страницы и языка, задержки, точечная пересборка опубликованных снимков и доставка кеша.
- Редакторские черновики не попадают в такую пересборку. Повтор идентичного результата не создаёт лишних обновлений строк и уведомлений.
- Не допускается выдавать fallback исходного текста за готовый актуальный перевод. Существующие fallback-контракты сами по себе не дают права установить признак актуальности.

Текущая очередь имеет конкретные обработчики, а не универсальную поддержку любых справочников. В реализации нужно проверить покрытие всех переводимых публичных полей и добавить только недостающие обработчики в существующую инфраструктуру.

### 8.2. Отзывы и настоящий оригинал

Для отзывов действует согласованное исключение: перевод непосредственно с настоящего оригинала, независимо от его языка. Исходный текст сохраняется. Для русского оригинала RU не является переводом, а UK и EN переводятся с RU, не через промежуточный UK.

Сверка выявила реальную интеграционную зависимость. Сейчас ERP запрашивает отзывы Google отдельно для языков и сохраняет полученные тексты в `description`, `description_ru`, `description_en`. Пара «настоящий исходный текст + его язык» надёжно не сохраняется. Мигратор передаёт `description` как `text` и UK-текст, а другие колонки — как RU/EN-переводы. Поэтому нынешний `text` нельзя автоматически объявить оригиналом.

Необходимая доработка ERP — сохранять настоящий оригинал и его язык/происхождение. Мигратор передаёт их CMS через уточнённый контракт. Названия вроде `originalText` и `originalLanguage` пока являются предложением, не существующими полями API. Определение языка уже переведённой строки не восстанавливает потерянный оригинал.

До появления достоверного источника старый отзыв сохраняется с честным состоянием неизвестного происхождения. Нельзя обещать перевод непосредственно с оригинала, используя вместо него украинскую машинную копию. Массовое повторное получение старых отзывов и переписывание данных не входят в эту задачу.

Если для такого отзыва запрошен новый перевод, CMS сохраняет существующие значения и возвращает понятную причину отсутствия достоверного оригинала. Показывается warning, а не ложный успех или подмена источника. Это ограничение возможности выполнить перевод, не новый запрет публикации существующего содержимого.

Мигратор должен перестать перезаписывать CMS-owned производные переводы таких отзывов, в том числе явными `null`. Сейчас такая перезапись существует в `upsert` и `update-existing`; нужен согласованный переход контракта на обеих сторонах. Старый отправитель после переключения не должен молча уничтожать новые CMS-переводы.

Сохраняются отправка отзыва по действию пользователя ERP, правила полной сверки, `source + externalId`, видимость, связи и смысл `null` для действительного исходного текста. Отсутствующее поле и явное очищение источника не отождествляются. Старые переводные поля ERP не удаляются: у них могут быть другие потребители.

### 8.3. Вакансии

Согласованное новое поведение заменяет прежнее правило «украинский текст во всех языках». CMS хранит RU/EN-переводы публичных названия и описания, позволяет исправлять и повторно переводить их в рамках разрешений.

Исходные название/описание, активность, видимость, сортировка, размещение и прочие ERP-owned факты остаются недоступными для редактирования в CMS. Подпись размещения (`workLocationLabel`) проверяется в выбранном языке через соответствующие названия и форматирование; сами географические связи не меняются. Процесс отправки и обработки отклика не меняется.

Нужно изменить реальный контракт вакансий: сейчас их языковые представления — readonly-копии UK, переводной PUT запрещён, runtime читает украинские source-поля, а обновление опубликованных вакансий имеет отдельный explicit-only путь. Требуются локализованные чтение/сохранение/диагностика и подключение к согласованной очереди обновлений с действующими паузами. Простого включения одной кнопки недостаточно. Новые черновики и версии вакансий не вводятся.

## 10. Минимальная техническая схема

Ниже — проект реализации согласованных правил; точные таблицы, DTO, API-маршруты и способ вызова worker оформляются в кодовом контракте до интеграции фронта. Не использовать этот раздел как перечень уже доступных endpoints.

### 10.1. Данные и события

- Добавить служебное происхождение переводов секций и справочников; не перегружать `sourceSectionVersionId`, `draft_stale` или `coverage`.
- Добавить долговечные задачи с источником, целевым объектом/языком, режимом automatic incremental либо explicit full, request/operation identity, попытками и безопасной диагностикой.
- Намерение перевода фиксируется вместе с успешным изменением источника в локальной транзакции. Внешний запрос к Google не выполняется внутри транзакции сохранения или публикации.
- Сохранение результата перевода или ручная правка целевого текста не являются изменением оригинала и не запускают цикл новых переводов. Нужные события обновления страниц при этом сохраняются.
- Для секций сохранять происхождение на каждой новой версии, включая опубликованные копии. Не менять задним числом provenance старой версии ради отметки актуальности.
- Для справочников сохранять техническое представление исходных полей для сравнения; это не пользовательский архив редакционных версий.
- В реестре полей явно разделить переводимые тексты, копируемые общие данные, защищённые технические поля и уже локализуемые существующим форматтером значения.

### 10.2. Worker и защита от гонок

Для секций worker получает зафиксированный опубликованный UA-источник; для справочников и отзывов — успешно сохранённый действительный оригинал и его хеш, без отдельного вымышленного этапа публикации. Вместе с этим фиксируется текущее целевое состояние. Перевод выполняется вне блокировок БД, затем результат атомарно проверяется на применимость и сохраняется.

Если за время запроса пользователь сохранил новую целевую версию или изменился источник, результат не перезаписывает новое состояние. Задача перечитывает актуальную основу и повторяется по согласованным правилам. Это защита от потери данных, не новый этап согласования редактором и не запрет вручную публиковать устаревший сохранённый перевод.

Один новый ручной запрос может создать новую версию при совпавшем тексте; повтор того же запроса возвращает прежний результат. Существующий guarded Save намеренно делает no-op для идентичного содержимого и запрещает `forceCreate`. Для перевода требуется отдельный защищённый режим сохранения; обходить это старым незащищённым Save нельзя.

Попытки ограничены по времени, числу и параллельности. Перезапуск процесса не теряет работу. Неудавшаяся секция не блокирует другие. Не сохранять частичный ответ и не повторять уже завершённые секции в рамках того же запроса.

Переиспользовать существующие подходы bounded worker и отложенных задач, но не выполнять долгие вызовы Google внутри нынешнего бюджета HTTP-dispatch обновлений страниц. Конкретный способ пробуждения выбирается отдельно в технической реализации; существующий caller, расписание и его таймауты не считаются автоматически расширенными. Новая пользовательская панель планировщика не требуется.

### 10.3. Google Cloud Translation и содержимое

Провайдер получает только извлечённые разрешённые тексты, не весь JSON секции, служебные поля, заявки клиентов или внутренние данные ERP. HTML/rich text обрабатывается с сохранением разрешённой структуры; IDs, ссылки, медиа и общие факты проверяются при обратной сборке. Переводчик не является редактором структуры документа.

Конкретный режим, модель, лимиты и конфигурация сервиса являются техническими параметрами, а не новыми настройками редактора. До включения необходимы проверки на русских и английских переводах типовых текстов, списков, ссылок, таблиц, имён и юридических формулировок. Успешный тест не заменяет текущий редакторский процесс.

Официальная документация предусматривает перевод текста/HTML и ограничения размера запросов: [перевод текста v3](https://docs.cloud.google.com/translate/docs/advanced/translating-text-v3), [квоты и лимиты](https://docs.cloud.google.com/translate/quotas). Разбивка длинного текста выполняется технически и не превращается в отдельные пользовательские версии фрагментов.

Включение API, настройка служебного доступа, региона, квот и ограничений расходов выполняются только отдельным согласованным cloud-шагом по gcp-infra-playbook. Секреты и клиентские ключи не передаются браузеру и не записываются в ТЗ. В журнале задач достаточно ID, безопасных кодов ошибок, времени и объёмов; полный текст и персональные данные не логируются.

## 11. Задачи по системам

### CMS backend

1. Реестр источников и переводимых полей, отдельное происхождение, хеширование и сравнение существующих устойчивых элементов.
2. Очередь, интеграция Cloud Translation и защищённое сохранение результатов с идемпотентностью.
3. События после UA-публикаций и изменений эффективных исходных полей справочников; отсутствие перевода на чтении/валидации.
4. Автоматическое создание отсутствующих языковых страниц из опубликованного источника без изменения маршрутизации.
5. Три ручных команды, исправление переводов и серверная защита производных полей от произвольного независимого редактирования, включая старые пути Save.
6. Предупреждения и поддерживаемые агрегаты всех уровней; сохранение публикации и раздельной content/SEO-модели.
7. Владелец CMS-переводов отзывов, уточнение входного контракта и защищённый переход со старого отправителя.
8. Вакансии: реальные переводы, разрешённые коррекции, локализованный runtime, диагностика и интеграция обновления страниц.

### CMS frontend

1. Сохранить матрицы, языковую навигацию, редакторы, контентбилдер, историю и стандартное сохранение/публикацию.
2. Производные тексты показывать readonly по умолчанию; «Исправить перевод» открывает существующую working copy. Проверить и другие пути изменений: создание пустого черновика, rollback/copy, состав секций и переключатели структуры.
3. Добавить команды нового перевода в согласованных местах и текущем языке. Использовать backend capabilities, не выводить права из языка, цвета или warning.
4. Передавать происхождение, рабочую/опубликованную актуальность и состояние фоновой операции через типы, gateway, BFF и loaders без потерь.
5. Показывать серверные предупреждения и итоги обычными компонентами. Не подменять ими `coverage` и не пересчитывать суммы самостоятельно.
6. После окончания перевода обновлять список версий и диагностику, не стирая несохранённый текст открытого редактора.
7. У вакансий убрать предположение «все языки равны UK», показать целевой перевод и разрешённые действия над ним. ERP-owned источник оставить readonly.

### Мигратор

1. Для управляемых CMS-переводов прекратить отправку производных языковых текстов как авторитетных значений; прежде всего исправить текущий импорт отзывов.
2. Передавать настоящий оригинал отзыва и его язык/происхождение после соответствующей доработки ERP.
3. Использовать согласованный новый контракт и в обычной отправке, и в полной сверке. Сохранить идентичность, связи, видимость, idempotency и правила отсутствующих записей.
4. Не вызывать переводчик, не получать прямой доступ к CMS-БД и не инициировать первичный массовый перевод.

### ERP backend

Необходимое изменение — надёжное сохранение оригинала отзыва и его языка/происхождения для передачи в CMS. Другие ERP-данные, процесс отправки отзывов по действию пользователя, задачи компетенций, формы заявок и внутренние языковые поля не переделываются без отдельной необходимости.

### Публичный сайт

Нового пользовательского механизма перевода на сайте нет. Сайт продолжает отображать опубликованный snapshot своего языка. В проверенном коде карточки вакансий уже читают `title`/`description` из CMS, поэтому прежде всего нужны локализованный backend-payload и регрессионная проверка карточки, окна вакансии и контекста отклика, а не переписывание сайта.

## 12. Переход и зависимости

- Добавочные миграции хранят техническое состояние; не изменяют старые тексты, историю, URL, опубликованные снимки и не создают массовые задания.
- Legacy-перевод без достоверной связи получает warning. Не проставлять всем старым RU/EN текущую UA-версию ради зелёной диагностики.
- Сначала подготовить совместимый backend-контракт и защиту CMS-owned полей; затем согласованно переключить мигратор и UI. Порядок включения не должен оставить два конкурирующих владельца переводов.
- Включение фоновой обработки и Cloud Translation проводится отдельно после проверки миграций, прав, контрактов отправителей и квот. Публикации и очереди не считаются автоматически разрешёнными этим документом.
- По отзывам готовность ERP передавать настоящий оригинал является реальной зависимостью полной приёмки. До неё можно реализовывать и тестировать остальные части, но нельзя объявлять выполненным перевод отзывов непосредственно с оригинала.
- Старые данные и уже опубликованные языковые версии не исчезают при ошибке worker или откате приложения. Откат не должен возвращать отправителю право молча перезаписать новые CMS-переводы.

## 13. Критерии приёмки

1. Сохранение UA-черновика, открытие редактора, матрицы, меню и валидация не вызывают Cloud Translation и не создают версии.
2. UA-публикация создаёт работу из действительно опубликованной версии. Неопубликованные content/SEO-изменения и зависимости не попадают в перевод.
3. Неизменённые поля и блоки с устойчивыми ID сохраняют перевод и ручные исправления; изменения, удаление и перестановка отражаются правильно. Для rich text без ID проверяется согласованная гранулярность целого поля.
4. Повторная UA-публикация до выпуска RU/EN создаёт следующую актуальную целевую версию, не уничтожая историю и не меняя публичный снимок.
5. Ручной полный перевод страницы/секции работает только для выбранного языка, не трогает глобальные/runtime-источники и не превышает права. Повтор одной операции не дублирует результат; новая отдельная команда создаёт новый черновик.
6. Сбой одной секции оставляет успешные черновики других; частичный результат одной секции не сохраняется. Перезапуск worker и потеря ответа не теряют работу.
7. Конкурирующие Save и публикация источника не приводят к потере ручных правок, движению целевого head назад или признанию старого результата актуальным.
8. Ручное исправление создаёт обычную новую версию секции с сохранённой исходной связью. Исторические версии не меняются.
9. Раздельно проверяются опубликованный перевод и черновик. Отсутствующая связь и устаревание дают warning во всех согласованных уровнях; новые блокировки публикации и ручные подтверждения не появляются.
10. Диагностические итоги не дублируют одну причину; `coverage` описывает вычисление итогов, не качество или актуальность перевода. Политика и зависимости read model обновляются при добавлении правил.
11. Обычные ошибки готовности переведённого содержимого видны в черновике. Текст не сокращается скрыто; структурно недопустимый результат не записывается.
12. Отсутствующие языковые страницы создаются из опубликованного источника с правильной сущностью и контекстом; существующие страницы/URL/история сохраняются. Перевод не создаёт SEO-подтверждение.
13. Для справочников переводится именно публичный источник; изменение внутреннего ERP-имени не затирает отдельное публичное имя CMS. Повторный импорт без изменений не вызывает перевод.
14. Готовый перевод справочника сохраняется вместе с техническим происхождением и вызывает точечные события нужного языка. Соблюдаются существующие паузы и задержки; черновики страниц не публикуются.
15. Старый формат мигратора не может молча перезаписать CMS-owned перевод. Проверены явные null, пустой текст, массивы, очистка источника, обычная отправка и полная сверка.
16. Отзыв переводится непосредственно с достоверного оригинала; для старого отзыва без такого оригинала нет ложного признания источника или массовой переделки данных.
17. Вакансии отображаются и корректируются в нужной локали, но ERP-owned поля остаются readonly. Отклик, видимость и критерии доступности вакансии не меняются.
18. Миграции и включение механизма не запускают первичную или массовую обработку; публичные данные без явной публикации/штатного refresh не заменяются.

Проверки гонок и транзакций проводить на изолированной тестовой БД. Синтетические тесты не должны публиковать или переписывать данные develop/release. Проверки развёрнутых сред и расходующие квоту реальные переводы согласуются отдельно.
