# Лицензия: согласованная структура и требования к backend

Дата: 2026-09-27.

Статус: продуктовые решения согласованы; backend реализован в рабочей ветке
`codex/license-page-backend` на базе `c085375`. Контракт реализации описан в
`docs/license-page-backend-contract-2026-09-27.md`.
Это исходный код, не подтверждение деплоя или наличия страницы в общей БД.
Контент, языковые правила редиректов и связь баннера нужно настроить при включении.
Приём и доставка заявок отложены; публичный контракт явно запрещает отправку.


## 1. Назначение и подтверждённые решения

Это отдельная страница лицензионного партнёрства с адвокатами, не страница вакансий.
Существующую `career_page` и её ERP-вакансии не заменяем и не переименовываем.

Цель: объяснить модель сотрудничества и взаимные ожидания, предложить развитие
индивидуальной практики или офиса и привести посетителя к общей заявке.

- Одна украинская страница `/license`; код языка в API/БД — `uk`, в интерфейсе — UA.
- `/ru/license` и `/en/license` перенаправляются на `/license` с HTTP 301.
- RU/EN-копий контента не создаём.
- Все тексты, фотографии и карточки заполняются вручную в CMS, без импорта из ERP.
- В блоке поддержки ровно четыре карточки. Анимированная смена — ответственность фронта.
- Оба предложения ведут к общей форме, подставляя формат; его можно изменить в форме.
- Обязательны имя, телефон, город и формат сотрудничества.
- Рассказ о специализации, опыте и планах необязателен.
- Email посетителя и загрузка резюме не нужны.
- Заявка должна поступать на email и в ERP; реализацию приёма и доставки отдельно
  согласуем на завершающем этапе подготовки сайта к запуску.

Наша часть — backend, схема, валидация, версии, публикация, публичный контракт и маршруты.
CMS frontend и публичная вёрстка — Юрий. Backend не задаёт тайминги и способ анимации.
Шапка, практики в футере и футер остаются общими элементами сайта.

## 2. Секции страницы

Тип: уже зарезервированный `lawyer_license_page`. Обычный жизненный цикл CMS:
черновик, валидация, preview, публикация, версии, откат. Отдельная система хранения
лендингов не нужна. Семь содержательных секций плюс техническая SEO-секция.

| Секция / slotKey | Данные CMS | Поведение |
| --- | --- | --- |
| `seo` | Стандартные SEO-поля | Штатный механизм; только украинская страница |
| Первый экран / `license_hero` | Надзаголовок, H1, описание, фоновое изображение, подпись CTA | CTA ведёт к общей форме |
| Роли сторон / `license_roles` | Заголовок, фотография, заголовки и тексты двух сторон: адвокат и Actum | Статический блок; стык-пазл относится к вёрстке |
| Модель / `license_model` | Акцентная строка, основной текст | Объяснение лицензионной модели |
| Поддержка / `license_support` | Заголовок, подзаголовок, четыре карточки: заголовок, описание, иллюстрация | Backend отдаёт четыре элемента в определённом порядке; смену выполняет frontend |
| Форматы / `license_formats` | Заголовок, описание, подпись действия для каждого из двух форматов | Переход к форме с выбранным форматом |
| Взаимные ожидания / `license_expectations` | Общий заголовок, два блока текста с фотографиями | Одна секция с упорядоченными элементами; чередование сторон задаёт вёрстка |
| Заявка / `license_application` | Заголовок, пояснение, подписи/подсказки полей, подпись кнопки, тексты состояний формы | Содержимое формы отделено от будущего механизма приёма и доставки |

Порядок секций соответствует макету. Все семь секций обязательны; отключение не разрешено,
чтобы CTA не вели на отсутствующую форму. Права редактора и версии используют
существующие механизмы CMS. Проверять согласованность CTA и доступности целевой формы.
Изображения используют существующие media references; содержательные изображения имеют alt.
Цвета, фигуры, тени и параметры анимации не превращать в бизнес-поля backend.

Вложенные элементы валидировать как предметный контракт, не как произвольный JSON.
Незавершённые черновики допустимы по общим правилам; при публикации проверять полноту,
ровно четыре карточки и оба формата сотрудничества. При сборке публичного payload
разрешать media references, в том числе внутри массивов карточек и текстовых блоков.

## 3. Форматы и данные заявки

Стабильные машинные значения:

- `individual_practice` — развитие индивидуальной адвокатской практики;
- `office` — развитие офиса в своём городе.

Подписи редактируются в CMS; значения и обязательность полей — контракт, не настраиваемый
редактором конструктор формы. Изменение подписи не меняет смысл переданного формата.

| Поле | Обязательность | Смысл |
| --- | --- | --- |
| `name` | Да | Имя посетителя |
| `phone` | Да | Контактный телефон |
| `city` | Да | Город; техническое предложение — текст, без связи с ERP-офисом |
| `cooperationFormat` | Да | Один из двух форматов |
| `about` | Нет | Специализация, опыт и планы |

Это состав будущей заявки, а не объявление уже работающего endpoint. Не добавляем
`vacancyId`, email заявителя, резюме или организацию партнёра. Не используем API откликов
на вакансии как готовый приёмник: у него другой контракт и другой бизнес-процесс.

CTA первого экрана ведёт к форме без навязанного формата;
CTA двух предложений передают свой формат, который остаётся изменяемым.
Использовать фиксированный якорь общей формы и необязательное значение формата, не
произвольный внешний URL. Scroll/focus и передача выбора внутри страницы — frontend.

Персональные данные заявок не относятся к контенту страницы: они не должны попадать
в версии страницы, публичный JSON, SEO или медиатеку.

## 4. Языки и маршруты

Техническая модель: национальная singleton-страница `lawyer_license_page`,
`locales: ['uk']`, без региональных вариантов. Запретить создание/публикацию RU/EN-копий
через прямой API. Закрепить `/license` как инвариант типа, а не только route template,
который можно заменить произвольным входным `pagePath`.

Языковые алиасы отдают серверный HTTP 301, а не украинский HTML с HTTP 200 и не
JavaScript-переадресацию. Backend выдаёт решение через существующий route resolver;
frontend-сервер сайта применяет статус и Location.

Реализация использует два явных правила существующего реестра редиректов,
направленных на pageId украинской страницы. Подготовка и активация после публикации —
часть контролируемого включения страницы. Не создавать вторую систему редиректов и
не вставлять ранний `if(path)` в обход проверок владения маршрутом и доступности цели.
При коллизии с существующей страницей/правилом остановиться, ничего не перезаписывать.

Оба алиаса должны вести непосредственно на канонический `/license`. До публикации
цели — штатный 404, при инфраструктурном сбое — штатный 503, без публичного использования
черновика. Origin берётся из конфигурации окружения, не из текстового поля секции.

В sitemap включать только опубликованный украинский URL. Не объявлять несуществующие
RU/EN-переводы через hreflang. Матрицы/диагностика CMS не должны считать отсутствие
RU/EN-копий ошибкой. Навигация CMS должна учитывать единственную доступную локаль.
Публичный переключатель учитывает редиректы, не называя украинский текст переводом.

## 5. Стыковки с существующими страницами

### Баннер карьеры

Предыдущее ТЗ `career_partner_banner` требовало опубликованную цель на том же языке.
Теперь нужно узкое исключение: баннер UA/RU/EN-карьеры может ссылаться на опубликованную
украинскую `lawyer_license_page`. Предпочтителен прямой `/license`, без промежуточного
редиректа. Для остальных типов страниц проверки локали не ослаблять.

CMS frontend должен позволять выбрать украинскую цель из редактора RU/EN-баннера.
Это дополнение к правилу ссылки, не изменение локализации карьеры или ERP-вакансий.

### Отметка адвоката

`hasLicensePartnership` остаётся ERP-признаком адвоката; он не управляет содержимым
страницы. Название организации в публичную отметку не добавляем. Ссылка из профилей
разных языков ведёт на опубликованную украинскую страницу.

Способ проверки доступности цели зафиксировать при интеграции с frontend: один boolean
адвоката не подтверждает, что `/license` опубликована. Если будет добавлено поле в
публичные snapshots адвокатов, потребуется явная пересборка соответствующих страниц;
не считать, что они автоматически изменятся при публикации «Лицензии».

## 6. Отложенный этап доставки

По решению пользователя реализацию отдельно обсуждаем перед запуском сайта. Сейчас
не выбираем получателя, ERP-endpoint, настройки очереди/повторов, SLA или новые секреты.
Не используем автоматически `global_career_form.hrEmail`: это настройки вакансий,
а не согласованный получатель партнёрских заявок.

Без реального сохранения заявки нельзя показывать успешную отправку. Готовность контента
не равна готовности формы к запуску. Приём и оба канала доставки — отдельный пункт
предпусковой приёмки. Если канал не готов, поведение согласуется явно, без имитации успеха.

Позже определить хранение и доступ, серверную валидацию, антиспам, повторы, сбои каналов,
настройки email и ERP-контракт. Согласованные поля и форматы повторно не обсуждаем.
