# Кэширование публичного сайта на Next.js и CDN

Дата согласования: 17 ноября 2026 года.

Статус: согласованная продуктовая модель и план внедрения. Технические решения из раздела 12
требуют проверки до включения. Этот документ не подтверждает завершённую реализацию.

**Сейчас выполняется только подготовка. Кэш не включать.** Документ не разрешает создание
облачных ресурсов, изменение IAM, runtime, DNS, доступности сайта, индексации или публикаций.
Такие действия выполняются отдельно, с подтверждением владельца и по `gcp-infra-playbook`.

## 1. Цель и границы

Неизменившиеся публичные страницы должны многократно обслуживаться без повторной сборки в
Next.js и без чтения CMS. Основной механизм актуализации: длительный кэш и надёжный адресный
сброс при изменении публичного состояния, а не постоянное истечение короткого TTL.

Область: `cms-back`, `site-front`, инфраструктура публичного сайта и существующий журнал
операций в `cms-front`. ERP, редакторские данные и механизмы принятия заявок не перерабатываются.

Основания:

- [Release contour, Decisions 27 и 28](release-contour-requirements.md#decision-28-frontend-cache-and-revalidation).
- [Контракт штатного обновления страниц](stale-page-refresh-contract-2026-10-12.md#публикация-и-кэш).
- [Backend implementation requirements](backend-implementation-requirements.md).
- [ТЗ заглушек карты и ограничений Google](office-map-placeholders-and-google-budget-specification-2026-11-11.md).
- Правила GCP, разрешений, выкладки и отката из соседнего `gcp-infra-playbook` имеют приоритет
  для инфраструктурных действий. До чтения фактического cloud state требуется его preflight.

При конфликте требований не включать спорный слой и не менять старый контракт молча.

## 2. Слои и единицы кэширования

Опубликованный снимок CMS является источником публичного содержимого, а не HTML-кэшем.
Фронт не пересобирает снимок из редакторских секций и не обращается к черновикам при cache miss.

В проверенном коде `site-front` публичная сборка использует два самостоятельных ответа:

- `GET /api/public/pages/by-route?route=...`: готовые публичные данные страницы на основе снимка;
- `GET /api/public/layout?locale=...`: общий layout, включая шапку, футер, контакты и конфигурацию карты.

Ответ страницы может содержать актуальные дополнения к снимку, например языковые связи.
Поэтому один `snapshotId` не обязательно описывает версию всего HTTP-ответа.

```text
CMS: публичный ответ страницы + публичный layout
                      |
Next.js: штатный серверный кэш этих ответов в одном экземпляре, затем рендер
                      |
CDN: готовый HTML и совместимые ответы клиентских переходов
                      |
Браузер: отображение страницы и длительный кэш версионированных файлов
```

Кэш данных Next.js хранит готовые ответы, а не отдельные заголовки, описания или редакторские
поля. На первом этапе не добавляем самостоятельный постоянный HTML-кэш внутри Next.js и
дублирующий TTL-кэш тех же публичных ответов внутри `cms-back`.

**Уточнение от 17.11.2026:** на текущем этапе исходим из одного обслуживающего экземпляра
`site-front` в Cloud Run и используем штатный локальный серверный кэш Next.js. Redis и другое
внешнее хранилище кэша в этот этап не входят. Это целевая архитектура, а не подтверждение или
изменение фактических Cloud Run limits. Перед включением нужно отдельно проверить её выполнение.

Потеря локального кэша при перезапуске означает холодное чтение актуальных данных CMS, а не
потерю контента. Дедупликация в рамках одного запроса не заменяет межзапросный кэш. При переходе
к нескольким обслуживающим экземплярам заново согласуем хранение и инвалидацию до масштабирования.
Смену ревизий/сборок и поздние ответы всё равно проверяем в G3/G5. Раннее предложение Redis,
а также его отдельные TTL 7 дней/24 часа и бюджеты памяти не являются принятым решением.

## 3. Согласованная политика хранения

| Объект | Браузер | CDN | Обновление |
| --- | --- | --- | --- |
| Версионированные CSS, JS и шрифты | До 1 года, immutable | До 30 дней | Новый URL при изменении файла |
| Публичные оригиналы изображений | До 1 года, immutable | До 30 дней | Новый URL при замене |
| Публичные уменьшенные изображения, WebP/AVIF | До 1 года для неизменяемого варианта | До 30 дней | Новый исходный URL и раздельные варианты |
| Публичные PDF | До 1 года, immutable | До 30 дней | Новый URL при замене документа |
| Публичный HTML | HTTP-кэш не сохраняет для повторной выдачи, no-store | Ориентир 30 дней | Событийный сброс |
| RSC и prefetch-ответы Next.js | Отдельная политика клиентской навигации | Только после доказанной совместимости вариантов | Сброс вместе с затронутой страницей |
| Готовые публичные ответы CMS в Next.js | Не самостоятельный браузерный API-кэш | Не публикуем CMS-back как общедоступный origin | 30 дней в штатном кэше Next.js; досрочная событийная инвалидация |

TTL означает допустимый срок повторного использования, а не гарантированное хранение:
редко используемый объект может быть вытеснен раньше. См. [Cloud CDN TTL](https://docs.cloud.google.com/cdn/docs/using-ttl-overrides).

### 3.1. Изменённые решения обсуждения

Раннее предложение хранить HTML в CDN только 60 секунд не принято как итоговая архитектура.
Общие 60 секунд / 5 минут больше не являются гарантированным аварийным пределом устаревания
всего сайта. Правило ограничения долгого HTML остатком такого короткого TTL также не применяется
как универсальная политика. Иначе согласованный длительный HTML-кэш фактически не работал бы.

**Согласованное уточнение от 17.11.2026: срок данных в штатном кэше Next.js — 30 дней
(2592000 секунд).** Он относится к полному успешному публичному ответу страницы, отдельно для
каждого URL и языка, и общему публичному layout по языку, исключая только `officeMap`.
Не разбиваем эти ответы на отдельные заголовки или поля. Числа 300/60 секунд не переносить
из старых механизмов; прежние Redis TTL 7 дней/24 часа также не применяются.

При неизменном публичном состоянии запись можно повторно использовать до 30 дней; обычный HIT
не продлевает этот срок бесконечно. После истечения следующий запрос к origin получает актуальные
данные CMS перед новым заполнением кэша. Не обновлять возраст старого значения и не наполнять
CDN на следующие 30 дней устаревшим ответом фоновой ревалидации. Истечение не запускает новый
планировщик, массовый прогрев или публикацию страниц.

Изменение опубликованного состояния принудительно инвалидирует затронутые данные раньше TTL:
Next -> проверка актуального origin -> purge CDN -> проверка CDN. Ожидание 30 дней не заменяет
доставку, повторы или защитные действия при отказе. Потеря записи, вытеснение или перезапуск
дают холодное чтение CMS. Срок не является обещанием физического хранения.

Preview, черновики, admin, персональные данные, команды и Google admission не получают
30-дневный кэш. Конфигурация карты сохраняет отдельное требование свежести до 60 секунд.
Решение не назначает 30 дней клиентскому Router Cache или RSC/prefetch в CDN. G1 теперь проверяет
реализацию принятого срока, точные keys/tags/API, вытеснение и ресурсы, а не выбирает TTL заново.

Сохраняется целевой штатный срок доставки изменения: **до 30 секунд от активации публичного
состояния**. Это контролируемый SLO, а не гарантия при отказе инфраструктуры. Согласованные
паузы до активации снимка не входят в этот отсчёт.

### 3.2. Файлы и браузер

- Не перезаписывать байты по URL, объявленному immutable. Исключения со стабильным URL
  сначала перевести на версионированную адресацию или исключить из длительной политики.
- Смена фото или PDF требует обновления ссылок и затронутого HTML, а не удаления старых
  файлов из всех браузеров. Уже полученную публичную копию принудительно отозвать нельзя.
- Изменение `alt`/`title` относится к данным и HTML; само по себе не требует нового файла.
- Старые файлы сборок должны оставаться доступны для уже открытых вкладок. Срок их хранения
  и защита от несовместимости сборок входят в G5; одного наличия файлов в CDN недостаточно.
- Для изображений различаем исходник, его ревизию, ширину, качество и формат. Не отбрасываем
  параметры доступа к медиа. Наличие токена не делает закрытый файл публичным.
- `next/image` выбирает формат по `Accept`. Передача этого заголовка к origin сама по себе
  не доказывает правильность CDN-ключа; требуется проверенное разделение вариантов.
  См. [Next.js Image](https://nextjs.org/docs/app/api-reference/components/image#formats).
- Подготовка не должна самовольно отключать уже существующий браузерный кэш файлов.

### 3.3. HTML, RSC и адаптивность

Один адаптивный HTML можно использовать для разных ширин экрана, если различия создают CSS
и клиентская логика. Не дробить HTML-кэш по каждой ширине viewport. При реальном серверном
различии ответов нужен проверенный признак варианта в ключе либо обход кэша для этих ответов.

Ключи изолируют окружение, host, путь, язык и влияющие на ответ варианты. Не нормализовать
пути, query или заголовки с изменением их смысла. Не смешивать HTML, RSC и разные prefetch-ответы.
Сохранить необходимые `rsc`, `_rsc` и другие параметры установленной версии Next.js.

RSC не исключается из задачи навсегда: без него внутренние переходы продолжат нагружать
Next.js. Однако неподтверждённые варианты обходят CDN и не входят в заявление о полной готовности.
Точный TTL RSC и политика Router Cache входят в G2, а не считаются автоматически согласованными
на 30 дней. См. [Next.js CDN caching](https://nextjs.org/docs/app/guides/cdn-caching).

HTTP no-store не является командой обновить уже открытую вкладку. Автоматическая смена текста
в открытых вкладках не требуется. Возврат назад, prefetch и клиентская навигация проверяются
отдельно: серверный purge не очищает память всех браузеров.

### 3.4. Исключения и запрет кэширования

Не включать в общий публичный кэш CMS/admin, preview, черновики, персонализированные ответы,
резюме, заявки, команды изменения данных, сессии, разрешения Google-карты и проверки лимитов.
Не помещать пользовательские или краткоживущие служебные токены в 30-дневный HTML.

Ошибки, неполные обязательные данные и деградировавший HTML не сохранять как успешную страницу
на 30 дней. На первом этапе также исключить HTTP-редиректы, 404 и другие отрицательные ответы,
поиск, произвольные фильтры и неизвестные query-параметры. Для sitemap, robots, редиректов,
рекламных query-параметров и динамических runtime-блоков нужны явные правила G5.

Не использовать FORCE_CACHE_ALL как способ обойти private/no-store или несовместимость Next.js.
Публичный и браузерный сроки задаются раздельно, с проверкой фактических заголовков.
См. [Cloud CDN caching](https://docs.cloud.google.com/cdn/docs/caching).

**Отдельное действующее обязательство карты сохраняется:** конфигурация заглушек и маячков
обновляется до 60 секунд, включая потерю уведомления, без перепубликации страниц и запуска Google.
30-дневный HTML не должен замораживать её. G6 должен определить отдельный путь актуализации
конфигурации, не превращая опубликованный список офисов в live-ERP-данные. Без такого решения
длительный кэш страниц карты не включать. Это исключение не отменяет длительный кэш остальных страниц.

## 4. Какие события запускают сброс

| Событие | Затронутые объекты |
| --- | --- |
| Активация публикации | Ответ страницы, HTML/RSC и фактически изменившиеся зависимые списки, карточки, sitemap |
| Откат | Те же объекты, но для заново активированного публичного состояния |
| Снятие с публикации | Доступность адресов, HTML/RSC, ссылки в меню, списках, sitemap и языковых связях |
| Изменение пути или редиректа | Старые и новые адреса, алиасы и изменившиеся зависимости |
| Вступление изменения layout в силу | Ответ layout и все использующие изменённые данные страницы |
| Активация снимка штатной refresh-очередью | Соответствующая страница и изменившиеся публичные зависимости |
| Выкладка новой версии site-front | Зависящие от сборки HTML/RSC; не массовый purge версионированных файлов |

Для данных внутри снимка сначала дождаться штатного обновления опубликованного снимка,
затем сбрасывать кэш. Для отдельного layout использовать его публичную версию. Map-only Save
сохраняет собственный контракт и не ставит все страницы в общую очередь обновления.

Сохранение черновика, подготовка перевода, проверка диагностики и семантический no-op не
запускают purge. Обычная правка статьи не очищает весь сайт. Другие языки затрагиваются только
при изменении их результата или связей. Прямые и транзитивные зависимости вычисляются на бэке,
а не угадываются site-front по URL.

## 5. Порядок доставки

1. CMS активирует публичное состояние и надёжно фиксирует обязательство доставки без окна
   между commit публикации и сохранением задания. Использовать существующий durable-механизм,
   а не параллельную независимую очередь.
2. После commit запускается оперативная попытка доставки. Пятиминутный резервный обход не
   является единственным источником запуска, если требуется штатная доставка до 30 секунд.
3. Обработчик определяет текущее публичное состояние и полный набор адресов/зависимостей.
4. Инвалидирует соответствующие данные штатного кэша единственного экземпляра Next.js. Подтверждённая инвалидация
   не должна разрешать первому посетителю получить старую версию через stale-while-revalidate.
5. Контрольный запрос к Next.js в обход CDN подтверждает нужную страницу, отсутствие страницы
   или редирект. Проверяется также версия layout и сборки, а не только текст статьи.
6. Затем выполняется адресный purge CDN для всех кэшируемых вариантов. Ждём завершения
   операции провайдера, а не только принятия запроса.
7. Выполняется проверка обычного публичного URL через CDN, без cache-busting-параметров.
8. Снова проверяется актуальность цели; только после подтверждённых обязательных этапов
   операция доставки завершается.

Сначала подготовить origin, затем чистить CDN: иначе он повторно наполнится старым результатом.
См. [Cloud CDN invalidation](https://docs.cloud.google.com/cdn/docs/cache-invalidation-overview).

Публикация и доставка имеют разные результаты. Сбой кэша не откатывает публикацию автоматически.
Повтор доставки не создаёт снимок и не вызывает публикацию статьи повторно.

### 5.1. Конкурентность и безопасность

- Ориентир: действующая активация, а не максимальный номер снимка. Это необходимо для rollback.
- Запоздалое задание не восстанавливает старую версию. При изменении цели во время доставки
  обработка продолжается для актуального состояния; ранее затронутые адреса не теряются.
- Повторы идемпотентны по логической операции и текущей цели. Одного ID операции недостаточно,
  если за время повтора изменились версия или маршрут.
- Ответ, начатый до публикации и завершённый после инвалидации, не должен снова заполнить
  Next/CDN старым содержимым. G3 должен доказать защиту и от поздней записи, и от поздней выдачи.
- Учитывать перезапуск worker, потерю lease, дубликаты и неопределённый исход timeout.
- Receivers защищены service-to-service-аутентификацией; разрешены только известные среды,
  адреса, операции и версии. Не принимать HTML от вызывающего и произвольные URL для прогрева.
- Браузерный пользователь не может произвольно запускать purge, прогрев или аварийный обход.

В коде бэка уже есть `cms-cache-delivery-v1`, проверка текущей цели, последовательность origin/CDN
и отдельные режимы неприменимости слоя. Переиспользовать и расширять этот механизм после аудита
покрытия. Старый site-front `/api/revalidate` нельзя считать готовым совместимым receiver.
Отдельный протокол обновления карты также не подменяется общим протоколом молча.

## 6. Отказы и повторные попытки

| Условие | Действие |
| --- | --- |
| Временная ошибка | Повторы через 5, 15, 30, 60 секунд после завершения предыдущей попытки, затем каждые 5 минут |
| Доставка дольше 30 секунд от активации | Зафиксировать превышение штатного SLO |
| Доставка дольше 2 минут от активации | Статус внимания и оценка точечного аварийного обхода |
| Ошибка доступа/конфигурации | Внимание немедленно; не продолжать бесполезную серию быстрых повторов |
| Перезапуск или потерянный ответ | Продолжить сохранённую операцию с проверкой текущего состояния |

После перехода в статус внимания задание не исчезает. Для временных сбоев повторы продолжаются
до восстановления или явного действия администратора. Успешные этапы учитываются, но после
смены цели нельзя слепо использовать старые подтверждения. Ограничить параллельность и
провайдерные запросы; разрешён ограниченный jitter без подмены порогов 30 секунд и 2 минуты.

### 6.1. Точечный обход

После двух минут неудачной доставки автоматически включить временный обход CDN для затронутых
адресов, **если Next.js подтверждённо отдаёт актуальное состояние и нагрузка входит в испытанный
безопасный предел**. Обход касается чтения существующих копий и заполнения новых, включая RSC.
Остальной сайт и версионированные файлы продолжают использовать CDN.

Один origin-заголовок no-store не устраняет старый CDN HIT. Правило должно срабатывать до
выдачи уже сохранённой копии. Конкретная поддерживаемая топология обхода и её задержка должны
быть доказаны в G4 до включения длительного кэша; это не утверждение о наличии готовой функции.

При обычной правке текста и неисправном Next.js автоматически переводить посетителей на
неработающий origin нельзя. Допускается предыдущая публичная версия с видимым статусом сбоя.
Это не разрешение использовать черновики или увеличивать срок уже просроченного кэша без политики.

### 6.2. Массовый обход

Штатный сброс после изменения общего layout выполняется автоматически. **Массовый аварийный
обход** всего сайта или значимой нагрузки требует решения администратора и проверки ресурсов.
Не путать эти две операции. Порог определяется нагрузкой, а не произвольным числом URL.

Доступные CSS/JS/изображения/PDF не переводить на origin вместе с HTML. Возврат к кэшу:
актуальный origin -> завершённый purge -> снятие обхода -> проверка CDN. При провале проверки
не закрывать задачу и не скрывать оставшийся обход.

### 6.3. Снятие с публикации

Для снятия действует срочный режим: обновление доступности в Next.js и purge запускаются
немедленно. При неудаче очистки сразу предпринимается запрет выдачи старой копии, без ожидания
двух минут. Приоритет: не показывать снятое содержимое, даже ценой временной ошибки.

Запрет действует перед выдачей CDN, на нужных адресах/алиасах и вариантах HTML/RSC. При
подтверждённом снятии возвращается штатный ответ отсутствия страницы; техническая невозможность
проверки не маскируется под окончательное удаление. Уже открытые вкладки и ранее скачанные файлы
не могут быть отозваны таким запретом. Снятие страницы не означает удаление всех её медиа.

Повторная публикация снимает запрет только после активации, подтверждения Next.js и очистки
старых копий. Запоздалое задание не может снять запрет для более нового состояния снятия.

Если недоступно управление CDN и механизм запрета, мгновенное прекращение выдачи гарантировать
нельзя. Фиксируется авария и неподтверждённая доставка снятия; успешным снятием с публичной
выдачи это не объявляется. Общий TTL 30 дней делает этот остаточный риск существенным.

## 7. Проверки и отображение в CMS

Использовать существующие операции публикации и раздел обновления страниц. Не создавать
параллельный пользовательский журнал. Права чтения, повтора и аварийных действий проверяет бэк.

Состояние публикации показывается отдельно от состояния доставки:

| Состояние доставки | Смысл |
| --- | --- |
| Обновление завершено | Обязательные этапы подтверждены, контрольная проверка пройдена |
| Ожидается повтор | Публичный источник изменён, доставка ещё не завершена |
| Требуется внимание | Устойчивый сбой, указаны стадия и причина |
| Временный обход кэша | Адрес обслуживается без CDN-кэша до восстановления |
| Проверка недоступна | Результат не подтверждён; отсутствие диагностики не равно успеху |

Показывать целевую публичную версию страницы/layout/сборки, затронутый охват, начало операции,
результаты этапов, последнюю ошибку, число попыток и время следующей попытки. Кнопка повтора
повторяет только доставку. Отдельно учитывать результат запрета снятой страницы и наличие bypass.
Точные поля DTO и локализованные подписи согласовать в B4; названия выше описывают семантику.

Приёмочная проверка начинается с **реально заполненного** кэша старой версии. После изменения
проверяется origin, затем тот же обычный URL через CDN без случайного query или принудительного
no-cache. Подтверждается новый ответ и его последующая выдача из кэша. HIT измерять на стороне
провайдера, а не доверять заголовку, однажды записанному origin внутрь кэшированного ответа.
См. [Cloud CDN logs](https://docs.cloud.google.com/cdn/docs/logging).

Проверка одного узла не доказывает синхронное обновление всего мира. Сохраняются подтверждение
провайдера и результаты ограниченных контрольных запросов. Массовый прогрев не нужен для
завершения каждой операции; объём проверки общей зависимости задаётся в G3/G4.

Метрики: CDN HIT без origin revalidation, обращения к Next.js и CMS, время ответа, задержка
доставки, возраст и число незавершённых операций, объём обхода, ошибки и стоимость. Логи не
содержат секретов, preview-токенов, произвольного query, резюме или персональных данных заявок.

## 8. Работа до публичного запуска

| Контур | Режим |
| --- | --- |
| Обычный develop | Новый межзапросный кэш данных/страниц выключен; CDN не обслуживает обычный трафик |
| Закрытый release | Код подготовлен, обычные запросы обходят новый кэш |
| Изолированный тест | Реальные cache fill/HIT/purge и управляемые отказы на разрешённых тестовых данных |

В обеих ветках одинаковая реализация, разные конфигурации. Выключенное состояние запрещает
использование уже сохранённых записей и не включает новые записи молча. Неприменимый слой
отмечается как неприменимый, а не как успешно проверенный purge. Точные переключатели ещё не
утверждены; не вводить в runtime придуманные имена env из этого описания.

Тестовое хранилище/ключи отделены от публичного. Проверять контроль доступа **до cache hit**.
Не открывать закрытый сайт и не считать секретный URL или noindex защитой. На одном backend
service балансировщика IAP несовместим с Cloud CDN; топология изолированного теста выбирается
отдельно. См. [ограничение IAP/CDN](https://docs.cloud.google.com/load-balancing/docs/backend-service#cloud_cdn).

Нельзя менять реальные статьи ради проверки, запускать Google-карту, отправлять заявки,
создавать расходы или менять инфраструктуру без соответствующего разрешения. Подготовка кода
и документации не является таким разрешением. До go-live пройти нагрузочный тест обхода и
проверить rollback. Если readiness не пройдена, сайт может запуститься без нового кэша.

## 9. Публичный запуск и включение

Публичный доступ, индексация и кэш являются отдельными управляемыми действиями. Выполнять
после явного разрешения; этот документ их не запускает.

1. Подтвердить готовность релиза: окончательный основной домен, доступ, canonical, hreflang,
   robots, sitemap, старые редиректы и отсутствие утечек. CMS и административный API закрыты.
2. Проверить окончательный публичный адрес без нового кэша. При изменении политики индексации
   не оставлять старые robots/noindex-ответы в промежуточных кэшах.
3. До первого cache fill включить надёжную регистрацию и оперативную доставку новых событий
   сброса. Не допустить окна, в котором кэш уже работает, а изменения ещё не отслеживаются.
4. Начать с чистого публичного состояния кэша. Не переносить тестовые, закрытые, preview или
   несовместимые с новой сборкой ответы. Проверить события, пришедшие во время переключения.
5. Включить CDN для проверенных версионированных файлов.
6. Включить штатный серверный кэш готовых публичных ответов CMS в одном экземпляре Next.js по решению G1.
7. Включить длительный HTML и проверенные RSC-варианты для небольшой явной группы адресов,
   включающей разные типы страниц и языки. Пилот использует целевую длительную политику,
   а не заменяет её минутным TTL. Непроверенные варианты продолжают обходить CDN.
8. Подтвердить HIT, актуальность, работу доставки и отсутствие ошибок, затем расширить охват.
9. Ограниченно прогреть главную и ключевые страницы языков. Остальные наполняются по обращениям;
   не выполнять бесконтрольный обход всего сайта.
10. Сопоставить нагрузку, задержки, ошибки и затраты с исходными замерами; проверить журнал.

Включение кэша не требует массовой перепубликации. Паузами очереди и публикациями не управлять
самовольно. Снятые страницы и ограничения доступа должны сохраняться при переключении режимов.

При проблеме остановить расширение охвата, отключить проблемный слой/включить разрешённый
обход и доказать прекращение выдачи старых записей. Не откатывать контент автоматически.
Отключение кэша само по себе не закрывает публичный сайт и не меняет индексацию.

## 11. Порядок работ и общая приёмка

1. Закрыть G1-G6 и согласовать B1 с фронтом и инфраструктурой. Сначала доказать совместимость,
   а не создавать ресурсы в расчёте на неподтверждённые возможности провайдера.
2. Реализовать B2-B5, S1-S5, подготовить I1-I3 и C1 с обычными режимами off.
3. После отдельного разрешения подготовить изолированный тест. Выполнить B6, S6, I4.
4. Принять журнал, метрики, лимиты нагрузки и I5. Отдельно разрешить выкладку подготовленного кода.
5. Отдельным решением владельца пройти публичный запуск и включение по разделу 9.

| Проверка | Ожидаемый результат |
| --- | --- |
| Повторные открытия неизменившейся страницы | Доказанные CDN HIT без вызова Next.js; кэш Next снижает CMS-чтения при origin miss |
| Срок данных Next.js | 30 дней (2592000 секунд); управляемое время подтверждает HIT до границы и актуальное чтение CMS после неё, без бесконечного продления по HIT или старого refill CDN |
| Изменение опубликованного материала | Новый ответ обычного URL после доставки; целевой штатный срок до 30 секунд измерен |
| Изменение layout | Актуальный layout во всех затронутых вариантах; нет ложного успеха по одному snapshotId |
| Черновик/no-op/диагностика | Публичный кэш и публикации не меняются без изменения публичного результата |
| Источник внутри снимка и paused refresh | Никакого обхода пауз или выпуска чужих черновиков |
| Две публикации, rollback, поздний ответ | Нельзя вернуть старое состояние или потерять старый адрес для очистки |
| Restart/timeout/дубликат | Задание сохранено, повтор безопасен, снимок не создаётся повторно |
| Ошибка purge | Видимый сбой, повторы, обход только при выполненных условиях, нет общего успеха |
| Массовый обход | Требует административного решения; предел нагрузки подтверждён тестом |
| Снятие и повторная публикация | Срочный запрет старой выдачи, сохранение при сбоях/переключении режима, безопасное снятие запрета |
| HTML/RSC/языки/размеры изображений | Нет смешивания ответов, рабочая навигация и адаптивное отображение |
| Preview/сессии/персональные файлы | Нет попадания в общий кэш или выдачи чужому пользователю |
| Map-only Save с потерей уведомления | Настройки актуальны до 60 секунд, без Google и перепубликации |
| Старый build/открытая вкладка | Файлы доступны, нет несовместимого RSC, проверено поведение смены сборки |
| Off и аварийное отключение | Ранее заполненный кэш не выдаётся; ограничения снятых страниц не теряются |

Все разрушающие сценарии выполняются на изолированных данных. Не использовать реальные
публикации release, заявки или платные API как тестовые фикстуры без отдельного разрешения.

## 12. Технические решения до включения

Это не новые молча согласованные настройки, а обязательные результаты проектирования.

## 15. Уточнение штатного кэша Next.js

Решение владельца от 17.11.2026: один обслуживающий экземпляр Next.js, штатный локальный серверный
кэш без Redis, срок полных публичных ответов страницы и стабильного layout — 30 дней
(2592000 секунд), с досрочным событийным сбросом и исключениями раздела 3.1.

Контракт Юрию, readiness-аудит и инфраструктурная документация обновлены в `cms-back` коммитом

G1 требует доказать соблюдение принятого срока, OFF, истечение, перезапуск и инвалидацию,
а не повторно выбирать TTL. Приёмка использует управляемое время, без ожидания 30 реальных дней.
Это только изменение документации: кэш не включён, код фронта и настройки сред не менялись,
deploy и публикации не выполнялись. Остальные G1-G6 и отдельное разрешение активации сохраняются.
