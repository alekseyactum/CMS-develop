# CMS backend для снятия и восстановления публикаций

Дата: 12.11.2026. Исполнитель: наша backend-часть в `re-actum/cms-back`.
Статус: задача к реализации, не сообщение о готовом API или выкладке.

Нормативные правила и общая приёмка:
[согласованное ТЗ](editorial-unpublish-restore-specification-2026-11-12.md).
[Задача Юрию](cms-front-editorial-unpublish-restore-task-2026-11-12.md) зависит от этого контракта.

## 1. Домен и хранение

- Ввести контролируемое снятие/восстановление одной языковой группы `blog_page`, `media_page`
  или `case_page`. Не распространять на коллекции и остальные типы страниц.
- Снятие сохраняет точный публичный набор по каждому опубликованному языку: идентичности страниц,
  неизменяемых снимков, опубликованного SEO и адресов. Это набор одного цикла, не ссылки на latest draft.
- Хранить групповую блокировку и поколение перехода независимо от per-page `publishState`.
  Только отсутствие `current_snapshot_id` не защищает от повторной активации.
- Неопубликованные/новые локали остаются неопубликованными, но не могут обойти блокировку группы.
- Запись перехода, изменения публичных указателей/проекций и durable-обязательства обновления
  фиксировать атомарно с согласованным порядком блокировок и существующими writer fences.
- Предусмотреть повторные циклы и корректное сохранение исходной даты первой публикации.
  Не менять авторинг, головы/номера версий, права ERP, `editorialStartedAt` и необратимые ERP-маркеры.
- Если нужна миграция, она не снимает существующие материалы и не угадывает восстановимые наборы
  для legacy-состояний. Нет достоверного набора — восстановление явно недоступно, без fallback.

## 2. Авторизация и запрет обходов

Снимать, восстанавливать и повторять техническое обновление может только активный `admin`.
Проверять это при подготовке и исполнении, не доверять роли/actor из тела запроса или фронта.
Обычный `publication_editor`, SEO-редактор или пользователь с общим Publish не получает эти действия.

Общая блокировка должна соблюдаться существующими content/SEO commit, rollback, batch/legacy путями,
translation/bootstrap/import writers и всеми refresh/rebuild workers. Администратор тоже не обходит
снятие обычным Publish: только специальное восстановление точного набора. После возврата действуют
прежние обычные права. Новый перевод не открывает группу и не добавляется в набор восстановления.

Старые планы должны протухать при смене поколения даже при возвращении того же snapshot ID.
Проверить реальную конкуренцию публикации, Save, создания локали, снятия/возврата и worker.
Save может продолжать работу в рамках существующих прав, но не является активацией.

## 3. Контракт для фронта

Подготовить и опубликовать фактический API/OpenAPI и контрактные тесты до подключения Юрия.
Названия новых маршрутов и DTO фиксируются в service-репозитории при реализации, не выдаются
за уже существующие эндпоинты этим ТЗ. Обязательная семантика:

1. Чтение состояния группы: идентичность/поколение, локальные статусы, групповая блокировка,
   серверная доступность снять/восстановить, причины отказа и текущее состояние обновления сайта.
2. Подготовка каждого действия: название, точный набор языков и URL, привязанный к состоянию
   серверный токен подтверждения. Подготовка не меняет публичное состояние.
3. Подтверждение с request ID и токеном: повторная проверка администратора, ревизии, состава группы,
   точного набора снимков и обязательных технических ограничений. Не принимать произвольные
   клиентские списки локалей/снимков как доверенный восстанавливаемый набор.
4. Чтение результата по request/operation ID после timeout; устойчивый receipt и идемпотентный повтор.
   Смена содержимого запроса при том же ID отклоняется. Не создавать новый цикл при повторном снятии.
5. Повтор только незавершённых целевых работ по обновлению сайта. Он не повторяет доменный переход,
   не публикует черновики и не запускает всю очередь.
6. В списке/detail/row/editor, где нужны действия, отдавать серверные lifecycle capabilities и состояние,
   не выводить их из legacy `canPublish`. Согласовать с `publicationAvailability`: обычная подготовка
   content/SEO во время снятия заблокирована по явной причине, редакторский Save не запрещается этим фактом.

Не менять смысл `not_published` и локального `withdrawn`: история публикации относится к точному
page ID. Групповое состояние передавать отдельно. Сервер считает фильтр и total до пагинации.
Не вводить N+1 запросы `/state` на каждую строку списка только ради действий снятия/восстановления.

Различать 403, типизированный 409 с необходимостью нового подтверждения, техническую недоступность,
принятую операцию с незавершёнными эффектами и неизвестный клиенту результат. Не терять код/статус
при сериализации ошибки. Безопасные структурированные причины — да; SQL, stack и токены — нет.

## 4. Публичная доступность и зависимости

- На снятой группе detail API и публичный маршрут недоступны без авторизованного preview.
  URL даёт 404 без другого языка/черновика/исторического снимка как fallback.
- Исключить материалы из действующих публичных проекций, коллекций/поиска, рекомендаций, подборок
  адвокатов и тематик, XML/HTML sitemap и hreflang. Не создавать новый поисковый функционал.
- Сохранять реестр адресов и intent-enabled состояние входящих редиректов. Недоступная цель — 404,
  восстановление возвращает исполнимость только ранее включённых правил. Не генерировать новые 301/410.
- Обновлять потребителей сразу, без стандартного отложенного due time и независимо от их паузы.
  Не менять pause-флаги, другие ожидающие причины, авторинг и неопубликованные страницы.
- В ручных подборках сохранять опубликованную привязку; удалять/возвращать только публичную карточку.
  В автоматических — необходимое восполнение по прежним правилам из опубликованных кандидатов.
- Для редактора ручного подбора сохранять выбранную ссылку в ответе с признаком недоступности
  из-за снятия, даже если её нет в публичных items. Сохранение формы не должно молча терять ссылку.
- Не пересобирать потребителя из working content или текущих неопубликованных composition.
  Изменять только целевую доступность, необходимое восполнение/лимит и связанные публичные проекции.
- Для восстановления обнаруживать и потребителей без видимой карточки. Не терять provenance
  после удаления карточки и не признавать список текущих items полным списком подписчиков.
- Отказ очистки/потребителя после commit не откатывает снятие/возврат. Состояние операции остаётся
  незавершённым; повтор ограничен её обязательствами и проверяет новое поколение группы.

## 5. Кэши, аудит и интеграция

Оркестрация и учёт работ по origin/Next.js/CDN принадлежат backend; поддерживаемый механизм
site-front согласовать с Юрием. Инвалидировать затронутые URL, входящие адреса, потребителей,
пагинацию/sitemap и отрицательные 404 после восстановления. Учесть реально включённые слои,
не создавать CDN или другие ресурсы в рамках прикладной задачи без отдельного решения.

Факт перехода и полная готовность сайта — разные состояния. Не сообщать полный успех до обязательных
эффектов и не маскировать отказ конфигурацией «кэша нет». Непредусмотренная недоступность слоя — ошибка,
действительно отсутствующий слой — не требуется. Повтор не должен применять устаревший результат
после противоположной операции; старый план и старое задание не являются правом на активацию.

Служебный аудит хранит доверенного администратора, время, действие, группу, языки/снимки, необязательную
причину и результаты. Отдельный UI истории не создавать; для фронта нужен только текущий результат,
без выгрузки секретов, контента или внутренних исключений.

## 6. Проверка и передача

- Выполнить общие AC-1–AC-20; покрыть policy, API и границы транзакций тестами.
- Для блокировок/атомарности дополнить doubles проверками конкурентных транзакций на изолированной
  MySQL-базе. Не считать unit-тесты доказательством поведения реальных блокировок.
- Проверить сохранность авторинга/версий, отсутствие ложной даты первой публикации и новых ERP-прав.
- Провести сценарии старого токена, потери ответа, повторного цикла, технического конфликта одной
  локали, сбоя эффекта и повторной обработки на уже изменённой группе.
- Передать Юрию точные маршруты, DTO, capabilities, коды ошибок, контракт статуса/повтора и механизм
  обновления site-front. Не поручать фронту самостоятельный пересчёт группы, фильтра или зависимостей.
- При последующем согласованном rollout применить нужные миграции в безопасном порядке; приёмку
  выполнять на специально согласованных материалах, не снимая произвольные рабочие публикации.

Эта задача и её push не выполняют миграции, деплой или изменения контента. Код фронта и ERP не входит
в нашу реализацию; фронтовые изменения выполняет Юрий по отдельному заданию.
