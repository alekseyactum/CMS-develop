# Кар’єра: согласованный backend-контракт

Уточнение от 2026-09-19: вакансии полностью read-only в CMS и имеют один украинский текст для всех
языковых версий страницы. Импорт и публикация разделены. Это решение заменяет первоначальные правила
редактирования RU/EN-переводов и автоматической перепубликации при импорте/сохранении.

## Границы

Одна обычная CMS-страница `career_page`, `/career`, `/ru/career`, `/en/career`, без региональных вариантов.
Вакансии — ERP-справочник, не страницы и не отдельные публикации. Кнопка карточки открывает модальную
форму отклика. Отдельных URL вакансий и `JobPosting` в этой версии нет.

Общий header/footer остаётся существующим. Секции страницы:

- `seo`;
- `career_header`: H1;
- `career_partner_banner`: изображение, alt, заголовок, вводный текст, подпись кнопки и ID страницы
  лицензионного партнёрства. Backend разрешает ссылку только на опубликованную страницу того же языка;
- `career_vacancies_intro`: заголовок, вводный текст, сообщение об отсутствии вакансий;
- `career_vacancies`: runtime-список из ERP, связанный с секцией intro;
- `career_application`: тексты инициативного отклика и формы;
- `career_application_capture`: runtime-контекст формы.

Нулевая выборка вакансий допустима. Показываем сообщение об отсутствии вакансий, баннер и инициативную
форму. Переключатели видимости секций продолжают работать по общим правилам CMS.

## Вакансии

ERP владеет `externalId`, украинскими `title`/`description`, `showOnSite`, `sortOrder`, датой создания
в ERP и одним значением `workLocation`. Это не несколько независимо выбранных локаций:

- `{kind: "office", cityName: {uk: "Київ", ru: "Киев", en: "Kyiv"}}`;
- `{kind: "remote", cityName: null}`;
- `{kind: "hybrid", cityName: {uk: "Київ"}}` → «Гібрид — Київ».

Название, описание и отображаемая локация вакансии всегда украинские, в том числе на `/ru/career`
и `/en/career`. Для города используется `cityName.uk`; дополнительные ERP-названия городов могут
храниться, но не используются для отображаемой подписи. Описания являются plain text: frontend не
должен вставлять их как HTML. Runtime каждой вакансии содержит `contentLocale: "uk"`.

Все поля вакансии принадлежат ERP: в CMS нельзя менять тексты, видимость, порядок или локацию.
Старый API сохранения переводов возвращает `403 CAREER_VACANCY_READ_ONLY` без записи данных.
Исторические RU/EN-переводы не удаляем, но больше не читаем для списка, диагностики, runtime и откликов.
Нет ручной публикации каждой вакансии или расписания закрытия. Редактор может вручную создавать новые
версии секций/страницы и публиковать страницу; это не даёт права редактировать поля вакансии.
SEO, заголовки, баннер, вводные тексты и тексты формы остаются локализованными CMS-полями.
Переданный клиентом runtime-список вакансий игнорируется при preview/публикации: активная секция
собирается из ERP, скрытая остаётся скрытой. Это исключает обход read-only через общий API публикации.

Порядок: `sortOrder` по возрастанию; `null` в конце; затем дата создания в ERP по убыванию; затем
стабильный ID. Изменения технической даты импорта не меняют порядок.

Вакансия доступна для включения в любую локаль, если ERP включил `showOnSite` и есть украинские
название и описание. Отсутствие/устаревание RU/EN не является ошибкой или предупреждением. Отсутствие
обязательного украинского текста диагностируется один раз как проблема ERP-источника.
Фактический публичный список определяется последним опубликованным snapshot соответствующей страницы.

Импорт пакетный, максимум 100 записей. Одна запись — полное состояние, отсутствие записи в пакете
не означает удаление. Повтор неизменившегося пакета не создаёт новые публичные версии. Для защиты
от запоздавших пакетов мигратор передаёт `sourceUpdatedAt` с часовым поясом.

## Приём данных и явная публикация

Импорт обновляет ERP-справочник, но сам не создаёт публичные snapshots, не перепубликует страницу и
не запускает повтор ранее неудачного обновления. Автоматические события/команды и политику повторов
со стороны ERP согласуем отдельно; ни CMS-сохранения, ни фоновый таймер их не заменяют.

Ручная публикация и явная пересборка страницы используют актуальные ERP-данные при сборке runtime
выбранной локали. Они не запускают дополнительное обновление остальных локалей. Rollback восстанавливает
именно исторический snapshot, включая исторический список вакансий; для актуального списка после
rollback нужна явная пересборка/публикация. Закрытая вакансия не принимает отклики даже при старом списке.

Сохраняем существующий технический механизм явного обновления опубликованного списка:
`POST /api/internal/erp/career/vacancies/refresh-published`. Он не вызывается импортом или CMS автоматически.
При изменении ERP-источника намерение обновить локали записывается атомарно; `refresh-state` сохраняет
счётчики и прежние ошибки. `automaticRefreshEnabled: false` означает отсутствие автоматического запуска;
`pending` означает ожидание отдельной команды, а не работающую фоновую задачу. Эти счётчики нельзя
использовать как общий индикатор актуальности страницы после ручной публикации.

Явная команда берёт за основу текущий публичный snapshot, а не черновики. Она заменяет только список
вакансий, сохраняя SEO, баннер, прочие секции, видимость и JSON-LD. Ссылки на версии копируются с новыми
ID связей snapshot, а не со старыми первичными ключами. Конкурентная публикация проверяется при записи;
при конфликте выполняется повтор на новой базе. Неопубликованная страница не публикуется, отключённый
блок не включается. Ошибка не теряет ERP-данные и остаётся видимой до успешной явной команды.

Уже опубликованные snapshots, старые переводы и принятые отклики автоматически не переписываются.
После выката украинский текст появится на ранее опубликованных RU/EN-страницах только после явной
публикации/пересборки. Изменение контракта не требует новой миграции БД.

## Отклики

Есть два случая: отклик на конкретную вакансию и инициативный отклик без `vacancyId`. Обязательны имя,
телефон и email; «о себе» и резюме необязательны. Разрешён один PDF/DOCX до 10 MiB. Файл не попадает
в публичную медиатеку CMS; хранение приватное, выдача только с авторизацией и как attachment.

Перед сохранением повторно проверяются наличие вакансии в опубликованном списке выбранной локали и
актуальные ERP-видимость/украинские тексты. RU/EN-переводы не требуются. Язык страницы, формы и заявки
остаётся выбранным пользователем; данные вакансии в новой заявке украинские. Закрытая вакансия возвращает
ошибку, не превращается автоматически в инициативный отклик. Для повторного запроса frontend сохраняет
один `Idempotency-Key` до подтверждения принятия заявки.

Заявка сначала надёжно сохраняется вместе с независимыми заданиями доставки в HR-email и ERP.
`accepted` означает сохранение, а не подтверждение доставки обоими получателями. Предусмотрены
ограничение частоты, первый запрос доставки и защищённый повтор очереди. Недоступный или ещё не
настроенный канал не помечается доставленным.

Один HR-email на все вакансии, инициативные отклики и языки задаётся в глобальной секции CMS
«Форма заявки на вакансію» (`global_career_form`, поле `hrEmail`). Секция shared: одна запись `uk`,
редактор любого языка работает с ней же. Сохранение черновика не меняет получателя: адрес вступает
в действие после публикации глобальной секции, без перепубликации страницы карьеры. Приём заявки
читает текущую опубликованную версию и фиксирует адрес внутри транзакции; последующие повторы доставки
используют адрес, сохранённый в заявке. Без корректного опубликованного адреса новая заявка не принимается.

HR-email — внутреннее CMS-поле: его нет в публичных snapshots, runtime формы или публичном представлении
глобальной секции. Отдельной таблицы/редактора настройки получателя и fallback на env нет. Локализованные
тексты формы остаются в секции страницы `career_application`. SMTP, токены
межсервисного доступа и адрес будущего ERP-приёмника — runtime configuration/secrets, не поля страницы
и не публичный JSON. ERP-приёмник предстоит реализовать отдельно. Для ERP обязательна дедупликация
по ID заявки; SMTP не обеспечивает строгую exactly-once доставку при разрыве после принятия письма.

## Выкат и проверка

Первоначальная backend-реализация выполнена в `codex/career-backend` репозитория `cms-back`;
уточнение 2026-09-19 реализуется в `codex/career-uk-readonly`. Изменения frontend — отдельная задача Юрия.
Это не разрешение применить миграции или изменить облако. Перед реальным включением нужны явные
миграции, приватное хранилище резюме, HR-email, SMTP и серверные секреты. ERP-доставка активируется
после готовности ERP-приёмника. Отдельные задания CMS/site frontend и ERP составляются после backend.

Приёмочные сценарии: bootstrap/редактор/preview/publish трёх локалей; одинаковые украинские вакансии
и локализованные тексты формы; пустая выборка; порядок; импорт и повтор пакета без публикации;
запрет CMS-записи во всех локалях; отсутствие диагностик переводов; ручная публикация актуального списка;
сохранность черновиков и новые ID ссылок при явном обновлении; конкурентная публикация;
исторический rollback без скрытого обновления; закрытие вакансии между открытием модалки и отправкой;
отклик с файлом и без; повтор ключа запроса; отказ одного канала и его повтор без повторной отправки
успешного канала.
