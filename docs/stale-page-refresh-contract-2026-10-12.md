# Обновление устаревших опубликованных страниц

Дата решения: 12 октября 2026 года. Статус: согласованное ТЗ, реализация нового общего механизма
не завершена. Этот документ не разрешает миграции, деплой, переключение режима публикации,
включение расписаний или изменение контента.

CMS должна самостоятельно обновлять устаревшие части уже опубликованных страниц, не публикуя
редакторские заготовки. Все такие обновления управляются через один раздел CMS. Очередь хранится
на бэке, шедулер ERP вызывает её обработку раз в пять минут, а публикация и доставка изменений
через кэши учитываются как отдельные этапы одной операции.

## Область действия и приоритет требований

Это ТЗ заменяет прежние ограничения «только ручная перепубликация после изменения источника»,
«только зависимости от уже включённых объектов» и отсрочку общей runtime freshness до отдельного
неопределённого этапа в следующих документах:

- [Модель справочников и runtime](reference-data-and-runtime-model.md), раздел Snapshot And Stale Policy.
- [Требования к бэку](backend-implementation-requirements.md), Post-release runtime freshness decision.
- [Требования к JSON-LD](json-ld-implementation-requirements-2026-08-03.md), Stale Dependency Contract:
  правило существенного изменения сохраняется, запрет обычной автоматической перепубликации заменяется
  ограниченной автоматикой по этому ТЗ.

Сохраняются [контракт версий секций](section-authoring-versioning-contract-2026-10-04.md), правила
локалей, eligibility, владения ERP/CMS, разрешений, маршрутов и валидации конкретных страниц.
Новый механизм не делает черновики автоматически одобренными и не меняет импорт данных из ERP.

Шедулер и границы будущей инфраструктурной интеграции согласованы в управляющем playbook:
[CMS stale refresh scheduling decision](../../gcp-infra-playbook/docs/projects/cms-stale-refresh-scheduling-decision-2026-10-12.md).
Исторические записи о развёртывании не являются доказательством готовности новой функции.

## Три независимых состояния

| Состояние | Значение | Действие |
| --- | --- | --- |
| Неопубликованная работа редактора | Рабочая форма или сохранённая версия отличается от опубликованной | Обычный редакторский процесс; автоматика её не активирует |
| Требуется проверка наследования секции | Изменился источник рабочей секции, требуется принять или отклонить его влияние | Существующий процесс проверки секции, отдельно от публичного снимка |
| Устарела опубликованная страница | Одобренное изменение источника меняет фактически публичный результат | Безопасное обновление через общую очередь |

Эти состояния могут существовать одновременно. Обновлённая публичная страница не означает, что
редактор проверил её рабочие секции. Наличие рабочей версии само по себе не блокирует безопасное
обновление опубликованного результата. Runtime-блок не получает фиктивные версии и черновики.

Очередь не должна определять эти факты по одному сводному `publishState`, ST или цвету индикатора.
Старые ответы API сохраняют совместимость; новый контракт возвращает независимые состояния.

## Что разрешено обновлять

Механизм действует только на страницы, которые сейчас опубликованы. Он не создаёт первую публикацию,
не возвращает снятые страницы на сайт и не изменяет состав, порядок, включённость секций или маршруты
из неопубликованного состояния редактора.

Основой служит текущий неизменяемый опубликованный снимок. Изменяются только фрагменты, связанные
с обрабатываемыми причинами устаревания, и необходимые зависимые данные. Например, изменение отзыва
может требовать согласованного обновления списка отзывов, счётчика/рейтинга и соответствующей части
JSON-LD, если эти данные предусмотрены схемой страницы.

Результат — новый полный согласованный снимок страницы, а не редактирование старого JSON на месте.
Не затронутые причиной опубликованные тексты, версии, настройки и структура сохраняются. Граф и
зависимости строятся для этого результата; нельзя подмешать другие свежие данные при полной
перегенерации JSON-LD. Не создаются искусственные версии секций ради обновления runtime.

Если границы безопасного обновления невозможно доказать, автоматика не переходит к обычной полной
публикации. Она сообщает конкретное препятствие:

- временный технический сбой — повторить незавершённый этап;
- некорректные данные — указать источник и необходимые исправления;
- неподдержанный формат снимка или сценарий — задача бэка, а не предложение редактору выбирать JSON-поля;
- необходимое редакторское изменение — обычная явная публикация с планом/предпросмотром и валидацией.

Безопасно независимые причины одной страницы можно обработать отдельно от заблокированных.
Если их зависимые фрагменты нельзя разделить без нарушения согласованности, соответствующее обновление
блокируется целиком. Уже опубликованный снимок сохраняется при ошибке до активации нового.

## Источники и момент одобрения

| Изменение | Когда может влиять на очередь |
| --- | --- |
| ERP-данные и связи | После успешного применения согласованного импорта в CMS |
| CMS-поля справочника без черновиков | Сохранение означает одобрение для последующего использования на опубликованных страницах |
| Версионная общая секция | Только публикация версии источника, не сохранение рабочей версии |
| Статья, дело, медиапубликация в связанных списках | Изменение опубликованной проекции, доступности или разрешённых связей, а не редакторского черновика |
| Переименование версии, служебные даты, внутренние поля | Не создают устаревание без изменения публичного результата |

Формы неверсированных CMS-полей должны объяснять, что сохранённые изменения могут автоматически
попасть на уже опубликованные страницы. Дополнительное согласование таких полей не вводится.
ERP-поля остаются readonly в CMS; частота и протокол их импорта не меняются этим ТЗ.

Изменение источника и долговечный сигнал о нём фиксируются атомарно либо через равноценный
восстанавливаемый протокол. Сигнал сохраняет сведения для поиска прежних и новых потребителей,
включая old/new связи. Само распределение по страницам может выполняться позже, ограниченными
партиями. Вызов уведомителя только после source commit без сохранённого обязательства недостаточен:
падение между этими шагами не должно навсегда потерять обновление. Это внутренняя гарантия CMS,
не новый протокол синхронизации ERP и не требование отдельного брокера сообщений.

Публикация общей секции активирует её источник, а распространение на страницы может ожидать очереди.
Статусы активации источника, его рабочих наследников и обновления публичных потребителей различаются.

## Как определяется устаревание

Причина должна отражать существенное изменение публичного результата, а не любой факт записи
источника. Проверяются содержимое, видимость, состав, порядок и связи действительно используемых
данных. Изменение, не влияющее на вывод конкретной страницы и её структурированные данные, не требует
нового снимка или очистки кэша.

Отслеживаются два вида зависимостей:

- конкретные объекты, уже использованные опубликованной страницей;
- область отбора списка, включая пустой список: новый подходящий объект, скрытие, удаление или перенос
  связи должны обнаруживаться и тогда, когда объекта не было в старом снимке.

При переносе объекта проверяются прежние и новые области отбора. Кандидат на проверку ещё не означает
доказанное устаревание: сравнение нормализованного публичного результата исключает ложные обновления.
Из сравнения исключаются технические даты, diagnostics и нестабильные варианты URL одного медиа;
публично значимые даты, порядок и сам выбор медиа сохраняют значение. Отключённые в опубликованной
структуре необязательные секции не становятся причиной обновления её видимого содержимого.

Runtime freshness не должна зависеть от того, включён ли JSON-LD для данного типа страницы.
Реестр источников/областей отбора и разрешённых обновляемых фрагментов общий для обнаружения,
подготовки, проверки результата и подтверждения обработанных причин. Нельзя объявить поддержку
произвольного runtime только потому, что существует универсальный rebuild.

## Очередь и сроки

Одна логическая запись очереди соответствует странице и локали и объединяет её актуальные причины.
Разные региональные варианты имеют разные page ID. Отдельная операция выполнения может иметь свою
историю попыток; это не дополнительные дубли страницы в списке текущей очереди.

Сохраняются первая дата обнаружения, время последнего события, источник, категория и поколение
изменения, затронутые секции, плановое время, приоритет, стадия, попытки и результат. Новое событие
не должно стирать раннюю дату ожидания или причину предыдущего сбоя.

| Правило | Значение |
| --- | --- |
| Обычная задержка по умолчанию | 30 минут от первого обнаруженного изменения |
| Настройка задержки | По категории причины, без персонального календаря каждой страницы |
| Повторные события | Не отодвигают уже назначенное время позже |
| Несколько совместимых причин | Одна сборка в наиболее ранний из назначенных сроков |
| Скрытие, удаление, отвязка показанной информации | Приоритетная обработка без обычной задержки накопления |
| Плановое время | Момент готовности к обработке, не обещание точного времени появления у посетителя |

Менее срочное разрешённое изменение может попасть в публикацию раньше вместе с более срочным:
задержка — допустимое ожидание, не запрет публиковать до определённой даты. Срочность не обходит
валидацию, общую паузу или ограничения нагрузки и не обещает мгновенное исчезновение из всех кэшей.

Категории должны различать как минимум изменения отзывов, данных адвокатов, состава связанных
дел/публикаций и опубликованных общих секций. Точный реестр кодов и таблица поддержанных потребителей
входят в backend-контракт. Изменение настроек не должно молча отодвигать уже назначенные задачи;
правило применения новой настройки к ожидающей работе должно быть явным в API и тестах.

## Обработчик и шедулер

Шедулер ERP раз в пять минут вызывает защищённую команду CMS «обработать готовую работу».
В будущем вызывающей стороной может стать отдельный Actum-сервис шедулера. Очередь, сроки,
повторы, выбор фрагментов и решения о публикации всегда принадлежат CMS.

Начальный предел — одна пересборка страницы одновременно на окружение, общий для автоматического
и ручного ускоренного обновления, включая несколько экземпляров обработчика. Длительность одного
запуска, размер партии и ограничение скорости подбираются по измерениям. Одна последовательная
пересборка сама по себе не задаёт достаточный предел запросов в секунду.

Повторные и пересекающиеся вызовы не создают дубли. Пропуск вызовов не теряет очередь; после
восстановления она разбирается в пределах нагрузки. Один вызов не обязан завершить всю очередь.
Браузер не выполняет цикл публикаций и не является условием продолжения принятой работы.

Шедулер не получает права отправлять произвольный контент, версии или страницы для активации.
Автоматические операции создаются CMS по согласованной политике обновления опубликованных данных,
с системным инициатором и указанием исходного события. Нельзя подделывать авторство редактора или
считать исходный ERP event уже принятой редакторской публикацией.

Существующие принятые immutable operations сохраняют свою семантику исполнения и аудита.
Для новых автоматических планов отдельно проверяются текущая опубликованность и допустимость scope.

## Управление и ошибки

«Обновить сейчас» убирает задержку накопления и инициирует внеплановую обработку через тот же
процессор. Если он занят, работа получает приоритет, а не неограниченный параллельный запуск.
Это безопасный stale refresh, не полная редакторская публикация и не обход backoff активного
технического сбоя. Для завершившейся ошибкой операции предназначено действие «Повторить».

Можно обновить одну страницу или явно выбранные несколько. До подтверждения показываются количество
и конкретный выбранный набор. Команда не расширяется до всех результатов фильтра или всего сайта;
кнопки «обновить всё» в первой версии нет. Каждая страница сохраняет отдельный результат.

Временные ошибки повторяются с растущей задержкой, максимум пять попыток, включая первую.
После исчерпания лимита работа остаётся в состоянии «Требуется внимание» до явного повтора.
Ошибки данных и неподдержанные сценарии сразу требуют исправления, без пяти бесполезных попыток.
Точные интервалы и учёт попыток незавершённых стадий закрепляются в backend API и тестах.

Сбой одной страницы не останавливает другие. Явный повтор продолжает только незавершённый этап;
повтор сетевого запроса с неизвестным исходом не должен заново активировать уже опубликованный снимок.

Общая пауза запрещает старт новой автоматической работы, включая срочную. Причины продолжают
накапливаться, начатая работа завершается, ручное ускорение остаётся доступным. Возобновление не
снимает ограничения нагрузки. Отдельные паузы для каждой страницы/источника не входят в первую версию.

## Публикация и кэш

Одна операция различает два результата:

1. Новый снимок успешно активирован.
2. Обязательные операции обновления кэшей успешно выполнены.

Общий успех показывается только после обоих этапов. Если снимок опубликован, а доставка не завершена,
CMS прямо сообщает: «Страница опубликована. Обновление кэшей не завершено — ожидается повторная
попытка» либо «Требуется внимание» после исчерпания попыток. Повтор кэша не создаёт ещё один снимок.

Точечное обновление кэшей запускается после каждой фактически изменившей страницу публикации:
редакторской, автоматической или ускоренной вручную. После периода накопления не добавляется
намеренное ожидание ещё одного полного TTL. Семантический no-op не создаёт новый снимок и purge;
причина закрывается как «изменений нет», а не как новая публикация.

Сначала origin должен быть способен отдавать новый результат, затем обновляются внешние кэши.
Нужно учитывать применимые слои site-front и CDN, локали, host/path и варианты ответа, а не только
один HTML URL. Next.js revalidation сама по себе не сбрасывает внешний CDN; это отдельные операции.
См. [Next.js CDN caching](https://nextjs.org/docs/app/guides/cdn-caching) и
[Cloud CDN invalidation](https://docs.cloud.google.com/cdn/docs/cache-invalidation-overview).

Успех доставки означает подтверждение обязательных операций, не гарантию одновременного обновления
всех edge-узлов и открытых браузеров. Недоступный обязательный адаптер нельзя выдавать за успешный
purge. Если определённый слой отсутствует в окружении, это явно отражается как неприменимость,
а не как имитация вызова. Конкретные адаптеры определяются по инфраструктуре при реализации.

Обычное обновление страницы не очищает весь сайт. Массовая смена схемы, маршрутов или общего layout
не должна маскироваться под обычную причину одной страницы; у неё отдельный существующий контракт.

## Один раздел CMS

В первой версии — один пункт меню и один URL для очереди, журнала, фильтров и управления.
В разделах отзывов, адвокатов и других источников встроенных очередей и кнопок управления не добавляем.
Точный путь и DTO фиксируются в контракте бэка/фронта до реализации Юрием; это не уже существующий API.

Очередь показывает страницу, публичный путь, локаль, тип, причины и источники, затронутые секции,
первое обнаружение, плановое время, стадию, попытки, ошибку и разрешённые действия. Доступны поиск
и фильтры по причине, состоянию, локали и типу страницы. Языковой охват явно виден; общий счётчик
не должен выглядеть как счётчик только выбранного языка.

Пользователь различает ожидание срока, готовность, выполнение, ожидание повтора, публикацию с
незавершённой доставкой и необходимость внимания. Обычное ожидание не рисуется как ошибка.
Нет ложного статуса «выполняется» только потому, что существует pending-запись.

У пункта меню — число доступных пользователю страниц, требующих внимания. Внутри раздела —
понятная причина и следующий шаг. Отдельно отображается предупреждение о пропавших регулярных
вызовах шедулера. Порог этого предупреждения задаётся с учётом пятиминутной частоты. Почта,
мессенджеры и новые внешние каналы уведомлений в первую версию не входят.

Журнал объединяет три вида операций:

- обычная ручная редакторская публикация;
- автоматическое обновление по устареванию;
- ускоренное вручную обновление по устареванию.

Он содержит страницу, локаль, время, инициатора, способ запуска, причины, затронутые секции,
результаты снимка и кэша, попытки и ошибки. Повторы остаются связанными с одной логической операцией.
Полное сравнение текстов «было / стало» не входит в первую версию. Старые события не получают
выдуманные причины/инициаторов, которых система тогда не сохраняла.

## Права

Используются существующие роли и разрешения:

- просмотр — только доступные пользователю страницы, включая журнал и суммарные счётчики;
- «Обновить сейчас» и «Повторить» — при праве публикации соответствующей страницы;
- общая пауза и изменение интервалов — администратору.

Новая роль не вводится. Проверки выполняются сервером для каждого элемента выбранного набора;
скрытие кнопки не является защитой. Существующие более строгие права повторов операций общих
секций не ослабляются через новый экран. API возвращает доступность и причину недоступности действия.

## Надёжность хранения и выполнения

Это обязательные технические следствия согласованного поведения, а не новые пользовательские шаги.

1. Накапливаемая потребность обновить страницу отделена от неизменяемого принятого плана исполнения.
   Объединение причин не переписывает manifest, receipt, expected snapshot или workset уже принятого effect.
2. Подготовка фиксирует текущий опубликованный snapshot ID, точные поколения причин и необходимые
   версии источников. Перед commit проверяются их согласованность и текущая опубликованность страницы.
3. Сравнение ожидаемого и текущего состояния при записи не позволяет старому обработчику перезаписать
   более новую ручную публикацию. При конфликте новый план строится от нового публичного снимка,
   а не путём редактирования старого принятого плана.
4. Активация снимка, обновление его зависимостей, подтверждение покрытых поколений причин и создание
   обязательства доставки через кэши атомарны. Нет окна «страница обновлена, задание кэша потеряно».
5. При событии во время выполнения новое поколение остаётся ожидающим. Закрываются только реально
   устранённые причины; совпадения общего кода ошибки недостаточно. Чистка JSON-LD не закрывает причину,
   для которой требовалось изменить видимый runtime.
6. Ручная редакторская публикация может закрыть уже покрытые причины, но не отменяет более новые.
   Новая публикация не стирает незавершённую доставку предыдущей; доставка учитывает актуальный origin.
7. Общий лимит обеспечивается между процессами, а не только локальным флагом `isRunning`. Потерявший
   владение обработчик не коммитит результат; прерванная работа восстанавливается без дублирования.
8. Повтор wake-up, команды ускорения, commit или ответа с неизвестным исходом безопасен. Cloud Scheduler
   допускает повторную доставку: [официальный контракт](https://docs.cloud.google.com/scheduler/docs/overview).
9. Возраст очереди считается от первоначального обнаружения, не от изменяемого timestamp повторной попытки.
10. Состояние очереди и история переживают перезапуск приложения. Отказ бэка или кэша не теряет работу
    и не превращается в ложное сообщение об успешной публикации.

Эта редакторская функция не считается реализацией новой серверной очереди.

## Границы первой версии

Не входят: встроенные очереди в источниках, новая роль, полные текстовые diff, внешние уведомления,
персональные календари и паузы страниц, кнопка массовой публикации всего сайта, новый микросервис
шедулера, новый брокер/Redis как обязательное условие, переработка ERP-синхронизации, активация
неопубликованных страниц, автопубликация черновиков, универсальная миграция схем/маршрутов.

Открытые продуктовые решения, например отложенный Intent Navigation, не считаются одобренными
этим общим механизмом. Header/footer вне снимка страницы сохраняют собственный контракт доставки.
Специальные потоки, включая career refresh, должны быть учтены в карте интеграции, а не получить
дублирующий процессор или неявно расширенные ERP-полномочия.

Не вводятся отдельная стартовая проверка всех страниц, пауза для рассмотрения начальной очереди
или её ручное утверждение. После разрешённого включения механизм сразу обрабатывает известные
устаревания по обычным правилам. Без ретроспективного обхода нельзя обещать обнаружение всех старых,
ранее не зарегистрированных изменений; новая система не должна выдавать это за подтверждённую свежесть.
Отказ от стартового аудита не отменяет тесты, проверки миграций и валидацию отдельных операций.

При этом новые события после включения должны находить поддержанных потребителей со старыми снимками,
даже если новые dependency captures ещё не записаны. Нужен поиск по доступному типизированному
контексту страницы/источника и областям отбора, без обязательной предварительной перепубликации всех
страниц. Если для конкретного сценария безопасное обнаружение или обновление невозможно, это явно
неподдержанный случай, а не молчаливое признание страницы свежей. Это обработка события, не стартовый обход.

## План реализации и ответственность

| Шаг | Ответственный | Результат |
| --- | --- | --- |
| 1. Карта покрытия и API | Бэк | Для каждой причины: событие, потребители, old/new scope, изменяемые фрагменты, проверки и тесты; точные DTO, состояния, права и ошибки |
| 2. Ядро refresh | Бэк | Durable demand, coalescing, сроки, безопасная подготовка, CAS, повторы, история и обязательство cache delivery |
| 3. Общий экран | Юрий, CMS-front | Один URL/пункт меню, очередь/журнал, фильтры, явный выбор, действия по capabilities, корректные промежуточные состояния |
| 4. Исполнение и доставка | Бэк совместно с ERP и site-front | Защищённый wake-up, ERP cadence, внеплановый запуск, cache adapters, проверка нескольких экземпляров |
| 5. Приёмка и включение | Бэк и Юрий | Интеграционные/браузерные тесты и отдельно разрешённая выкладка; без ручного утверждения стартовой очереди |

Точный контракт API выдаётся Юрию после первого шага; ему не нужно воспроизводить правила публикации
по UI или формировать backend-планы самостоятельно. Работа над backend-ядром может идти параллельно
с общим экраном после фиксации API. Создание отдельного scheduler-сервиса не блокирует первую версию.

В реализации нужно определить, а не выдавать за уже согласованные числа: размер партии, лимит
скорости и времени запуска, интервалы retry, порог пропавших вызовов, объём/срок хранения журнала
и физическую схему хранения. Удаление старой истории/idempotency records не входит в это ТЗ.
Границы supported source/consumer определяются тестируемой картой, а не обещанием «любой runtime».

Используется одна согласованная ветка записи снимков. Наличие подготовленных exact jobs не означает,
что writer mode уже переключён или его можно включить вместе с этим документом. Переход с legacy,
совместимость старых клиентов/операций и назначенная версия отката требуют отдельного плана выкладки.
Старые принятые эффекты нельзя переопределить как новую объединяемую очередь.

## Критерии приёмки

| Сценарий | Обязательный результат |
| --- | --- |
| Падение после source commit до распределения по страницам | Сохранённый сигнал позволяет восстановить очередь; old/new scopes не потеряны |
| Старый снимок без новых dependency captures и первое новое событие | Поддержанный потребитель найден без стартового обхода; невозможность обработки не скрыта |
| Новый отзыв для ранее пустого списка | Потребитель обнаружен; обновлён список и только необходимые связанные данные |
| Изменение показанного отзыва, профиля или карточки | Обновлены реальные потребители и локали, не весь сайт |
| Скрытие/удаление/перенос связи | Учтены старый и новый scope; срочный приоритет без обычных 30 минут |
| Внутреннее поле или результат вернулся к прежнему | Нет лишнего снимка и purge; причина закрыта как no-op |
| Неопубликованная страница или снятие перед commit | Нет первой публикации/реактивации |
| Сохранённый draft и изменённая рабочая composition | Они не попали в публичный результат; рабочее состояние сохранено |
| Source Save без публикации версии | Не распространяет новую версию общей секции на сайт |
| Публикация source с рабочими наследниками | Публичные потребители обновляются отдельно от review рабочих секций |
| Несколько причин и постоянный поток событий | Нет дублей страницы; первый срок не сдвигается, причины объединяются безопасно |
| Неподдержанная причина рядом с поддержанной | Нет широкого rebuild; независимое разрешённое обновление не снимает чужую причину |
| Новое событие во время обработки | Новое поколение остаётся в очереди после завершения старого |
| Ручная публикация раньше commit worker | Старый результат её не перезаписывает; перепроверяется новый публичный снимок |
| JSON-LD-only backfill | Не снимает причину неустранённого изменения видимого runtime |
| JSON-LD выключен для типа страницы | Freshness видимых runtime-данных продолжает работать |
| Повторный tick, double-click, потеря HTTP-ответа | Один логический результат без повторной активации |
| Два процесса и перезапуск worker | Общий лимит соблюдён, работа восстановлена, потерявший lock не коммитит |
| Одна страница падает | Другие готовые страницы продолжают обрабатываться |
| Пятая неудачная попытка или постоянная ошибка | Требуется внимание, нет бесконечного автоматического повторения |
| Snapshot успешен, cache упал | Видна частичная готовность; повторяет только доставку, не публикацию |
| Падение на границе snapshot и cache enqueue | Нет опубликованного результата без сохранённого обязательства доставки |
| Новая публикация при незавершённой доставке старой | Retry не возвращает старый снимок; origin и cache delivery согласованы |
| Пауза автоматики | Причины копятся, срочные авто не стартуют, начатые завершаются, ручной запуск разрешён |
| ERP не вызывает CMS | Очередь сохраняется, виден пропавший heartbeat; восстановление не создаёт залп |
| Обновление выбранных и закрытие браузера | Принятая сервером работа продолжается только для выбранного набора |
| Ограниченные права | Нет утечки страниц/счётчиков; запрещённые команды отвергаются сервером |
| Журнал трёх способов публикации | Различимы инициатор, причины, секции, snapshot/cache outcomes и связанные попытки |
| Первое включение | Нет отдельного аудита/утверждения очереди, действуют обычные ограничения и проверки |

Приёмка требует unit/contract tests, интеграционных тестов транзакций и конкуренции на изолированной
БД, проверки сбоев cache adapter и браузерных сценариев. Одного успешного build недостаточно.
Для фактических миграций, развёртывания и активации действуют отдельные подтверждения и playbook.
