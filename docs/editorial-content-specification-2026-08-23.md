# Editorial Content Specification - 2026-08-23

Status: normative product and integration contract for the first complete editorial-content contour.

This document supersedes conflicting product details in the June 2026 editorial architecture, roadmap,
and execution-plan documents. Those documents remain useful as implementation history. Migration of
legacy Actum content is deliberately excluded and requires a separate specification.

## 1. Objective

Build one shared editorial mechanism for three content kinds:

- Blog;
- Media / "Actum in media";
- Cases.

Each kind has two public page roles:

- a collection page;
- a detail page for one publication.

The six page types are:

- `blog_collection_page` and `blog_page`;
- `media_collection_page` and `media_page`;
- `case_collection_page` and `case_page`.

The mechanism must reuse the normal CMS page, section, draft, snapshot, preview, validation, publication,
history, and rollback lifecycle. It must not create a second publication CMS or a parallel body store.

## 2. First-Version Boundaries

Included:

- structured publication metadata;
- a typed ordered content builder;
- authors and legal reviewer relations;
- multiple service-tree relations;
- three independent public collections;
- server-rendered pagination;
- structured data generated by backend;
- locale families with independent publication;
- a late, separately delivered archive/unpublish slice.

Not included:

- tags;
- public search or filters;
- one mixed collection combining all three kinds;
- inline CTA blocks;
- gallery, video, arbitrary embed, or raw HTML blocks;
- manual collection-card ordering;
- legacy-content migration;
- automatic translation;
- slug editing and redirect management after first publication.

## 3. Public Routes

Primary Ukrainian routes have no locale prefix:

```text
/blog
/blog/{slug}
/media
/media/{slug}
/cases
/cases/{slug}
```

Russian and English variants use the normal locale prefix:

```text
/ru/blog/{slug}
/en/blog/{slug}
```

The same rule applies to media and cases.

Rules:

- the slug is required and unique within publication kind and locale;
- after first publication the slug is treated as immutable;
- an external media reference still has an Actum detail page at `/media/{slug}`;
- backend returns `publicPath`, canonical URL, and exact locale-switch URLs;
- frontend must not reconstruct routes from page type or slug;
- redirect handling for imported legacy URLs belongs to the separate migration specification.

## 4. Localization

Every localized publication is an independent normal CMS page joined through `localeGroupId`.

Rules:

- the Ukrainian variant is created first;
- Russian and English variants are created manually from locale tabs;
- one locale group may contain at most one page per locale;
- each locale owns its draft, content, dates, validation, history, preview, publication, and rollback;
- Russian and English may be edited before Ukrainian publication, but cannot be published until the
  Ukrainian variant is published;
- publishing or rolling back one locale never modifies another locale;
- locale creation copies only structural relations: authors, reviewer, service-tree relations, cover,
  external media relation, and ERP case reference;
- localized title, excerpt, SEO, body, case summary, and editorial dates are not copied as translations;
- only published locale variants are exposed as public alternates.

## 5. CMS Navigation And Editor

The CMS navigation contains one localized collapsible group, shown as "Materials" / "Публікації" as
appropriate for the UI locale, with three entries:

- Blog;
- Media;
- Cases.

Opening an entry shows publications of that kind, newest created first by default. Collection-page settings
are opened from a dedicated button in that list; a fourth navigation entry is not added.

The publication editor route is:

```text
/{locale}/admin/publications/{kind}/{pageId}
```

Desktop layout:

- left: publication list, preserving current filter, sort, search, and page;
- center: structured sections and block editor;
- right: public preview;
- top: locale switching, validation diagnostics, publication actions, and history.

On narrower screens the panes may collapse, but the contract and lifecycle remain the same.

Editing rules:

- explicit draft save; no autosave in V1;
- unsaved local changes produce a navigation warning;
- preview uses the saved draft and asks the editor to save first when the form is dirty;
- blocks can be added, deleted, duplicated, reordered by drag-and-drop, and moved with accessible up/down
  actions;
- editor actions use normal workbench/page endpoints and do not introduce a second draft API.

## 6. Detail Page Structure

### `blog_page`

1. `seo`
2. `publication_meta`
3. `content_builder`
4. optional `editorial_cta`
5. runtime service-hierarchy relations

### `media_page`

1. `seo`
2. `publication_meta`
3. `content_builder`
4. optional `editorial_cta`
5. runtime service-hierarchy relations

### `case_page`

1. `seo`
2. `publication_meta`
3. `case_summary`
4. `content_builder`
5. optional `editorial_cta`
6. runtime service-hierarchy relations

`publication_meta` is the only source for the public intro and collection card. A separate editable intro
section must not duplicate the same values.

Public render order is fixed in V1:

1. public intro from `publication_meta`;
2. `case_summary` for a case;
3. generated table of contents when applicable;
4. `content_builder`;
5. enabled `editorial_cta`;
6. runtime service-hierarchy section.

Missing optional parts are omitted without empty placeholders. Editors reorder blocks inside
`content_builder`, not whole page sections.

## 7. `publication_meta`

### Common fields

- `title`: required;
- `slug`: required;
- `excerpt`: required plain text;
- `coverMediaId`: optional;
- `coverAlt`: required when a cover exists;
- `publishedAt`: required public editorial date;
- `isFeatured`: boolean, default `false`;
- ordered service-tree relations defined below.

SEO is a separate standard page section and is not duplicated in `publication_meta`.

### Blog contributors

- zero to five ordered public lawyer authors;
- the first selected author is primary for compact UI presentation;
- no public lawyer authors means Actum Organization is the public author;
- one optional lawyer legal reviewer;
- no reviewer means `reviewedBy` is omitted and produces a warning;
- CMS actor/editor identity remains private workflow data and never becomes public authorship.

### Media fields

- `representationMode`: required enum `actum_article | external_reference`;
- `sourceName`: required;
- `sourceUrl`: required absolute URL for `external_reference`, recommended with warning for
  `actum_article`;
- `mediaPublishedAt`: the original external publication date.

For `actum_article`:

- zero to five ordered public lawyer authors;
- Actum is the fallback author;
- one optional lawyer reviewer;
- the local page contains an Actum-authored article about the media publication;
- table of contents is optional and off by default.

For `external_reference`:

- mode is selected explicitly and never inferred;
- the external source is the author/publisher of the original work;
- Actum and Actum lawyers are not represented as authors of that external work;
- `sourceName`, an absolute `sourceUrl`, and `mediaPublishedAt` are required;
- the public intro exposes a primary action to open the original material;
- `content_builder` may be empty without warning;
- table of contents is forced off.

### Case contributors and external relation

- exactly one primary lawyer is required;
- up to four ordered co-authors are allowed;
- total lawyer count cannot exceed five;
- duplicate lawyers are invalid;
- `erpCaseExternalId` is optional; missing value produces a warning.

## 8. Service-Tree Relations

A publication may have any number of ordered relations to the service hierarchy.

Each relation is one valid chain ending at one of:

- practice;
- service;
- problem.

Rules:

- if at least one relation exists, exactly one is marked `isPrimary=true`;
- remaining relations are additional and reorderable;
- hierarchy membership is validated by backend;
- duplicate endpoint chains are errors;
- an empty relation list is allowed with a warning;
- all primary and additional relation endpoints participate in runtime related content and JSON-LD
  `about` relations;
- backend owns validation and normalization; frontend uses selector contracts and must not reproduce the
  hierarchy algorithm.

There is no product-level relation-count limit. Normal request-size and abuse limits still apply.

## 9. `case_summary`

`case_summary` exists only for `case_page`.

Fields:

- `lead`: required plain text;
- `situation`: required rich text;
- `actions`: optional rich text, missing value is a warning;
- `result`: optional rich text, missing value is a warning;
- `courtName`: optional;
- `caseNumber`: optional;
- `resultLabel`: optional;
- `timelineNote`: optional;
- `confidentialityNote`: optional.

The section provides a fast structured case page. The long-form builder is optional but its absence is a
warning for a case.

## 10. `content_builder`

The builder is an ordered array with stable block identities:

```json
{
  "tocEnabled": true,
  "items": [
    {
      "blockId": "stable-uuid",
      "blockType": "paragraph",
      "variant": "default",
      "content": {}
    }
  ]
}
```

Rules:

- `blockId` remains stable while the block is edited or moved;
- array order is authoritative;
- `blockType` belongs to a closed backend registry;
- every block type has a typed content schema;
- arbitrary fields, raw HTML, custom CSS, nested builders, and unknown block types are rejected;
- an empty builder never blocks publication;
- an empty builder produces a warning for blog, `media/actum_article`, and case;
- an empty builder does not warn for `media/external_reference`.

### V1 block registry

#### `heading`

- `level`: `2 | 3 | 4`;
- `text`: required;
- `includeInToc`: boolean;
- backend generates a stable anchor.

#### `paragraph`

- one rich-text fragment;
- supported inline formatting and validated links only.

#### `list`

- `ordered | unordered`;
- typed list items.

#### `quote`

- required text;
- optional author and source.

#### `image`

- required valid `mediaId`;
- required alt text;
- optional caption, source, and link.

#### `table`

- typed columns and rows;
- optional caption;
- optional header row;
- merged cells are not supported in V1.

#### `callout`

- variant `info | warning | tip | important`;
- optional title;
- required text.

Deferred block types include gallery, video, arbitrary embeds, inline CTA, and related-links composition.

### Exact V1 block payloads

The following payload shapes are the backend contract. Fields not shown for a block type are rejected.

```json
{
  "blockId": "heading-1",
  "blockType": "heading",
  "content": { "level": 2, "text": "Section title", "includeInToc": true }
}
```

```json
{
  "blockId": "paragraph-1",
  "blockType": "paragraph",
  "variant": "default",
  "content": {
    "children": [
      { "type": "text", "text": "Plain text ", "marks": ["bold"] },
      { "type": "link", "text": "with a link", "href": "/contacts", "marks": [] }
    ]
  }
}
```

Supported inline marks are `bold`, `italic`, `underline`, and `strikethrough`. Links are limited to safe
site-relative or HTTP(S) URLs.

```json
{
  "blockId": "list-1",
  "blockType": "list",
  "content": {
    "style": "unordered",
    "items": [
      {
        "itemId": "list-item-1",
        "children": [{ "type": "text", "text": "First item" }]
      }
    ]
  }
}
```

```json
{
  "blockId": "quote-1",
  "blockType": "quote",
  "content": { "text": "Quote text", "author": "Author", "source": "Source" }
}
```

```json
{
  "blockId": "image-1",
  "blockType": "image",
  "content": {
    "mediaId": "media-id",
    "alt": "Meaningful image description",
    "caption": "Optional caption",
    "source": "Optional source",
    "link": "/services"
  }
}
```

```json
{
  "blockId": "table-1",
  "blockType": "table",
  "content": {
    "columns": [
      { "columnId": "column-1", "label": "Name" },
      { "columnId": "column-2", "label": "Value" }
    ],
    "rows": [
      { "rowId": "row-1", "cells": ["Item", "100"] }
    ],
    "caption": "Optional caption",
    "hasHeaderRow": true
  }
}
```

```json
{
  "blockId": "callout-1",
  "blockType": "callout",
  "content": { "variant": "important", "title": "Optional title", "text": "Required text" }
}
```

Backend adds `content.anchor = "heading-{blockId}"` to heading blocks in the public payload. The editor
must preserve `blockId` when a block is edited or moved and generate a new stable ID only for a new block.

## 11. Table Of Contents

The table of contents is generated from `heading` blocks and is not independently edited.

Rules:

- H2, H3, and H4 are supported;
- every heading can be included in or excluded from the TOC;
- excluding a heading does not hide it from the body;
- nesting follows heading level;
- a missing logical parent is a warning, not a publication error;
- backend owns stable anchors;
- Blog TOC is always enabled; no included headings produces a warning;
- Media `actum_article` and Case TOC are optional and off by default;
- Media `external_reference` TOC is always off;
- enabled TOC with no included headings produces a warning.

## 12. `editorial_cta`

V1 supports one fixed optional CTA section after the body, not CTA blocks inside the builder.

Fields:

- title;
- text;
- button label;
- validated action/target.

The section can be enabled or disabled. A disabled CTA is ignored. An enabled but incomplete CTA is a
publication error.

## 13. Collection Pages

There is one collection page per kind and locale.

Each collection page has:

1. `seo`;
2. editable `collection_header` with required title, optional lead, and optional cover;
3. read-only runtime `editorial_listing`.

Collection publication is independent from detail publication. Publishing a collection never publishes
its detail pages. An empty collection may be published with a warning.

The runtime list contains only currently published detail projections of the same kind and locale. Drafts,
unpublished translations, and archived items are excluded.

### Automatic collection refresh

When a detail page is published, rolled back, or archived:

1. the detail lifecycle operation succeeds first;
2. backend rebuilds its published projection;
3. if the related collection is already published, backend creates a technical collection snapshot with
   current runtime items;
4. collection SEO and header content remain unchanged;
5. audit records a system actor and a membership-change reason;
6. a refresh failure leaves the previous collection live and marks the collection stale/error;
7. an unpublished collection is never automatically published.

## 14. Collection Cards, Ordering, And Pagination

Stable card contract:

```ts
type EditorialCard = {
  pageId: string;
  kind: 'blog' | 'media' | 'case';
  publicPath: string;
  title: string;
  excerpt: string;
  cover: {
    mediaId: string;
    url: string;
    alt: string;
  } | null;
  publishedAt: string;
  isFeatured: boolean;
  attribution: unknown;
  relations: {
    practiceId: string | null;
    serviceId: string | null;
    problemId: string | null;
    practice?: EditorialCardRelation;
    service?: EditorialCardRelation;
    problem?: EditorialCardRelation;
  };
};

type EditorialCardRelation = {
  kind: 'practice' | 'service' | 'problem';
  id: string;
  externalId: string;
  sourceSlug: string | null;
  title: string;
  displayTitle: string;
  menuTitle: string | null;
  sourceName: string | null;
};
```

Attribution by kind:

- Blog: public authors or Actum fallback;
- Media `actum_article`: public authors plus source name;
- Media `external_reference`: external source and original URL;
- Case: primary lawyer and optional `resultLabel`.

Service-tree card clarification (2026-09-10): primary relation IDs remain compatible, and each resolvable
practice/service/problem also has the optional summary shown above. `home_cases` uses its `displayTitle`
for the relation chips in the current design. The same enrichment is available in `home_publications`
and editorial collection runtime cards; displaying chips on those surfaces remains a design choice.
The full multi-selection tree remains separate from these primary relation summaries.

Names use the containing page's locale and the existing fallback priority: nonempty localized menu
title, localized public name, source name, then external ID. No `shortName` is needed for these chips.
A null relation or missing reference row omits that summary, not the card; frontend skips the chip
instead of displaying its UUID. Relations are resolved in the card-list query, not with one additional
reference request per card. This does not change selection, ordering, or pagination.

A missing cover returns `cover: null`; frontend renders the standard placeholder.

Public ordering:

1. featured publications, newest first;
2. normal publications, newest first;
3. deterministic ID tie-break for equal dates.

`isFeatured` affects public order. A visible featured badge is optional.

CMS list behavior:

- default sort: `createdAt desc`;
- available sorts: `createdAt`, `updatedAt`, `publishedAt`, `title`;
- search: title or slug;
- filters: all, draft, published, errors, warnings, stale;
- page size: 50;
- featured ordering applies only when explicitly selected.

Public pagination:

- 12 cards per page;
- `/blog` for page 1 and `/blog?page=2` for subsequent pages;
- normal server-rendered anchor links; pagination works without JavaScript;
- response includes `page`, `pageSize`, `total`, and `totalPages`;
- featured items appear only on page 1 and are not repeated;
- every valid pagination page has its own canonical URL;
- pages after the first receive a localized page-number title suffix;
- JSON-LD `ItemList` includes only current-page items and uses global positions;
- a page number beyond the available range returns 404;
- pagination URLs are not added to `sitemap.xml`.

Public filters and search are deferred from V1.

## 15. Date Semantics

- `publishedAt` is the editor-owned public date and maps to JSON-LD `datePublished`;
- `modifiedAt` is backend-owned and maps to `dateModified` after a newly published version materially
  changes public content;
- draft edits do not change public `modifiedAt`;
- technical refresh with unchanged visible content preserves `modifiedAt`;
- `createdAt` and internal `updatedAt` are not public editorial dates;
- `mediaPublishedAt` belongs to the original external media work and never replaces the Actum page's
  `publishedAt`;
- case event, court, and result dates belong to case content and never replace page publication dates.

## 16. Validation Boundary

Publication-blocking errors:

- invalid required SEO;
- empty title or excerpt;
- missing/invalid/duplicate slug;
- unsupported block type or invalid block payload;
- broken media or entity references;
- invalid or duplicate service-tree chains;
- more than five authors or duplicate contributor relations;
- missing type-required media or case fields;
- enabled but incomplete CTA;
- type-specific requirements documented above.

Warnings:

- missing cover;
- empty builder where a warning is required;
- no service-tree relations;
- no named Blog or local Media author when Actum fallback is used;
- no reviewer;
- suspicious H2/H3/H4 hierarchy;
- enabled TOC with no included headings;
- optional weak/missing case-summary values;
- missing recommended local-media source URL;
- empty published collection.

Warnings never block publication. Frontend displays diagnostics returned by backend and must not recreate
the rules.

## 17. JSON-LD

Backend builds JSON-LD from the published snapshot. Frontend inserts the ready graph and does not infer
semantics.

Types:

- Blog detail: `BlogPosting`;
- Media `actum_article`: `Article`;
- Media `external_reference`: local `WebPage` whose `mainEntity` references the original external work by
  stable external `@id`;
- Case: `Article` whose `about` includes a stable case-matter `Thing`;
- Collections: `CollectionPage` plus `ItemList`.

Rules:

- Actum is referenced through one global Organization `@id`, not duplicated as a new organization on every
  page;
- lawyers use stable public `Person @id` values;
- up to five authors are emitted as an ordered `author` array;
- a selected reviewer is emitted through `reviewedBy` and is not silently converted to an author;
- all primary and additional service-tree endpoints become deduplicated `about` references;
- canonical URL, public dates, cover, and `BreadcrumbList` are included when applicable;
- absent optional properties are omitted;
- internal CMS user identity is never exposed;
- the external source, not Actum, owns the original work for `external_reference`.

## 18. Archive And Unpublish

Archive/unpublish belongs to V1 but is a late independent delivery slice and must not block the first Blog
end-to-end release.

Target rules:

- a never-published draft may be hard-deleted after confirmation and permission check;
- a previously published page cannot be hard-deleted through the normal editor;
- archive/unpublish removes the public snapshot pointer and projection row;
- related published collection is refreshed automatically;
- the old public URL returns 410 while archived;
- history is retained;
- restore returns the page to draft for normal validation and publication;
- permissions and audit events are explicit.

## 19. Responsibility Boundary

Backend owns:

- schemas and validation;
- lifecycle and snapshots;
- reference normalization;
- stable anchors and public routes;
- published projection and collection refresh;
- card and pagination contracts;
- dates and structured data.

CMS frontend owns:

- list and editor UI;
- typed block controls;
- drag/drop and accessible ordering controls;
- displaying backend diagnostics;
- dirty-state and explicit-save UX;
- preview orchestration through existing contracts.

Site frontend owns:

- rendering typed detail sections and blocks;
- rendering cards and pagination;
- rendering the standard missing-cover placeholder;
- inserting backend JSON-LD without semantic reconstruction.

## 20. Delivery Sequence

1. Align documentation and contracts.
2. Complete the common backend foundation.
3. Deliver Blog detail end-to-end through backend, CMS, and site frontend.
4. Extend the proven contour to both Media modes.
5. Extend it to Cases and `case_summary`.
6. Complete all three collection pages and automatic refresh behavior.
7. Deliver archive/unpublish as a bounded late slice.
8. Run contract, integration, end-to-end, accessibility, and manual acceptance checks.

This sequence intentionally proves the shared mechanism on one kind before multiplying it across all three.
