# Editorial Content Specification - 2026-08-23

Status: normative product and integration contract for the first complete editorial-content contour.

This document supersedes conflicting product details in the June 2026 editorial architecture, roadmap,
and execution-plan documents. Those documents remain useful as implementation history. Migration of
legacy Actum content is deliberately excluded and requires a separate specification.

2026-09-13 follow-up: [Redirects specification](redirects-specification-2026-09-13.md) now defines the
separate shared redirect mechanism and migration-map preparation boundary for editorial and other pages.
It does not permit changing published editorial slugs or imply that legacy content has been migrated.

2026-10-16 amendment: Blog detail pages gain optional structured FAQ and an aside recommendation list
containing only Blog articles. The requirements below are approved targets; this documentation change
does not implement them, rewrite existing content, or activate new refresh consumers.

2026-10-19 amendment: the approved
[CMS publication search and selection specification](cms-publication-search-and-filter-specification-2026-10-19.md)
defines independent Search and Selection modes, Enter-only search, explicitly applied filters and
newest-created-first ordering. It supersedes conflicting administrative list requirements below;
public collections and public search remain outside this amendment.

2026-11-15 amendment: the owner approved the publication-role, external-source, validation and JSON-LD
rules in sections 7, 16, 17 and 21. They replace conflicting earlier five-author limits, automatic Actum
fallbacks, organization-authored Cases, Case reviewers and the two Media representation modes,
including those in the JSON-LD architecture/implementation documents and older import specifications.
This is an approved target specification, not an implemented or deployed API change. No implementation,
data migration, retranslation, publication, queue action or snapshot rewrite is authorized by this edit.
Existing profile associations, search/filter semantics, selection, ordering and pagination are outside
this amendment and must not be redesigned as a consequence of the new role names.

## 1. Objective

Build one shared editorial mechanism for three content kinds:

- Blog;
- Media / "Actum in media";
- Cases.

Each kind has two public page roles:

- a collection page;
- a detail page for one publication.

The six page types are:

- `blog_collection_page` and `blog_page`;
- `media_collection_page` and `media_page`;
- `case_collection_page` and `case_page`.

The mechanism must reuse the normal CMS page, section, draft, snapshot, preview, validation, publication,
history, and rollback lifecycle. It must not create a second publication CMS or a parallel body store.

## 2. First-Version Boundaries

Included:

- structured publication metadata;
- a typed ordered content builder;
- optional Blog FAQ and automatic/manual Blog-only recommendations outside the builder;
- kind-specific lawyer authors, Media participants and explicit legal-review attribution;
- multiple service-tree relations;
- three independent public collections;
- server-rendered pagination;
- structured data generated by backend;
- locale families with independent publication;
- a late, separately delivered archive/unpublish slice.

Not included:

- tags;
- public search or filters;
- one mixed collection combining all three kinds;
- inline CTA blocks;
- gallery, video, arbitrary embed, or raw HTML blocks;
- manual collection-card ordering;
- mixed Blog/Case/Media recommendations, pinned-plus-automatic recommendation modes, and tag weights;
- legacy-content migration;
- automatic translation;
- slug editing after first publication; redirect management is a separate follow-up under the
  2026-09-13 redirect specification, not a content-section operation.

## 3. Public Routes

Primary Ukrainian routes have no locale prefix:

```text
/blog
/blog/{slug}
/media
/media/{slug}
/cases
/cases/{slug}
```

Russian and English variants use the normal locale prefix:

```text
/ru/blog/{slug}
/en/blog/{slug}
```

The same rule applies to media and cases.

Rules:

- the slug is required and unique within publication kind and locale;
- after first publication the slug is treated as immutable;
- an external media reference still has an Actum detail page at `/media/{slug}`;
- backend returns `publicPath`, canonical URL, and exact locale-switch URLs;
- frontend must not reconstruct routes from page type or slug;
- redirect handling for imported legacy URLs follows the separate
  [redirect specification](redirects-specification-2026-09-13.md).

## 4. Localization

Every localized publication is an independent normal CMS page joined through `localeGroupId`.

Rules:

- the Ukrainian variant is created first;
- Russian and English variants are created manually from locale tabs;
- one locale group may contain at most one page per locale;
- each locale owns its draft, content, dates, validation, history, preview, publication, and rollback;
- Russian and English may be edited before Ukrainian publication, but cannot be published until the
  Ukrainian variant is published;
- publishing or rolling back one locale never modifies another locale;
- locale creation copies the applicable structural relations and explicit choices: Blog author mode
  and authors/reviewer, Case primary/coauthors, Media participants/review mode/source-link mode,
  service-tree relations, cover, external media relation, and ERP case reference;
- localized title, excerpt, SEO, body, case summary, and editorial dates are not copied as translations;
- Blog FAQ text and recommendation settings are authored independently per locale; a new locale starts
  with FAQ disabled and automatic recommendations, without copying the source FAQ or manual selection;
- only published locale variants are exposed as public alternates.

## 5. CMS Navigation And Editor

The CMS navigation contains one localized collapsible group, shown as "Materials" / "Публікації" as
appropriate for the UI locale, with three entries:

- Blog;
- Media;
- Cases.

Opening an entry shows publications of that kind, newest created first by default. Collection-page settings
are opened from a dedicated button in that list; a fourth navigation entry is not added.

Search and Selection are independent list modes under the
[19 October 2026 specification](cms-publication-search-and-filter-specification-2026-10-19.md).
Each mode retains its own edited and applied conditions; list navigation and return from an editor
must not apply an unconfirmed search or filter change.

The publication editor route is:

```text
/{locale}/admin/publications/{kind}/{pageId}
```

Desktop layout:

- left: publication list, preserving current filter, sort, search, and page;
- center: structured sections and block editor;
- right: public preview;
- top: locale switching, validation diagnostics, publication actions, and history.

On narrower screens the panes may collapse, but the contract and lifecycle remain the same.

Editing rules:

- explicit draft save; no autosave in V1;
- unsaved local changes produce a navigation warning;
- preview uses the saved draft and asks the editor to save first when the form is dirty;
- blocks can be added, deleted, duplicated, reordered by drag-and-drop, and moved with accessible up/down
  actions;
- editor actions use normal workbench/page endpoints and do not introduce a second draft API.

## 6. Detail Page Structure

### `blog_page`

1. `seo`
2. `publication_meta`
3. `content_builder`
4. optional `blog_faq`
5. optional `editorial_cta`
6. runtime service-hierarchy relations
7. `blog_recommendations`: separate aside selection configuration and resolved recommendation list

### `media_page`

1. `seo`
2. `publication_meta`
3. `content_builder`
4. optional `editorial_cta`
5. runtime service-hierarchy relations

### `case_page`

1. `seo`
2. `publication_meta`
3. `case_summary`
4. `content_builder`
5. optional `editorial_cta`
6. runtime service-hierarchy relations

`publication_meta` is the only source for the public intro and collection card. A separate editable intro
section must not duplicate the same values.

Public render order is fixed in V1:

1. public intro from `publication_meta`;
2. `case_summary` for a case;
3. generated table of contents when applicable;
4. `content_builder`;
5. enabled `blog_faq` for Blog, immediately after the builder;
6. enabled `editorial_cta`;
7. runtime service-hierarchy section.

For Blog, the body and FAQ belong to the same HTML `article` on the same URL. Recommendations are
complementary `aside` content, not an article-body block; responsive placement belongs to the frontend
template. Separate CMS sections do not imply separate public pages or separate HTML articles.

Missing optional parts are omitted without empty placeholders. Editors reorder blocks inside
`content_builder`, not whole page sections.

## 7. `publication_meta`

### Common fields

- `title`: required;
- `slug`: required;
- `excerpt`: required plain text;
- `coverMediaId`: optional;
- `coverAlt`: required when a cover exists;
- `publishedAt`: required public editorial date;
- `isFeatured`: boolean, default `false`;
- ordered service-tree relations defined below.

SEO is a separate standard page section and is not duplicated in `publication_meta`.

### Article title length (14 November 2026 amendment)

For Blog (`blog_page`), Media (`media_page`, both representation modes) and Cases (`case_page`),
the recommendation for `publication_meta.title` is up to 100
characters inclusive in all three languages (UK/RU/EN), using the existing content-length
calculation. More than 100 characters produces the field warning `PAGE_SECTION_TITLE_LONG`;
100 does not, while 101 does. The warning alone does not block draft Save or publication.
The same rule applies to saved-version, editor and publication validation.

The 100-character Case rule is extended to Blog and Media, replacing their previous 90-character
warning boundary. SEO title, slug, excerpt, other section title recommendations,
required-field and structural rules do not change. No frontend change, migration, historical
version rewrite or automatic republication is part of this amendment. Previously stored
diagnostics adopt the new boundary through their normal validation refresh.

### Blog contributors

- Choose one to three ordered lawyer authors OR explicitly choose "Автор — Актум". Every personal
  author is a lawyer selected from the existing CMS lawyer reference model. Non-lawyer personal author
  profiles are not introduced.
- The first selected lawyer remains primary for compact presentation; the other selected lawyers are
  also authors, not reviewers. Duplicate author references or more than three authors are errors.
- The Actum choice means corporate authorship, not unknown authorship. Show a visible Actum byline
  linked to the localized About page through the existing route contract. It is mutually exclusive
  with selected lawyer authors; a conflicting selection is an error, not a reason to discard lawyers.
- If neither lawyer authors nor the explicit Actum choice is present, report a missing-authorship
  warning. A selected reviewer does not remove that warning. An empty field is not an implicit Actum
  choice, and JSON-LD must not manufacture an author in that state.
- One optional lawyer legal reviewer may be selected. The reviewer must not be any of this Blog
  publication's authors; an overlapping reference is an error. This is an Actum editorial rule, not
  a Google requirement for two different people.
- Missing Blog reviewer is valid and never produces a missing-reviewer warning, including when the
  explicit author is Actum. Do not create a new warning for corporate authorship without a reviewer.
- CMS actor/editor identity remains private workflow data and never becomes public authorship or
  public review attribution.

### Media fields

- Media describes material from an external source: an interview, comment, broadcast or other external
  publication. Independent Actum articles belong in Blog. Media has no public author selector and no
  "our article / external material" distinction. `representationMode` is not a new-authoring requirement
  or a condition for role validation/JSON-LD; its old values remain historical data only.
- `sourceName` is required in all cases. Missing/blank source name is a publication-blocking error.
  A reviewer or participant does not replace the source.
- The editor must explicitly provide one of: a valid absolute HTTP(S) `sourceUrl`, OR the mode
  "Без посилання". Missing URL without the explicit no-link choice is an error, not a warning.
  A malformed/unsafe populated URL is an error. The two choices are mutually exclusive; conflicting
  populated URL/no-link state is an error, not silently normalized by deleting one choice.
- Explicit "Без посилання" is a complete valid decision and produces no missing-link warning.
  In this mode omit the original-material link/action; do not use `#`, the Actum detail URL, the source
  homepage or another fabricated URL as a substitute.
- `mediaPublishedAt` remains required for the described external work, preserving the existing
  external-reference date requirement; it never replaces the local Actum page's `publishedAt`.
  No new date policy, body rewrite, TOC-setting change or video-contract change is introduced here.
- No public authors are assigned from Media participants, reviewers, CMS users or an empty author list.
  The external source is not automatically asserted to be the personal author of the original work.

#### Media participants

- A dedicated participants field contains zero to seven ordered lawyer references explicitly selected
  by the editor. The editor's saved selection is authoritative; do not infer participants from text,
  bylines, specialization, ERP associations or review attribution.
- Empty participants are valid without a warning. More than seven or duplicate references are errors.
- Label selected people as participants, not authors of the external work. Selection alone does not
  assert that they wrote the text or qualify them as `Article.author` / `CreativeWork.contributor`.
- A participant may also be the selected reviewer. The reviewer may instead be a lawyer outside the
  participants list; that does not add them to the list or consume one of its seven places.

#### Media review attribution

- Select one lawyer reviewer OR explicitly select "Перевірено редакцією Актум".
- The organization option attests actual editorial checking of our local page's description,
  quotations and presentation of the external material. It is not a claim to have checked the entire
  external website, and is not merely publisher/responsible-party metadata.
- Missing both choices produces one missing-review-attribution warning, which does not block
  publication. An empty field never automatically means Actum reviewed the page.
- Selecting both choices or multiple lawyer reviewers is an error. Public UI and JSON-LD use the
  selected choice consistently; the organization option uses the existing global Actum identity.

### Case contributors and external relation

- Exactly one explicitly selected primary lawyer is required. No primary lawyer is a publication error,
  including when the coauthor list is empty. Neither a coauthor nor Actum is silently promoted.
- Zero to two ordered lawyer coauthors are allowed: at most three lawyers including the primary.
  More than two coauthors, duplicate references or repeating the primary in coauthors are errors.
- All personal authors/coauthors are lawyers. Organization-authored Cases are no longer a target
  authoring option; the older corporate fallback does not satisfy the required primary lawyer.
- Case has no reviewer role, selector, missing-reviewer diagnostic or new `WebPage.reviewedBy` relation.
  Historical reviewer values remain in historical data; do not erase them from saved versions.
- ERP source linkage remains a separate page-level system concern, not an authored-public-byline field.
  Do not restore the obsolete missing-`erpCaseExternalId` section warning or expose a technical source ID
  in public payloads/JSON-LD. The read-only ERP deal number and confirmed linkage rules are unchanged.

### Administrative ERP deal number (20 October 2026 clarification)

For Cases, the `publication_meta` editor displays the ERP `deals.deal_str` as read-only
"Номер справи ERP". It comes from administrative fields on the existing `cms_pages` record, linked
through confirmed `source.system + source.dealId`, not from editable `publication_meta` or `case_summary`
content. No separate table is added: one existing page stores the source fields and all translations
resolve them through their locale group, including translations created later.
The input contract retains `CreateArticlePayload.dealNumber`; earlier placement in
`case_summary.dealNumber` is superseded. ERP owns the value; CMS stores the last trusted value
locally in `erp_deal_number` for display and Case-only search. Linked language variants use the same
source value. Updates preserve the ordinary page `updated_at` and `updated_by`.

Editor API enrichment is outside `content`; ordinary section Save/history restore cannot write the
number. Trusted synchronization updates do not create section versions, change SEO approval or page
publication/staleness, or require republishing. The number is administrative-only and is not added to
public payloads/snapshots, JSON-LD, title or slug. Missing numbers do not block editing/publication;
do not substitute `erpCaseExternalId`, the judicial `case_summary.caseNumber`, or a generated value.
Editor reads/search use the local projection, without synchronous ERP requests.

This is an approved target contract, not implemented integration or deployment. See the
[search and selection specification](cms-publication-search-and-filter-specification-2026-10-19.md)
for integration dependencies and acceptance criteria.

### Public display data for detail pages

The 2026-10-15 clarification separates editable references from resolved public display fields.
Preview and newly assembled snapshots for `blog_page`, `media_page` and `case_page` add the following
to the normalized `publication_meta` payload without changing its stored IDs:

- `coverMediaUrl: string | null` and `cover: { mediaId, url, alt } | null`;
- kind-appropriate public authors, participants and reviewer display objects, resolved from the saved
  role selections; retain names, available photos and existing public-profile links;
- `primaryLawyer`: the same person shape for the explicitly selected case primary author, otherwise `null`;
- Blog reviewer: selected lawyer display data or `null`;
- Media reviewer: selected lawyer display data, the explicitly selected Actum organization, or `null`;
- Case reviewer: absent from new presentation semantics; historical raw content remains readable.

The optional person fields are nullable. Names use the requested locale's public name with ERP source
name fallback. Only publicly visible lawyers are resolved; links require a current published profile
in that exact locale, and photos require available uploaded media. Missing selected references are
omitted without substituting another lawyer or the organization. Reference errors retain their ordinary
diagnostics; this amendment does not weaken reference checks. Actum authorship is used only for the
explicit Blog organization choice. Media exposes its external-source data and editor-selected
participants, not lawyer authors; review attribution describes the local WebPage, not authorship of the
external work. CMS editor identity remains private.

The public roles must be visible and distinguishable: author/coauthors for Blog/Case, participants for
Media, and the chosen review attribution where applicable. Do not render an unresolved identity as an
invented named expert, invent credentials, or treat an unavailable profile link as a new identity.
Exact new DTO field names, schema revisions and compatibility fixtures must be agreed before a later
implementation rollout; this specification does not claim the deployed API already returns them.

Each content-builder image additionally receives `content.imageUrl: string | null`; its original
`mediaId`, alt text, caption, source and link remain unchanged. Frontend renders this URL, not the ID.
Generated display fields are not editable or sent back in section save requests. Collection-card
payloads retain their separate existing contract.

Exact publication captures resolved data during preparation and uses that capture during commit,
without re-resolving live references. Existing published snapshots and older prepared plans are not
rewritten automatically. Subsequent lawyer profile changes currently reach these detail-page display
fields on a new publication, not through an automatic editorial-detail refresh handler.

## 8. Service-Tree Relations

A publication may have any number of ordered relations to the service hierarchy.

Each relation is one valid chain ending at one of:

- practice;
- service;
- problem.

Rules:

- if at least one relation exists, exactly one is marked `isPrimary=true`;
- remaining relations are additional and reorderable;
- hierarchy membership is validated by backend;
- duplicate endpoint chains are errors;
- an empty relation list is allowed with a warning;
- all primary and additional relation endpoints participate in runtime related content and JSON-LD
  `about` relations;
- backend owns validation and normalization; frontend uses selector contracts and must not reproduce the
  hierarchy algorithm.

There is no product-level relation-count limit. Normal request-size and abuse limits still apply.

## 9. `case_summary`

`case_summary` exists only for `case_page`.

Fields:

- `lead`: required plain text;
- `situation`: required rich text;
- `actions`: optional rich text, missing value is a warning;
- `result`: optional rich text, missing value is a warning;
- `courtName`: optional;
- `caseNumber`: optional;
- `resultLabel`: optional;
- `timelineNote`: optional;
- `confidentialityNote`: optional.

The section provides a fast structured case page. The long-form builder is optional but its absence is a
warning for a case.

## 10. `content_builder`

The builder is an ordered array with stable block identities:

```json
{
  "tocEnabled": true,
  "items": [
    {
      "blockId": "stable-uuid",
      "blockType": "paragraph",
      "variant": "default",
      "content": {}
    }
  ]
}
```

Rules:

- `blockId` remains stable while the block is edited or moved;
- array order is authoritative;
- `blockType` belongs to a closed backend registry;
- block-level `variant` belongs to the allowlist of that block type;
- every block type has a typed content schema;
- arbitrary fields, raw HTML, custom CSS, nested builders, and unknown block types are rejected;
- an empty builder never blocks publication;
- an empty builder produces a warning for Blog and Case;
- Media can describe an external work without a copied full body; an empty Media builder does not
  produce a missing-body warning and does not select an authorship/representation mode.

### V1 block registry

#### `heading`

- block variant `default | marker`;
- `level`: `2 | 3 | 4`;
- `text`: required;
- `includeInToc`: boolean;
- backend generates a stable anchor;
- `marker` selects the designed accent-marker appearance; color and geometry remain frontend styles.

#### `paragraph`

- one rich-text fragment;
- supported inline formatting and validated links only.

#### `list`

- `ordered | unordered`;
- typed list items.

#### `quote`

- block variant `text_first | attribution_first`;
- required text;
- optional author and source;
- legacy `default | top` values remain readable as `text_first | attribution_first` respectively.

#### `image`

- block variant `default | horizontal | vertical`;
- required valid `mediaId`;
- required alt text;
- optional caption, source, and link.

#### `table`

- block variant `default | comparison`;
- typed columns and rows;
- optional caption;
- independent `hasHeaderRow` and `hasHeaderColumn` flags;
- `comparison` requires exactly two columns and visible column headings;
- merged cells are not supported in V1.

#### `callout`

- variant `info | warning | tip | important`;
- optional title;
- required text.

Deferred block types include gallery, video, arbitrary embeds, inline CTA, and inline related-links
composition. The approved Blog recommendation aside is a separate section, not one of these blocks.

### Exact V1 block payloads

The following payload shapes are the backend contract. Fields not shown for a block type are rejected.

```json
{
  "blockId": "heading-1",
  "blockType": "heading",
  "variant": "marker",
  "content": { "level": 2, "text": "Section title", "includeInToc": true }
}
```

```json
{
  "blockId": "paragraph-1",
  "blockType": "paragraph",
  "variant": "default",
  "content": {
    "children": [
      { "type": "text", "text": "Plain text ", "marks": ["bold"] },
      { "type": "link", "text": "with a link", "href": "/contacts", "marks": [] }
    ]
  }
}
```

Supported inline marks are `bold`, `italic`, `underline`, and `strikethrough`. Links are limited to safe
site-relative or HTTP(S) URLs.

```json
{
  "blockId": "list-1",
  "blockType": "list",
  "content": {
    "style": "unordered",
    "items": [
      {
        "itemId": "list-item-1",
        "children": [{ "type": "text", "text": "First item" }]
      }
    ]
  }
}
```

```json
{
  "blockId": "quote-1",
  "blockType": "quote",
  "variant": "attribution_first",
  "content": { "text": "Quote text", "author": "Author", "source": "Source" }
}
```

```json
{
  "blockId": "image-1",
  "blockType": "image",
  "content": {
    "mediaId": "media-id",
    "alt": "Meaningful image description",
    "caption": "Optional caption",
    "source": "Optional source",
    "link": "/services"
  }
}
```

```json
{
  "blockId": "table-1",
  "blockType": "table",
  "content": {
    "columns": [
      { "columnId": "column-1", "label": "Name" },
      { "columnId": "column-2", "label": "Value" }
    ],
    "rows": [
      { "rowId": "row-1", "cells": ["Item", "100"] }
    ],
    "caption": "Optional caption",
    "hasHeaderRow": true,
    "hasHeaderColumn": false
  }
}
```

For an ordinary table, the two header flags are independent: both false means no headers, only
`hasHeaderRow` marks column headings, only `hasHeaderColumn` marks the first cell of every body row as a
row heading, and both true provide both semantics. A comparison table uses `"variant": "comparison"`,
exactly two columns, and `hasHeaderRow: true`.

```json
{
  "blockId": "callout-1",
  "blockType": "callout",
  "content": { "variant": "important", "title": "Optional title", "text": "Required text" }
}
```

Backend adds `content.anchor = "heading-{blockId}"` to heading blocks in the public payload. The editor
must preserve `blockId` when a block is edited or moved and generate a new stable ID only for a new block.

## 11. Table Of Contents

The table of contents is generated from `heading` blocks and is not independently edited. Blog adds one
entry for an enabled, nonempty FAQ, using its section title and a backend-owned stable anchor. Individual
FAQ questions are not added to the TOC in this version.

Rules:

- H2, H3, and H4 are supported;
- every heading can be included in or excluded from the TOC;
- excluding a heading does not hide it from the body;
- nesting follows heading level;
- a missing logical parent is a warning, not a publication error;
- backend owns stable anchors;
- Blog TOC is always enabled; no resulting entries, including FAQ, produces a warning;
- Case TOC is optional and off by default;
- existing Media TOC settings are preserved; this role/source amendment does not add a mode selector,
  change TOC behavior or reset a saved TOC setting;
- enabled TOC with no resulting entries produces a warning.

## 12. `editorial_cta`

V1 supports one fixed optional CTA section after the body and any enabled Blog FAQ, not CTA blocks inside
the builder.

Fields:

- title;
- text;
- button label;
- validated action/target.

The section can be enabled or disabled. A disabled CTA is ignored. An enabled but incomplete CTA is a
publication error.

## 12a. Blog FAQ

`blog_faq` is one optional, page-owned section per Blog locale, disabled by default. It reuses the
structured FAQ model rather than adding a builder block or guessing questions from ordinary headings.

- Editable fields: plain-text `title` and ordered `items` with stable question IDs, plain-text
  `question`, and `answer` using the existing safe rich-text contract, including formatting and links.
- The editor can add, remove, edit and reorder questions, and enable or disable the whole FAQ.
- When enabled, a nonempty title and at least one complete question/answer pair are required. Empty
  questions/answers and invalid item identities block publication; three questions are not a minimum.
- A disabled FAQ has no missing-content diagnostics, public placeholder, TOC entry or FAQ graph nodes.
- Saving and history follow the normal section lifecycle. Public activation is `with_page`, through the
  normal page publication flow, not an independently published reusable FAQ source.
- The frontend renders FAQ inside the same `article`, directly after the body and before CTA or
  recommendations: section title H2, question titles H3. All answer text is present in server-rendered
  HTML; expanding a question must not be required to fetch its answer.
- The page remains a Blog article. Backend structured data describes the visible FAQ as a subordinate
  fragment, following the common FAQ graph contract; it must not replace `BlogPosting` with `FAQPage`
  or invent a separate public FAQ URL. No Google rich-result or ranking outcome is promised.
- Existing question/answer prose remains intact until explicitly converted. Conversion must move the
  intended text without leaving a second visible copy or automatically reclassifying unrelated headings.

## 12b. Blog Recommendations

`blog_recommendations` is outside `content_builder` and always renders as an aside. Its page-owned
selection configuration follows normal saved-version/history/page-publication rules; resolved cards are
backend-generated read-only data, never an additional editable copy of the recommended article.

The default is `auto`. `manual` completely replaces automatic selection. The public list contains at
most three eligible Blog articles in the current locale. Cases and Media are excluded in both modes,
including articles selected manually. The current article/locale family and duplicate selections are
excluded. Drafts, archived pages and missing published translations cannot become cards; there is no
cross-locale fallback. An empty result is valid and hides the entire aside without a placeholder.

Automatic selection:

1. Read the owning article state explicitly selected for preview or captured by the publication plan.
   A scoped refresh instead retains its current published relations/settings, never saved drafts.
   Candidate articles always come from published projections of the same locale.
2. Compare primary and additional chains by their deepest shared identity: same problem, then same
   service, then same practice. Use the best single match, not a sum of matches or number of relations.
3. Exclude candidates with no common practice/service/problem. No taxonomy means no automatic results,
   not an unrelated newest-articles fallback. CMS explains an empty result without blocking publication.
4. Sort by match depth descending, public `publishedAt` descending, then stable page ID ascending.
   `isFeatured`, technical update dates and tag weights do not override thematic relevance.
5. Select at most three distinct articles. One or two eligible results remain one or two cards.

Manual selection:

- Store up to three ordered Blog locale-group IDs, following the existing editorial selector convention.
- Resolve only each selected group's currently published article in the owner's locale, retaining order.
- Reject duplicate, own-family, wrong-kind and invalid references. An existing selected group without an
  available published locale is omitted with an editor diagnostic; preserve the selection so its return
  can be detected. Do not substitute a different article or automatically fill unused positions.

Use the common `EditorialCard` data for title, excerpt, cover, date and backend-provided public path.
Compatibility: a valid published legacy article without an immutable editorial-card capture is
temporarily unavailable for this selector. Omit it before the three-card limit and report a CMS
warning; retain its automatic scope/manual selection so a later normal publication can make it
eligible. Never fill the gap from live reference data or a draft. A present but corrupt capture or
inconsistent published head remains an explicit error. This avoids mutually blocking first
publications when all related legacy articles still lack captures.
Frontend must not fetch extra candidates, score articles, rebuild URLs or reorder the list. Cards link to
their detail pages; this three-item aside is not a paginated collection. The existing public collections
and their pagination remain unchanged.

Exact preparation captures the selected owner configuration and resolved cards; commit uses that capture
under the existing freshness guards rather than silently reselecting articles from live data.

Refresh is part of this feature, not an implied capability of the existing resolver:

- Register a narrow Blog recommendation consumer in the common stale-refresh mechanism under
  `related_content`, with the published selection mode, selected IDs and taxonomy scope as dependencies.
- Detect relevant published card/availability/relation changes, rollback/unpublish, and newly eligible
  articles even if absent from the previous three cards. Manual mode tracks selected groups, including
  temporarily unavailable selections; automatic mode tracks the selection scope, including empty lists.
- Refresh only the recommendations and their necessary dependent graph/dependency records from the
  current published owner snapshot. Preserve body, FAQ, metadata, CTA, selection settings and drafts.
- Do not publish a draft configuration, introduce the new aside into an old snapshot that lacks it, or
  fall back to full page publication. Unsupported old shapes require an explicit normal page publication.
- Follow common batching, delay, urgent-removal, retry, no-op and cache-delivery rules. A changed
  recommendation list alone must not be treated as a change to the owner's recommendation-card source
  and cause reciprocal refresh loops. No separate scheduler or per-visitor reselection is introduced.

Acceptance requires preview/publication parity, independent locales, disabled/incomplete FAQ checks,
stable question IDs and one FAQ TOC entry, server-rendered article membership, both selection modes,
0/1/2/3/>3 candidates, equal-score/date ordering, excluded self/Case/Media/draft entries, and published
refresh after a new candidate or removal. Refresh tests must prove unchanged unrelated drafts/content,
no-op handling and no recommendation-to-recommendation loop. Existing imported prose is not migrated by
this specification update.

## 13. Collection Pages

There is one collection page per kind and locale.

Each collection page has:

1. `seo`;
2. editable `collection_header` with required title, optional lead, and optional cover;
3. read-only runtime `editorial_listing`.

Collection publication is independent from detail publication. Publishing a collection never publishes
its detail pages. An empty collection may be published with a warning.

The runtime list contains only currently published detail projections of the same kind and locale. Drafts,
unpublished translations, and archived items are excluded.

### Automatic collection refresh

When a detail page is published, rolled back, or archived:

1. the detail lifecycle operation succeeds first;
2. backend rebuilds its published projection;
3. if the related collection is already published, backend creates a technical collection snapshot with
   current runtime items;
4. collection SEO and header content remain unchanged;
5. audit records a system actor and a membership-change reason;
6. a refresh failure leaves the previous collection live and marks the collection stale/error;
7. an unpublished collection is never automatically published.

Attribution by kind:

ordering, pagination or layout. Do not redesign those mechanisms as part of the 2026-11-15 amendment.

Service-tree card clarification (2026-09-10): primary relation IDs remain compatible, and each resolvable

Names use the containing page's locale and the existing fallback priority: nonempty localized menu
title, localized public name, source name, then external ID. No `shortName` is needed for these chips.
A null relation or missing reference row omits that summary, not the card; frontend skips the chip
instead of displaying its UUID. Relations are resolved in the card-list query, not with one additional

2. normal publications, newest first;

  and unsaved local changes are excluded;
- preserve mode, separate edited/applied conditions, pagination and scroll on return from a material;
- page size: 50;
- featured priority, alternative user sorts and public search are not added by this amendment.

- 12 cards per page;
- `/blog` for page 1 and `/blog?page=2` for subsequent pages;
- normal server-rendered anchor links; pagination works without JavaScript;

Public filters and search are deferred from V1.

## 15. Date Semantics

- `publishedAt` is the editor-owned public date and maps to JSON-LD `datePublished`;
- `modifiedAt` is backend-owned and maps to `dateModified` after a newly published version materially
  changes public content;
- draft edits do not change public `modifiedAt`;
- technical refresh with unchanged visible content preserves `modifiedAt`;
- `createdAt` and internal `updatedAt` are not public editorial dates;
- `mediaPublishedAt` belongs to the original external media work and never replaces the Actum page's
  `publishedAt`;
- case event, court, and result dates belong to case content and never replace page publication dates.

## 16. Validation Boundary

Publication-blocking errors:

- invalid required SEO;
- empty title or excerpt;
- missing/invalid/duplicate slug;
- unsupported block type or invalid block payload;
- broken media or entity references;
- invalid or duplicate service-tree chains;
- Blog: more than three lawyer authors, duplicates, conflicting lawyer/Actum authorship, or reviewer
  equal to any selected author;
- Case: no explicit primary lawyer, more than two coauthors, duplicate lawyers or the primary repeated
  in coauthors; the absence of coauthors does not waive the primary requirement;
- Media: more than seven participants, duplicate participants, multiple/conflicting review choices,
  missing source name, missing both a valid source URL and explicit no-link choice, invalid populated
  source URL, or a conflicting URL/no-link choice;
- missing type-required media or case fields;
- enabled but incomplete CTA;
- enabled but incomplete Blog FAQ or invalid Blog recommendation configuration;
- type-specific requirements documented above.

Warnings:

- missing cover;
- empty builder where a warning is required;
- no service-tree relations;
- Blog: neither lawyer authors nor an explicit Actum author choice, even when a reviewer is selected;
- Media: neither a lawyer reviewer nor explicit "Перевірено редакцією Актум";
- suspicious H2/H3/H4 hierarchy;
- enabled TOC with no resulting entries, including the Blog FAQ entry;
- optional weak/missing case-summary values;
- empty published collection.

Missing or disabled optional Blog FAQ and an empty recommendation result do not themselves produce
publication errors. Unavailable manually selected translations are diagnosed without silently replacing
the editor's selection.

Warnings never block publication. Frontend displays diagnostics returned by backend and must not recreate
the rules.

## 17. JSON-LD

Backend builds preview JSON-LD from the corresponding resolved preview and captures publication JSON-LD
from the exact selected publication inputs. The ready graph is stored in the immutable published
snapshot. Frontend inserts it and does not infer semantics or rebuild roles from live reference data.

Types:

- Blog detail: `BlogPosting`;
- Media: local `WebPage` describing an external `CreativeWork`; no locally owned `Article` is fabricated
  from the former `actum_article` value;
- Case: `Article` whose `about` includes a stable case-matter `Thing`;
- Collections: `CollectionPage` plus `ItemList`.

### Identity and truthful visible attribution

- Actum is referenced through one global Organization `@id`, not duplicated as a new organization on every
  page or replaced with the localized About page's `WebPage @id`. The About link identifies the company
  to readers; it is not a different author/reviewer organization.
- Lawyers use the existing stable public `Person @id` contract, not a new identity per role, locale or
  appearance. Include supported name/profile information matching visible resolved attribution; do not
  invent profile URLs or qualifications. Existing profile publication/access rules are unchanged.
- For Media participant/reviewer overlap, both relations reference the same Person. Actum may be the
  local publisher and the explicitly selected reviewer through the same global Organization identity.
- `reviewedBy` belongs on the local `WebPage` (the wrapper for Blog as well as Media), not on the
  `Article`/`BlogPosting` or the external work. Case does not gain this relation.
- Review attribution describes an actual accuracy/completeness check of the local material. Mere
  publisher responsibility, an empty field or a CMS operation is not evidence of a review.
- Roles represented in JSON-LD must match visible attribution on that page. A reviewer is never
  silently converted to an author, contributor or external publisher; a participant is not an author.
- Internal CMS user identities are never exposed. Optional unknown facts are omitted, not fabricated.

### Role mapping by kind

| Kind / explicit role | JSON-LD relation |
|---|---|
| Blog, 1-3 lawyer authors | Ordered `BlogPosting.author` Person references |
| Blog, explicit Actum author | `BlogPosting.author` references global Actum Organization |
| Blog, no author choice | Omit `author`; retain the editorial warning; do not invent a blocking Google-required-author error |
| Blog, selected distinct lawyer reviewer | Local `WebPage.reviewedBy` references that Person |
| Blog, no reviewer | Omit `reviewedBy` without a missing-reviewer warning |
| Case | Ordered `Article.author`: primary first, then 0-2 coauthors; no `reviewedBy` |
| Media participants | Local `WebPage.mentions` references selected, visibly represented Persons |
| Media lawyer reviewer | Local `WebPage.reviewedBy` references the selected Person |
| Media explicit editorial Actum review | Local `WebPage.reviewedBy` references global Actum Organization |
| Media no review choice | Omit `reviewedBy` and retain the nonblocking editorial warning |

The dedicated Media selection is the participant source of truth. `mentions` represents their visible
presence without asserting authorship of the external text. Do not emit Schema.org `participant` on
Article/WebPage or infer `contributor`, `author`, `speaker` or an external review from this selection.
No new finer-grained interview/guest/speaker taxonomy or automatic text analysis is introduced.
Case coauthors are authors in `Article.author`, not a downgraded `contributor` list.

### Media original work and source link

- The local `WebPage.publisher` references Actum. Its `mainEntity` references the described external
  `CreativeWork`. The external work's publisher is the named source, not Actum or the selected lawyers.
  Do not guess the external personal author from source name, participants or review attribution.
- With a real source URL, use that validated absolute URL for the external work's `url` and stable
  external `@id`. The local canonical and `WebPage @id` remain the Actum detail page.
- With explicit "Без посилання", omit external `url` and identify the described work structurally as
  `{localCanonicalUrl}#external-work`. This fragment is a local graph identifier, not a claimed
  original-source URL. Do not turn it into a visible "open original" link or an external canonical.
- The source's name remains available in both modes. Optional original-work title/date/type may only
  come from known source facts; do not manufacture them or infer NewsArticle/VideoObject from a URL.
- Local public dates and external-work dates keep their distinct existing meanings.

Other preserved rules:

- all primary and additional service-tree endpoints become deduplicated `about` references;
- for Media, Actum service relations belong to the local WebPage, not invented external-work topics;
- canonical URL, public dates, cover, and `BreadcrumbList` are included when applicable;
- absent optional properties are omitted;
- public graph assembly does not alter profile associations, filters or collection selection/order;
- an editorial warning cannot become a publication-blocking graph error merely because Google lists
  a property as recommended; actual reference, safety and graph-integrity errors remain enforced.
