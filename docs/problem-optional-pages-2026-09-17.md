# Проблемы без собственных страниц

Согласовано 2026-09-17. Правило относится только к ERP-объектам «Проблема».

1. `showOnSite=false`: проблема не включается в формируемые списки на сайте.
2. `showOnSite=true`: проблема может отображаться обычным текстом независимо от наличия slug и страницы.
3. Отсутствие собственного slug проблемы — не warning и не error.
4. Без корректных slug практики, услуги и проблемы создавать новую страницу проблемы нельзя. Это проверка возможности операции, а не ошибка объекта.
5. Наличие slug не обязывает создавать страницу. Отсутствие страницы проблемы не порождает критическую диагностику «страница не создана».
6. Ссылка появляется только при наличии опубликованной страницы того же объекта, языка и регионального контекста. Черновик сам по себе не даёт ссылку; новый черновик поверх опубликованной версии не отменяет существующую ссылку.
7. Если подходящей опубликованной страницы нет, отображается текст без ссылки, стрелки перехода и подстановки `#`. Ссылку нельзя угадывать по slug.
8. Дополнительный признак «страница планируется» не вводится. Статусы покрытия сохраняют информацию о наличии страницы и возможности её создания; не каждая отсутствующая страница является обязательной недоделкой. API отдельно сообщает допустимость отсутствия страницы и возможность создания. CMS не должна превращать допустимое отсутствие в красную ошибку покрытия.

## Нейтральное покрытие необязательных страниц

Уточнение 2026-09-17 после проверки списка проблем услуги: снятие ошибки из `diagnostics` само по себе не исправляет отображение `pageCoverage`.

- В `pageCoverage.own` и строках детализации добавляются `absenceIsExpected` и `canCreate`.
- `absenceIsExpected=true` означает допустимое отсутствие отдельной страницы проблемы: либо slug корректен, но страница не создана, либо создание недоступно только из-за отсутствия собственного slug проблемы.
- Это не признак, хранимый в ERP/CMS-записи, а вычисляемая информация. Скрытый объект, проблемы с родителем/регионом, конфликт URL и ремонт существующей страницы этим исключением не скрываются.
- `canCreate=true` только для действительно доступной к созданию страницы; допустимость отсутствия страницы не разрешает её создание без slug.
- В итогах потомков и групп добавляется `optionalNotCreated` — нейтральная часть общего `notCreated`. Старые статусы и счётчики сохраняют технический смысл и не меняют формат.
- Для строки проблемы с допустимым отсутствием CMS показывает нейтральное «Без окремої сторінки». При отсутствии slug поясняет: «Проблема відображається у списку без посилання. Для створення сторінки потрібен slug». Если slug есть, поясняет, что создание страницы необязательно.
- Необязательные несозданные страницы в счётчиках отделяются от требующих внимания; они не окрашиваются красным. Например, `9 / 0 / 9` региональных вариантов без slug — не девять ошибок.
- Кнопка создания учитывает доступные к созданию варианты и ремонт, а не только `descendants.state=incomplete`. Наличие девяти заблокированных вариантов не разрешает создание.
- В смешанных списках практики, услуги или региона настоящие блокировки и страницы с необходимостью ремонта остаются видимыми.

Обновляются CMS backend и CMS-front. Публичный frontend, правила включения в списки и определения опубликованной ссылки в этом уточнении не меняются. Миграция БД не нужна.

Порядок отдельного согласованного выката: backend, затем CMS-front. Старый frontend игнорирует новые поля и до своего обновления может продолжать показывать красную метку. Новый frontend при старом ответе не должен угадывать по тексту сообщения, у какого объекта отсутствует slug, и скрывать ошибки родительской иерархии.

Приёмка:

1. Видимая проблема без slug: нейтральная строка, нейтральные отсутствующие региональные страницы, создание недоступно.
2. Добавлен корректный slug, страницы ещё нет: отсутствие всё ещё допустимо, создание доступно.
3. Страница создана/опубликована: обычный статус существующей страницы.
4. Не хватает slug практики/услуги, есть конфликт URL или существующая страница требует ремонта: проблема не скрывается под нейтральной меткой.
5. Смешанные группы и постраничная детализация сохраняют корректные общие счётчики, отделяя необязательное отсутствие.

### Локальная проверка реализации

Проверено 2026-09-18 в отдельных рабочих ветках `codex/problem-coverage-neutral` для backend и CMS-front:

- Backend: 976/976 тестов, сборка TypeScript успешна.
- CMS-front: 574/574 unit-тестов, общий ESLint и TypeScript typecheck успешны. Production-сборка frontend не запускалась без отдельного запроса, согласно правилам репозитория.
- Сквозная проверка реального backend-сервиса на подставной БД и функций CMS-front: девять региональных вариантов без slug и с пробельным slug нейтральны, создание отключено; корректный slug разрешает создание, но не делает страницу обязательной; отсутствие slug родителя остаётся ошибкой покрытия; скрытый объект остаётся скрытым.
- Проверены цвета счётчиков, пояснения, смешанное покрытие, детализация, фильтрация, сортировка и изменение общего счётчика при загрузке следующих страниц детализации.
- Общая проверка Prettier выявляет существующие замечания по всему репозиторию CMS-front; массовое переформатирование вне текущей задачи не выполнялось.

Это локальная реализация и проверка, не отчёт о выкате. В рамках этой правки коммиты, push, деплой, миграции и изменения живых данных не выполнялись.

## Применение

Backend пакетно проверяет доступность целевых страниц по устойчивому ID объекта, языку и региону. При публичном чтении уточняются только ссылки в списках проблем. Публикация/снятие целевой страницы отражается при следующем чтении родительской страницы без публикации её черновиков.

Изменение не запускает автоматическое обновление членства ERP-объектов в уже сохранённых списках. Чтобы добавить проблемы, ранее исключённые из старого snapshot из-за отсутствия slug, нужна обычная перепубликация исходной страницы. Выполнение этой операции на реальных данных требует отдельного разрешения.

Миграции БД не нужны. Backend и публичный frontend требуют согласованного выката. Технический контракт и тестовые сценарии: `cms-back/docs/problem-optional-pages.md`, `site-front/docs/problem-links.md`.
