# ТЗ: ролі CMS та публікація в межах повноважень

Дата: 18 жовтня 2026 року.

**Статус: проєкт письмового ТЗ для погодження перед реалізацією.** Продуктові рішення
нижче погоджені з власником у розмові; цей документ збирає їх у перевірюваний контракт.
Запушена документація не означає готовність коду, виконання міграцій, зміну ролей
користувачів, публікацію контенту чи деплой у develop/release.

## 1. Рішення та межі

1. ERP-розділ, повні картки довідників і їх адміністрування доступні лише адміністратору.
2. Глобальні секції доступні адміністратору та окремому редактору глобальних секцій.
   Обидві ролі можуть їх редагувати й публікувати.
3. Замість широких `editor` і `publisher` вводяться окремі редактори сторінок та публікацій.
4. SEO всіх сторінок редагують лише SEO-редактор та адміністратор. SEO-редактор також
   керує редиректами й самостійно публікує SEO вже опублікованих сторінок.
5. Перша публікація сторінки потребує підтвердженої збереженої SEO-версії.
6. Неадміністратори мають лише обмежений перегляд журналу оновлень у своєму діапазоні.
   Усі ручні команди черги та її налаштування залишаються адміністратору.
7. Ролі можна поєднувати. Їхні дозволи об'єднуються, але системні обмеження не зникають.

Це зміна прикладної авторизації CMS, не зміна зовнішнього доступу до середовищ.
Немає дозволу змінювати інфраструктурні доступи або чинні призначення користувачам.
Назви ролей не змінюють правил ERP-власності, незмінності збережених версій, доступності
локалей, підтриманих типів сторінок, валідації та дозволених стратегій успадкування.

Після затвердження цей контракт замінює лише суперечливі правила повноважень у
[ТЗ редиректів](redirects-specification-2026-09-13.md),
[ТЗ оновлення сторінок](stale-page-refresh-contract-2026-10-12.md) та уточнює межі
публікації й відновлення з [контракту версій секцій](section-authoring-versioning-contract-2026-10-04.md).
Інші правила цих документів залишаються чинними. До контрольованого впровадження
нової моделі фактична авторизація залишається попередньою.

## 2. Назви ролей

Назви в інтерфейсі українські. Стабільні технічні ключі в API та БД залишаються латиницею.
Назву не використовувати як ключ перевірки доступу.

| Назва в CMS | Технічний ключ | Призначення |
| --- | --- | --- |
| Адміністратор | `admin` | Усі дозволені адміністративні операції CMS |
| Редактор сторінок | `page_editor` | Контент і публікація звичайних сторінок, без SEO |
| Редактор публікацій | `publication_editor` | Контент і публікація блогу, медіа, справ та їх списків, без SEO |
| SEO-редактор | `seo_editor` | SEO всіх сторінок, його підтвердження/публікація та редиректи |
| Редактор глобальних секцій | `global_section_editor` | Перегляд, редагування та публікація глобальних секцій |
| Спостерігач | `viewer` | Перегляд сторінок без змін |

Немає окремих обмежень «лише власні матеріали» або «лише одна мова». Роль працює
з усіма об'єктами свого типу та їх дозволеними мовними й регіональними варіантами.
Зокрема, «Про нас» залишається загальноукраїнською сторінкою без регіональних варіантів.

## 3. Діапазони сторінок

`publication_editor` отримує рівно шість типів:

- `blog_page`, `blog_collection_page`;
- `media_page`, `media_collection_page`;
- `case_page`, `case_collection_page`.

Поточний явний перелік для `page_editor`:

- `home_page`, `about_page`, `career_page`, `contacts_page`;
- `practice_collection_page`, `practice_page`, `service_page`, `problem_page`, `intent_page`;
- `lawyers_page`, `lawyer_page`, `lawyer_license_page`, `sitemap_page`.

Дозвіл на тип не створює відсутній редактор, не вмикає непідтриману публікацію та
не робить автоматично сформовані секції редагованими. Наприклад, runtime-профіль
адвоката не можна змінити через роль редактора сторінок: його ERP-джерело залишається закритим.
Нові типи не повинні автоматично потрапляти в правило «все, що не блог»;
їх явно класифікують у серверній політиці. Невідомий тип не дає нових прав.

РС = редактор сторінок; РП = редактор публікацій; РГС = редактор глобальних секцій.

| Публікація їх контенту | Так | Так | Ні | Ні | Ні | Ні |

| Публікація їх контенту | Так | Ні | Так | Ні | Ні | Ні |
| Редагування SEO всіх сторінок | Так | Ні | Ні | Так | Ні | Ні |
| Підтвердження SEO перед першою публікацією | Так | Ні | Ні | Так | Ні | Ні |

Перегляд охоплює дозволену історію, діагностику й прев'ю. Редактор сторінки може
бачити SEO readonly для контексту, але не змінювати його, перейменовувати SEO-версії,
підтверджувати їх чи підміняти вибір SEO у плані публікації.
SEO-редактор може читати контент сторінки, але редагувати лише її дозволені SEO-поля.
РГС без додаткових ролей має історію/прев'ю власних глобальних секцій, не каталог сторінок.

## 5. ERP, глобальні джерела та допоміжні дані

### 5.1. ERP

Закриті повні ERP-списки, картки, діагностика імпорту/компетенцій та команди адміністрування.
Адміністративний доступ не означає дозвіл редагувати поля, що належать ERP: правила
read-only і синхронізації джерела зберігаються.

Для дозволеної форми залишити мінімальні lookup-відповіді: вибір автора, перевіряючого,
адвоката, практики, послуги, офісу тощо, якщо цього вимагає схема. Відповідь містить
ідентифікатор та необхідний підпис/публічну ознаку, а не повну ERP-картку, контакти,
службові оцінки, raw JSON чи діагностику. Контекст форми перевіряється сервером.
Lookup не відкриває ERP-редактор і не дає права змінити вибрану сутність.

### 5.2. Глобальні секції

Неавторизований редактор бачить глобальні елементи у зібраному прев'ю сторінки,
але не отримує доступу до їх редактора, історії, raw source payload або чернеток.
Назва успадкованого блока й зрозуміле пояснення залежності допустимі без повної картки джерела.
Прямий перехід за URL або використання ID у вкладеному запиті не обходить заборону.

Власний локальний override сторінки залишається у сфері її редактора лише там,
де це вже дозволяє схема; він не змінює глобальне джерело. Цей контракт не додає
нових override-стратегій і не дозволяє змінювати системні binding/source ID вручну.

Публікація глобальної секції може штатно запустити оновлення її залежних сторінок,
включно з чужими для РГС типами. Це обмежений системний наслідок дозволеної публікації,
а не право РГС викликати довільну публікацію сторінки, змінювати її чернетки чи керувати чергою.
Редактор отримує підтвердження операції своєї секції та безпечний підсумок її наслідків.

Глобальні налаштування без версій не отримують штучної кнопки публікації чи історії.
У технічному інвентарі явно вказати, де збереження застосовує зміну відразу;
доступ до глобального контенту не надає доступу до системних налаштувань CMS.

### 5.3. Медіа

Завантаження і вибір файлів доступні в дозволеному редакторі, з перевіркою власника
та цільового поля: SEO, власний контент сторінки або глобальна секція.
Не відкривати через медіабібліотеку закриті ERP-вкладення чи чужі службові файли.
Зміна спільного медіазапису не повинна бути непрямим способом змінити заборонений
контент. Потрібні перевірки використання або окремий дозволений медіазапис.

## 6. Розділена публікація SEO та контенту

SEO означає поля/композицію SEO-секції відповідно до схеми, а не будь-які дані, що
впливають на пошук. H1 матеріалу, його автор, текст, дати, зв'язки та блоки залишаються
контентом. Генеровані canonical/JSON-LD та правила slug не стають довільно редагованими.

### 6.1. Підтвердження перед першою публікацією

1. SEO-редактор або адміністратор зберігає SEO та явно підтверджує його готовність.
2. Підтвердження прив'язане до точного `sectionVersionId`, сторінки, локалі та перевіреного
   контексту маршруту/успадкування. Воно не публікує сторінку і не дає їй публічного URL.
3. Профільний редактор готує план першої публікації. План показує конкретну підтверджену
   SEO-версію, а не просто прапорець «SEO готове» чи останню чернетку.
4. На commit сервер повторно перевіряє підтвердження, права, контекст і очікуваний стан.
   Відсутнє, відкликане або неактуальне підтвердження блокує першу публікацію з поясненням.
5. Адміністратор теж виконує підтвердження; він може виконати обидва кроки самостійно,
   але не має прихованого обходу перевірки готовності.

Новий SEO-чернетковий варіант не отримує підтвердження автоматично і не підміняє раніше
підтверджений ID. Саме збереження нової версії не переписує старе підтвердження.
Зміна контексту, що впливає на перевірений SEO-результат, потребує повторного підтвердження.
Для успадкованого SEO фіксуються також точні джерела й перевірений результат композиції.
Протокол підтвердження, відкликання та конфліктів деталізується в API-контракті до реалізації UI.

### 6.2. Публікація контенту вже опублікованої сторінки

Редактор публікує дозволені контентні секції свого типу сторінки. SEO береться з поточного
опублікованого знімка, не з latest draft і не з нового підтвердження для першої публікації.
Незавершені SEO-зміни залишаються чернетками. Якщо новий контекст несумісний зі збереженим
SEO, операція потребує окремого погодженого рішення, а не мовчазного захоплення SEO-чернетки.

### 6.3. Окрема публікація SEO

SEO-редактор обирає точну збережену SEO-версію. Базою є поточний опублікований знімок
цієї сторінки. Новий знімок змінює лише SEO та його явно визначені похідні проєкції;
весь інший опублікований контент, порядок, видимість, глобальні та runtime-блоки зберігаються.
Не читати для такого складання чужі чернетки, не оновлювати заодно ERP/runtime-залежності.
Немає опублікованої бази: доступне підтвердження SEO, але не перша публікація всієї сторінки.

Зміни похідних метаданих і графа JSON-LD визначає серверна схема. Не можна назвати
«SEO-публікацією» повне перескладання зі свіжих робочих даних. Непідтриманий старий
знімок дає явний блокер, без fallback на широку публікацію.

### 6.4. Спільні гарантії

- Зберегти існуючий plan/commit, optimistic concurrency, ідемпотентність, аудит та доставку кешу.
- Паралельні SEO/контентні публікації не затирають одна одну: зміна базового знімка
  між plan і commit вимагає нового плану, а не тихого перезапису.
- Права та активність користувача перевіряються повторно на commit; відкликана роль
  не дозволяє виконати раніше підготовлений план або нову команду через retry.
- Ролі разом не означають автоматичну публікацію всіх чернеток. Дозволений набір змін
  явно показаний у плані; ширша операція перевіряє кожну включену секцію.
- Системна черга продовжує роботу за власним published-only контрактом. Обмеження
  інтерактивних ролей не повинні зупинити її чи розширити склад її оновлень.

## 7. Історія, відновлення та обхід через інші команди

Історія залишається незмінною. Перегляд версії не є редагуванням; «взяти за основу»
дозволяється лише за наявності права запису саме цієї секції та її контексту.

Відновлення контенту не відновлює старе SEO; відновлення SEO не відновлює старий
контент. РГС працює з версіями глобальних секцій, не зі знімками всього сайту.
Повний історичний page rollback не можна залишити неадміністратору як обхід цих меж.
Якщо безпечне scoped-відновлення ще не підтримується, дія недоступна з поясненням;
підміна її старим повним rollback заборонена. Адміністративний rollback зберігає
існуючі перевірки та явний план впливу.

Перевірити також копіювання, створення перекладу, імпорт, bulk bootstrap, зміну
видимості/композиції, перейменування версії, архівацію та видалення.
Створення структурної порожньої SEO-секції разом зі сторінкою не надає редактору
права записувати в неї SEO-контент чи створювати підтвердження від імені SEO-редактора.
Копіювання/переклад не переносить підтвердження на нову сторінку або локаль.

SEO має право керувати редиректами всіх сторінок, але це не право редагувати їх тіло,
ERP-slug або довільно змінювати статус контентної сторінки. Команди, що одночасно
змінюють маршрутизацію та саму сторінку, потребують обох відповідних дозволів або адміністратора.

## 8. Журнал оновлення сторінок

РС бачить лише свої типи, РП лише свої, SEO і спостерігач усі доступні сторінки.
РГС без іншої ролі не отримує розділ журналу сторінок.

Неадміністратору показувати назву/URL сторінки, локаль, час, зрозумілу причину,
стан очікування/виконання/успіху/помилки, останнє успішне оновлення та номер операції
для звернення до адміністратора. Результат публікації та доставки кешу не змішувати.
Приклад причини: «Змінилися відгуки» або «Оновлено спільну форму заявки».

Не повертати raw payload, внутрішні графи залежностей, службові журнали, stack traces,
конфігурацію обробника, закриті ERP/глобальні дані або секретні URL/заголовки.
Безпечний номер операції не є дозволом відкрити її повну адміністративну картку.

Лише адміністратор може прискорювати, повторювати операції/етапи, відновлювати
обробник, керувати паузою та інтервалами. Заборона діє в усіх точках входу, включно
з окремими retry/effects endpoints поза екраном журналу. Звичайна публікація зі
свого редактора залишається дозволеною; вона не є заміною керування чергою.

Сервер фільтрує записи, totals, badge, пошук, пагінацію, деталі операцій і пов'язані
сутності. Змішані операції не повинні розкривати приховані сторінки через aggregate
чи вкладений JSON; потрібна дозволена проєкція або відмова в деталях.

## 9. Вимоги до реалізації

### Backend

Побудувати єдину політику `користувач -> дія -> ресурс -> контекст` з урахуванням
типу сторінки, slot, ownership, локалі, зв'язку версії та поточного стану.
Широкого `pages.write` або `sections.write` без цих перевірок недостатньо.
Одна політика використовується контролерами, command handlers, читанням списків,
publication plan/commit, історією, runtime-inspect і capabilities для frontend.

Перевіряти кожен елемент пакетної операції до змін. Заборонений елемент не можна
мовчки пропустити або виконати частину команди під ширшими правами.
Закрити legacy endpoints; нові маршрути не компенсують обхід через старі.
Відповідь про заборону не повинна розкривати закритий об'єкт.
Зберегти блокування disabled-користувачів і захист останнього активного адміністратора.

До frontend-реалізації узгодити конкретні DTO/endpoints, коди відмов, стан підтвердження
SEO, capabilities, точний перелік похідних SEO-проєкцій та план міграції даних.
Цей документ не вигадує URL API і не стверджує наявності цих механізмів у поточному backend.

### CMS-front

Українські назви ролей, мультивибір ролей, зрозумілий підсумок доступу користувача.
Меню, матриці, списки, поля, історія та кнопки використовують серверні capabilities.
Недоступні редактори не завантажувати приховано і не передавати їх дані в браузер.
SEO readonly для редакторів контенту; для SEO-редактора решта контенту readonly.

Додати видимі стани «SEO не підтверджено», підтверджену версію/дату/ініціатора та
причину блокування першої публікації. Розділити команди публікації контенту й SEO.
Після зміни ролей очистити недоступні клієнтські дані; втрата прав не перетворює
локально відкриту форму або старий plan на дозвіл запису.

### Site-front

Нові ролі самі по собі не потребують UI на публічному сайті. Перевірити, що зміна
SEO доходить до HTML/head, потрібних похідних і кешу без зміни тіла сторінки.
Якщо знадобиться зміна публічного контракту, оформити її окремим інтеграційним пунктом.

## 10. Перехід зі старих ролей

1. Інвентаризувати користувачів та ролі окремо для develop і release, без зміни даних.
2. Підготувати й погодити явне призначення нових ролей кожному старому `editor`/`publisher`.
   Не призначати автоматично всі нові ролі або `admin` для збереження колишніх широких прав.
3. `admin` і `viewer` зберігають ключі; спостерігач втрачає старий доступ до ERP та
   глобальних редакторів відповідно до нової матриці. Disabled-статуси не змінюються.
4. При переході старі `editor`/`publisher` більше не дають прав і не доступні для нових
   призначень. Непризначені/невідомі ролі не повинні перетворюватися на ширший fallback.
5. Зберегти історичні актори, контент, версії, знімки та аудит. Не перепубліковувати сайт
   і не підтверджувати масово чернетки під виглядом міграції ролей.
6. Уже опубліковані сторінки продовжують використовувати своє опубліковане SEO.
   Для ще не опублікованих сторінок потрібне явне підтвердження, не автоматичний backfill.
7. Перед live-переходом окремо погодити виконання, перевірити резервний стан призначень,
   backend/frontend-сумісність і спосіб відновлення без прихованого повернення широких прав.

Спочатку погоджується це ТЗ, потім API/план реалізації, тести, призначення користувачам
і контрольоване впровадження. Поточне завдання обмежене документацією та її push.

## 11. Критерії приймання

| Перевірка | Очікуваний результат |
| --- | --- |
| Кожна роль окремо й у поєднаннях | Серверна поведінка відповідає матриці, немає неявних успадкованих широких прав |
| РС відкриває публікацію або РП звичайну сторінку | Немає неавторизованого перегляду/запису через UI, URL, ID, пошук чи bulk |
| Редактор надсилає SEO через прямий запит або загальний Save | Відмова без зміни SEO чи його підтвердження |
| SEO-редактор надсилає контентну секцію або сторонній ID | Відмова без зміни контенту |
| Заборонені ERP/глобальні дані | Не витікають через nested editor, history, runtime-inspect, media чи lookup |
| Lookup у дозволеній формі | Можна вибрати автора/практику без доступу до повної ERP-картки |
| Публікація глобальної секції РГС | Успіх і штатні залежні оновлення, але немає права довільно публікувати сторінки |
| Перша публікація без підтвердження SEO | Заблокована з поясненням; з валідним точним підтвердженням дозволена |
| Нова SEO-чернетка після підтвердження | Не підтверджується й не підхоплюється автоматично |
| Копія/переклад/зміна контексту | Чуже чи застаріле підтвердження не придатне для першої публікації |
| SEO-публікація за наявності контентних чернеток | Змінюються лише SEO та дозволені похідні; контент і чернетки збережені |
| Контентна публікація за наявності SEO-чернетки | Опубліковане SEO збережене, чернетка не виходить на сайт |
| Одночасна публікація SEO/контенту або відкликання ролі | Конфлікт/відмова без втрати чужих змін та обходу авторизації |
| Відновлення старої версії/знімка | Немає непрямого відновлення заборонених секцій |
| Журнал, sidebar badges, totals, detail, mixed operations | Лише дозволені сторінки та безпечні поля, узгоджена пагінація/лічильники |
| Ручні queue/retry/effects/recovery запити неадміністратора | Відмова, навіть якщо користувач може публікувати свої сторінки/секції |
| Міграція користувачів | Лише погоджені призначення; старі ролі не обходять нову політику; останній адмін збережений |
| UA/RU/EN та дозволені регіональні варіанти | Однакові перевірки прав, коректна локаль SEO-підтвердження |

Потрібні unit-тести політики, API-тести позитивних і негативних сценаріїв, DB integration
для підтвердження/публікації/concurrency, тести BFF і browser-приймання всіх ролей.
До окремого погодження реалізації жоден пункт не вважається виконаним лише завдяки цьому ТЗ.
